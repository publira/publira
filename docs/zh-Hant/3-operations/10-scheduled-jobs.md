安裝實例在沒有請求的情況下所做的一切，都由`publira worker`完成：它會發布排定在此刻的章節、告訴Web應用程式哪些快取頁面因變更而過時、寄送郵件和推播通知、重新建立統計和排行榜，並刪除超過保留期限的內容。不需要其他任何東西依計時器執行，也不需要主機的cron或Kubernetes CronJob。本頁說明什麼工作在何時執行、如何判斷症狀背後是哪個工作，以及如何以`publiractl job`手動執行工作。

每個工作的間隔、調整它的變數以及完整的工作清單，請參閱[`publira worker`參考文件](https://github.com/publira/publira/blob/main/server/cmd/publira/README.md#publira-worker)和[`publiractl job`參考文件](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#job)；本頁不再重複。

## 症狀背後是哪個工作

從您看到的現象出發，查看負責它的工作：

| 章節的網站頁面在免費閱讀期間內仍顯示價格，或在期間結束後仍顯示免費 | 免費閱讀期間 | [免費閱讀期間](#免費閱讀期間與其他快取頁面) |

這些工作全都需要`publira worker`先處於執行中且就緒的狀態：worker停止的安裝實例雖然能提供每個頁面，卻不會發布、不會寄送，也不會重新建立任何東西。worker上的`GET /readyz`會為它登入時所用的每個資料庫登入身分列出一項檢查，因此停止回應的登入身分會在那裡被指出。在依佇列拆分worker的安裝實例上，每個工作還需要一個負責其佇列且正在執行的worker，如[只負責部分工作的worker](#只負責部分工作的worker)所述。

### 工作失敗的記錄位置

worker會將每次失敗記錄在日誌中，日誌行會指出是哪個工作。排程工作的每次執行，也都會在資料庫的`river_job`資料表（worker將自己的工作排入佇列的地方）中留下一列，因此可以從該資料表看出工作是否執行過，以及何時執行。

該列對失敗的記錄方式取決於工作。發布、免費閱讀期間、日期切換、置頂公告、預約系列、活動橫幅、活動價格、代幣到期、發布後免費和預約公告這些工作，即使其中有部分失敗也會完成該次執行：每個工作都會記錄它無法完成的部分，並留待一分鐘後的下一次執行，因此它們的列會顯示為已完成，失敗只會出現在日誌中。其他所有工作都會在其列中將該次執行記錄為失敗，並在`errors`欄中保留每次嘗試的錯誤，指出它停在哪個租戶和哪一天。請以資料庫的[管理用登入身分](../2-deployments/2-installing.md#佈建服務)連線，使用`psql`查詢：

```sql
SELECT kind, state, attempt, finalized_at, errors
FROM river_job
WHERE state IN ('retryable', 'discarded')
ORDER BY id DESC
LIMIT 20;
```

`retryable`是等待下一次嘗試的執行，`discarded`則是已用完嘗試次數的執行。已完成或已取消的列會在一天後刪除，已捨棄的列則在一週後刪除，因此請在症狀出現後盡快查看。outbox則保有自己的記錄，如[下文](#查看被放棄的項目)所述。

## 預約發布

工作人員預約的章節，會在時間過後由worker發布，同時通知系列的追蹤者，並捨棄將其列為已預約的快取頁面。worker每分鐘尋找一次到期的章節，因此章節會在其時間後約一分鐘內上線。

發布失敗時，會在同一次執行中重試幾次。若所有嘗試都失敗，章節會維持**已預約**，worker會撰寫一則標題為「有章節發布失敗」的通知，給租戶主控台中的租戶管理員，以及平台主控台**通知**下的每位營運人員。這樣的通知每個章節只會撰寫一次。worker會在之後的每次執行中再次嘗試該章節，因此一旦原因排除——資料庫故障、遷移尚未執行——章節就會自行發布。工作人員不必等待：在租戶主控台的章節頁面上，於**發布設定**下輸入目前時間，就會在該請求中發布章節，不經過worker。不過其追蹤者仍是由worker透過[outbox](#outbox郵件推播與快取重新驗證)通知。

## 免費閱讀期間與其他快取頁面

有六個工作負責讓Web應用程式的快取頁面在時間經過後保持正確：

- **免費閱讀期間**。**免費閱讀期間**項目內的章節，從期間開始的那一刻起就是免費的，結束後又會恢復價格，這不涉及任何工作：每次讀取都會將期間與目前時間比較。這個工作修正的是網站在邊界之前快取的頁面，它會在每個期間的兩端將這些頁面標記為過時。
- **租戶的日期切換**。在每個租戶自身時區的午夜，它會將網站的每週更新表標記為過時，這是唯一以租戶的日曆日為答案的頁面。
- **置頂公告**。公告的**停止展示的時間**一過，它就會將公告從橫幅上撤下，並將橫幅標記為過時。
- **預約系列**。以未來的**發布日期與時間**儲存的系列，從該時間起即公開，這不涉及任何工作：每次讀取都會將該時間與目前時間比較。這個工作修正的是網站在系列仍隱藏時快取的系列列表、作者頁面和系列本身的頁面，它會在時間過後將這些頁面標記為過時。在同一次執行中，它會將系列隱藏期間發布的章節的日期改為該時間，並將其發布通知交給[outbox](#outbox郵件推播與快取重新驗證)。
- **活動橫幅**。已發布的活動橫幅會從其期間開始顯示到結束，這不涉及任何工作：每次讀取都會將期間與目前時間比較。這個工作修正的是網站在邊界之前快取的橫幅，它會在每個已發布橫幅期間的兩端將其標記為過時。
- **活動價格**。適用活動價格的章節，從活動開始到結束都以該價格報價和收費，這不涉及任何工作：每次讀取和每次結帳都會將活動與目前時間比較。這個工作修正的是網站在邊界之前快取的章節頁面和系列頁面，它會在每個活動的兩端將其標記為過時。

每個工作都每分鐘執行一次。它們都不會自行捨棄快取：每個工作都會將捨棄記錄為outbox中的一個項目，再由worker傳送給Web應用程式，因此若worker已設定`PUBLIRA_REVALIDATE_TOKEN`，頁面卻仍維持過時，那就是outbox的問題，如[下文](#outbox郵件推播與快取重新驗證)所述。

在沒有`PUBLIRA_REVALIDATE_TOKEN`的情況下啟動的worker，快取重新驗證是關閉的。這些工作此時完全不記錄捨棄，卻仍會將每個邊界和每個系列的時間視為已過去，並撤下每個橫幅，因此outbox沒有可重試的東西，即使以權杖重新啟動worker，也無法找回那些捨棄。原本會被捨棄的頁面會保留其快取內容，直到同一對象的下一次變更捨棄它們，或其快取到期為止。請在您需要準時的第一個邊界之前，於`publira server`和`publira worker`上設定權杖，如[安裝](../2-deployments/2-installing.md#產生密鑰)所述。

這些工作沒有`publiractl job`指令，也不需要：每次執行時，它們都會處理所有已經過去的時間，包括worker啟動後的第一次執行。

## 統計與排行榜

統計、排行榜、系列評分和推薦，會在每一天（以租戶自身的時區計算）結束後，根據閱讀活動建立。由四個工作依序組成一條鏈來完成：

1. **閱讀投影**（`project-episode-reads`）將每次讀完記錄為分析事件。
2. **每日統計**（`aggregate-content-stats`）重新建立每個已結束日期中各系列和各章節的瀏覽、讀完、購買、評分、收藏和留言，以及讀者在每個章節中讀到了多遠。網站顯示的系列評分就是由這些資料計算的。它還會記錄哪些已登入讀者在當天瀏覽、讀完或購買了章節，以及屬於哪個系列，主控台正是依此追蹤某一週註冊的讀者。升級到引入這些記錄的版本時，會為分析事件仍保留著的每一天補上這些記錄；在那之前已被清除的日子則沒有記錄，之後也無法補上。
3. **排行榜**（`aggregate-rankings`）重新建立網站**排行榜**頁面所顯示的每日和每週排行榜。
4. **推薦**（`build-recommend-features`）重新建立每位讀者的推薦所依據的快照。

這條鏈每小時啟動一次，每個環節結束時會啟動下一個環節。由於每個租戶的午夜落在不同的小時，租戶的一天會在結束後大約一小時內，再加上鏈所需的時間，重新建立完成。因此，在租戶午夜過後幾小時排行榜還沒更新是正常的；但一整天都沒有更新就不正常了。

worker會為每個租戶記住每個環節最後完成的日期，並從其下一天開始。某一天失敗時，該租戶會停在那裡，其他租戶則繼續進行：錯誤會出現在失敗環節的`river_job`列中，該次執行最多嘗試三次，下一次每小時的執行會再從失敗的那一天開始。原因排除後，該租戶會依序自行補上所有遺漏的日子。

## 其他排程工作

| 工作 | 頻率 | 內容 |
| --- | --- | --- |
| 發布後免費 | 每分鐘 | 為系列的發布後免費規則所涵蓋的每個已發布、有價格的章節加上免費閱讀期間：章節發布後已經過設定的天數，且不屬於規則保留價格的最新章節。期間從那一天開始，若當時有仍在進行中的手動排定期間，則從該期間結束時開始，而若該期間被刪除，則移回那一天。期間持續到規則不再涵蓋該章節為止：以關閉的狀態或排除該章節的數值儲存規則會立即將其移除，而章節以其他方式離開規則時（例如移入最新章節之列或被撤下），則會在下一次執行時移除。章節的頁面會在同一次執行中標記為過時，就像期間開始或結束時一樣。與讓快取頁面保持準時的工作一樣，它沒有`publiractl job`指令 |
| 預約公告 | 每分鐘 | 在時間過後送出工作人員預約的每則公告，如[公告](../4-console/3-setup/4-announcements.md#預約公告)所述：將其標記為已送出（這正是讓讀者看到它的條件）、將其通知交給[outbox](#outbox郵件推播與快取重新驗證)，並將讀者的公告頁面，以及以橫幅顯示的公告的橫幅標記為過時。與讓快取頁面保持準時的工作一樣，它沒有`publiractl job`指令 |
| 代幣到期 | 每分鐘 | 對每筆在仍有未使用代幣時到期的代幣發放，在讀者的代幣記錄中寫入一筆項目，讓記錄說明這些代幣的去向。代幣在到期的那一刻就不再計入餘額，這不涉及任何工作，且絕不會恢復。與讓快取頁面保持準時的工作一樣，它沒有`publiractl job`指令 |
| 版稅結算（`close-royalty-statements`） | 每小時 | 在租戶的結算日到來後，結算設為**自動結算**的租戶所應結算的每個月份。已經手動或由先前執行結算過的月份則保持原樣 |
| Google Play退款同步（`sync-google-play-voided-purchases`） | 每小時 | 為每個已開啟Google Play商店的租戶，讀取Google Play在過去30天內退款的購買並將其收回，如[販售章節](../4-console/4-selling-episodes.md#退款)所述 |
| 搜尋索引建立（`build-search-index`） | 每30秒 | 在新儲存的搜尋引擎上建立索引，並將搜尋切換過去，如[搜尋](./7-search.md#遷移到其他引擎)所述 |
| 付款對帳（`reconcile-payments`） | 每10秒 | 執行租戶管理員開始的每項對帳，從租戶的付款服務商或商店讀取其期間內的付款，如[販售章節](../4-console/4-selling-episodes.md#與付款服務商對帳)所述。來源拒絕的執行會記錄為失敗，由租戶管理員重新開始，而不會重試。停止的worker執行到一半的對帳，會在兩小時後重新接手 |
| 資料下載（`build-data-exports`） | 每10秒 | 準備讀者索取的每份資料副本，將其儲存到儲存貯體中，並告訴讀者已準備就緒，如[讀者帳戶](../4-console/2-readers/1-accounts.md#讀者下載的個人資料)所述。在未設定物件儲存時提出的請求會記錄為失敗，由讀者重新索取，而不會重試。停止的worker處理到一半的請求，會在15分鐘後重新接手 |
| 清除工作（`purge-*`） | 每小時或每24小時 | 刪除超過保留期限的已撤回留言、分析事件和排行榜快照，如[平台預設值與政策](./9-platform-policies.md#保留期限)所述；兩步驟登入已用完的驗證挑戰；準備就緒七天後的讀者資料下載，以及已刪除帳戶的資料下載；以及任何租戶都不再使用、且已存在一天以上的圖片 |

## 只負責部分工作的worker

以`--queue`啟動的worker會執行其指定佇列的工作，其他工作則留給指定那些佇列的worker，如[依佇列拆分worker處理程序](../2-deployments/7-scaling-out.md#依佇列拆分worker處理程序)所述。本頁的工作分佈在六個佇列上，`river_job`以相同的名稱稱呼它們，唯有`outbox`被稱為`default`：

| 佇列 | 工作 |
| --- | --- |
| `outbox` | [outbox](#outbox郵件推播與快取重新驗證)：郵件、推播通知、快取重新驗證，以及搜尋引擎的索引更新 |
| `ticker` | 預約發布、免費閱讀期間、租戶的日期切換、置頂公告、預約系列、活動橫幅、活動價格、代幣到期、發布後免費，以及預約公告 |
| `maintenance` | 統計與排行榜鏈、版稅結算、Google Play退款同步，以及清除工作 |
| `search_index` | 搜尋索引建立 |
| `payment_reconciliation` | 付款對帳 |
| `data_export` | 資料下載 |

每個佇列都至少需要一個負責它且正在執行的worker。負責排程的worker會排程所有工作，無論它自己負責哪些佇列，因此沒有任何執行中的worker負責其佇列的工作不會遺失，但也沒有東西執行它：它會在`river_job`中等待，直到負責其佇列的worker啟動，然後如[停機後](#停機後)那樣執行。每個worker在啟動時都會以`worker leaves queues to other replicas`記錄它留給其他worker的佇列，並以`not_hosted`列出這些佇列。工作處於等待狀態的佇列會顯示在`river_job`中：

```sql
SELECT queue, kind, count(*), min(scheduled_at)
FROM river_job
WHERE state = 'available' AND scheduled_at < now() - interval '5 minutes'
GROUP BY queue, kind;
```

這裡出現的列，是已到期五分鐘卻沒有任何worker接手的工作：請啟動一個負責其`queue`的worker，或將該佇列加入執行中worker的`--queue`。

## 停機後

已停止的worker，或在沒有可用資料庫的情況下執行的worker，在那段期間什麼都不做，而工作會在資料庫中等待，不會遺失。它再次啟動時：

| 工作 | 啟動時 |
| --- | --- |
| outbox | 寄送所有等待中的項目。停止的worker處理到一半的項目，會在15分鐘後重新接手 |
| 預約發布 | 發布時間已過的所有章節，並通知其追蹤者 |
| 免費閱讀期間、租戶的日期切換、置頂公告、預約系列 | 將期間內邊界已過的所有頁面標記為過時，並撤下時間已到的所有橫幅 |
| 發布後免費 | 從那一天起開放期間內日期已過的所有章節 |
| 預約公告 | 送出時間已過的所有公告，並通知其讀者 |
| 統計與排行榜鏈 | 依序重新建立每個租戶遺漏的每一天，但分析事件已超過保留期限，或在先前儲存的較短期限下已被清除的日子除外：這些日子會被記錄為遺漏並跳過，且無法重新建立 |
| 版稅結算 | 結算所有已到應結算時間的月份 |
| 搜尋索引建立 | 建立待建立的索引 |
| 付款對帳 | 執行期間內開始的所有對帳 |
| 資料下載 | 準備期間內索取的所有副本 |
| 清除工作 | 只有在目前的小時或日期內（依時鐘計算，而不是從worker啟動時計算）尚未完成任何一次時才執行；此時的第一次執行會刪除期間內過期的所有內容 |
| Google Play退款同步 | 與清除工作一樣，只有在目前的小時內尚未完成任何一次時才執行。停機超過30天的worker會錯過Google Play已不再列出的退款 |

這段等待間隔，正是避免重新啟動或部署變成對每個資料表和整個儲存貯體進行全面掃描的機制。

## outbox：郵件、推播與快取重新驗證

請求留待之後處理的每一項副作用——郵件、推播通知、快取頁面的捨棄、搜尋引擎的索引更新——都會在與引起它的變更相同的交易中寫入outbox。因此，變更絕不會在沒有其副作用的情況下被儲存，而worker會在幾秒內傳送該項目。

失敗的項目會被重試，每次失敗後等待的時間加倍：一秒，接著兩秒，再來四秒。第十次嘗試失敗後，也就是第一次嘗試約九分鐘後，該項目會被永久放棄：它會變成**dead**，之後不會再有任何東西傳送它。永遠不可能成功的項目，例如寄給已刪除帳戶的郵件，會立即被放棄。worker不認識的類型的項目並不算失敗：在升級期間，那是只有新版本才會寫入的項目，因此worker會將它留給新版本的worker，每分鐘重新查看一次，只有在寫入一天後才會放棄它。失敗的意義取決於項目：

- **郵件**在SMTP伺服器（或啟用後的`email-renderer`）拒絕或無法連線時失敗，如[電子郵件](./6-email.md#安裝實例寄送的郵件)所述。
- 傳送到手機的**推播通知**，在租戶尚未儲存Firebase認證資訊時會被跳過而非失敗，因此儲存之後也不會重試。瀏覽器通知只有在開啟Web Push後才會傳送，如[Web Push](./8-web-push.md)所述。
- **快取重新驗證**在Web應用程式停擺時失敗。沒有`PUBLIRA_REVALIDATE_TOKEN`的worker，每次嘗試都會讓`publira server`或`publiractl`記錄的每個捨棄失敗；而它自己的工作所產生的捨棄則完全不會記錄，如[免費閱讀期間](#免費閱讀期間與其他快取頁面)所述。
- **Webhook傳送**（`event_type`為`webhook_delivery`）會將一個事件傳送到租戶管理員儲存的端點，如[API金鑰與Webhook](../4-console/10-api-keys-and-webhooks.md#重試與重新傳送)所述。它在該端點停擺或以`2xx`以外的任何狀態回應時失敗；當端點以`408`與`429`以外的其他`4xx`回應，或其主機解析為私人位址、回送位址、鏈路本機位址或共用位址時，會立即被放棄。端點是租戶自己執行的伺服器，因此失敗的傳送應由租戶而非安裝實例修正。若端點的簽章密鑰無法以`PUBLIRA_SECRET_ENCRYPTION_KEYS`中的任何金鑰開啟，該傳送會等待，且不消耗嘗試次數，直到金鑰放回或簽章密鑰重新產生為止。

`publira worker`上的`PUBLIRA_OUTBOX_MAX_ATTEMPTS`可設定嘗試次數。等待時間持續加倍，最長可達每次嘗試間隔一小時，因此多加幾次嘗試就能讓項目撐過長得多的停擺。無論`PUBLIRA_OUTBOX_MAX_ATTEMPTS`如何設定，Webhook傳送都有自己的20次嘗試額度，約八小時，因為它傳送到的伺服器停擺的時間可能比安裝實例自身的服務更久。

worker會透過HTTPS將Webhook傳送到各端點指定的任何主機與連接埠，因此限制worker對外流量的安裝實例必須允許這些流量，Webhook才能送達。

### 查看被放棄的項目

worker會以`outbox event dead`在日誌中記錄它放棄的每個項目，並在開啟指標後將其計入`publira.outbox.events.dead`指標，如[監控](./11-monitoring.md#outbox)所述；請對其中任一項設定警示。項目本身會連同最後的錯誤保留在`outbox_events`資料表中：

```sql
SELECT event_type, tenant_id, attempts, last_error, updated_at
FROM outbox_events
WHERE status = 'dead'
ORDER BY updated_at DESC
LIMIT 20;
```

dead的項目無法再次傳送，但Webhook傳送除外。其代價取決於它的`event_type`：

- **郵件**永遠不會送達。讀者需要重新申請密碼重設或確認郵件，管理員邀請則需要重新寄送，如[租戶的工作人員](./3-tenant-staff.md)所述。
- **推播通知**永遠不會送達，但通知會留在讀者於網站和應用程式中的通知列表裡。
- **快取重新驗證**會讓它指定的頁面繼續顯示先前的內容，直到同一對象的下一次變更再次捨棄它們，或其快取到期為止。
- **Webhook傳送**會在租戶主控台的**API金鑰與Webhook**中列為**已放棄**，租戶管理員可在端點修正後於該處重新傳送。

## 手動執行工作

`publiractl job <job>`會執行維護工作的一次執行後結束。它執行的程式碼與worker的排程執行相同，而不是其副本，因此行為與排程執行一致。它適用於排程不會做的事：

- **回填**：重新建立鏈已經處理過的指定日期的統計。
- **試執行**：在清除工作刪除之前，先計算它會刪除多少。
- **立即套用變更**：將剛儲存的較短保留期限立即清除，而不是等到下一次每日執行。
- **除錯**失敗的執行，同時查看其日誌。

請以安裝實例所執行版本的映像檔執行，並將`PUBLIRA_CONTENT_STATS_DB_URL`設為`publira_content_stats`的連線：

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job purge-content-events
```

在[Docker Compose](../2-deployments/3-docker-compose.md)安裝實例上，`docker compose run --rm publiractl job purge-content-events`已經具備該連線。圖片清除、資料下載及其清除、Google Play退款同步、付款對帳和搜尋索引建立，在其使用的認證資訊保存在安裝實例中時（例如儲存貯體的存取金鑰、租戶的付款服務商和商店認證資訊，或搜尋引擎的密碼），還需要`PUBLIRA_SECRET_ENCRYPTION_KEYS`和`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`。

工作會將日誌輸出到標準輸出，並在執行失敗時以`1`結束。逐一處理租戶的工作，會在結束前處理完其他租戶，其日誌會指出每個失敗的租戶。

### 試執行

每個清除工作都有一個讓它只計算而不刪除的變數，例如`purge-content-events`的`PUBLIRA_CONTENT_EVENTS_PURGE_DRY_RUN=true`；每個清除工作的變數名稱請見其參考文件。計算結果會出現在日誌中：

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  -e PUBLIRA_CONTENT_EVENTS_PURGE_DRY_RUN=true \
  publira/publiractl:<tag> job purge-content-events
```

清除工作會在開始時讀取保留期限，因此試執行計算的是以目前儲存的期限會刪除的數量。在儲存了短得多的期限之後，請在正式執行前先試執行一次，看看清除工作會帶走多少內容。`purge-orphan-images`的試執行會回報儲存貯體中沒有任何圖片列指向、且已存在一天以上的物件；在[還原](../2-deployments/9-backup-and-restore.md#worker處理程序會補做的工作)之後，這些物件包括備份之後上傳的圖片。

### 重新建立某一天的統計

鏈絕不會回頭處理已完成的日子，因此日後修正了其背後的資料，該日的統計也不會再次重新建立。若要重新建立某一天的統計，請在這樣的修正之後，或在版本說明要求時，依序執行這四個環節，並以租戶自身的日曆指定日期：

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job project-episode-reads
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  -e PUBLIRA_CONTENT_STATS_DATE=2026-10-01 \
  publira/publiractl:<tag> job aggregate-content-stats
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job aggregate-rankings
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job build-recommend-features
```

一次執行會為所有租戶重新建立該日。由於網站只顯示最新的排行榜，而以昨天結束的每週排行榜涵蓋了最近七天，因此這裡的排行榜和推薦是為每個租戶的昨天重新建立；只有在要重新建立較舊的排行榜時，才以`PUBLIRA_CONTENT_RANKING_DATE`和`PUBLIRA_RECOMMEND_FEATURES_DATE`指定日期。

內容事件保留期限已不再涵蓋該日的租戶，會被排除在這次執行之外，與worker跳過這樣的日子相同：該租戶該日的分析事件已經不存在，因此其統計會維持原狀，而不是根據剩下的資料重新建立。在清除工作已帶走該日之後才延長期限的租戶也是如此：較長的期限無法找回已刪除的事件。這次執行會將每個這樣的租戶記錄為已跳過，並仍為其他所有租戶重新建立該日。

手動執行不會移動worker對每個租戶進度的記錄，因此worker不會因此跳過或重複任何一天。

### 哪些工作可以安全地重複執行

每個工作都可以再次執行，也可以與worker本身的執行同時進行：

| 工作 | 再次執行時 |
| --- | --- |
| `project-episode-reads` | 所有讀完都已記錄後，不會寫入任何東西 |
| `aggregate-content-stats`、`aggregate-rankings`、`build-recommend-features` | 以相同的結果取代它們建立的內容。同一個工作針對同一個租戶和日期的兩次執行會互相等待，第二次會在30秒後失敗，而不是兩者都寫入 |
| 所有`purge-*` | 找不到剩下可刪除的東西 |
| `close-royalty-statements` | 發現所有應結算的月份都已結算。第一次執行只會實際結算下一次排程執行會結算的月份：也就是設為**自動結算**且結算日已到的租戶的月份 |
| `sync-google-play-voided-purchases` | 不會重複收回任何東西 |
| `build-search-index` | 沒有到期的建立作業，或worker已在建立時，什麼都不做 |
| `reconcile-payments` | 沒有等待中的對帳時，什麼都不做。worker正在執行的對帳不會被重複接手 |
| `build-data-exports` | 沒有讀者在等待副本時，什麼都不做。worker正在準備的副本不會被重複接手 |

唯一的例外是時機：在複製儲存貯體的備份期間，請勿執行`purge-orphan-images`或`purge-data-exports`，如[備份與還原](../2-deployments/9-backup-and-restore.md#1-停止worker處理程序)所述。

發布、免費閱讀期間、日期切換和置頂公告這些工作沒有自己的指令。要讓它們動作，請讓worker執行起來。
