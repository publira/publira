安装实例在没有请求的情况下所做的一切都由`publira worker`完成：它发布预约在此刻发布的章节，告知Web应用哪些缓存页面因更改而过时，发送邮件和推送通知，重建统计数据和排行榜，并删除超过保留期限的内容。没有其他任何东西需要按定时器运行，也不需要主机的cron或Kubernetes CronJob。本页说明什么在何时运行、如何判断某个症状背后是哪个任务，以及如何使用`publiractl job`手动运行任务。

每个任务的间隔、调整它的变量以及完整的任务列表，请参阅[`publira worker`参考](https://github.com/publira/publira/blob/main/server/cmd/publira/README.md#publira-worker)和[`publiractl job`参考](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#job)，本页不再重复。

## 症状背后是哪个任务

从您看到的现象出发，查看负责它的任务：

| 您看到的现象 | 任务 | 查看位置 |
| --- | --- | --- |
| 章节过了预定时间仍为**已预约** | 定时发布 | [定时发布](#定时发布) |
| 章节的网站页面在其免费阅读期内仍显示价格，或在免费阅读期结束后仍显示免费 | 免费阅读期 | [免费阅读期](#免费阅读期及其他缓存页面) |
| 网站的每周更新表仍将昨天显示为今天 | 租户的日期切换 | [免费阅读期](#免费阅读期及其他缓存页面) |
| 网站横幅过了**停止展示的时间**仍在显示 | 置顶公告 | [免费阅读期](#免费阅读期及其他缓存页面) |
| 系列过了**发布日期和时间**仍未出现在网站的列表中 | 定时系列 | [免费阅读期](#免费阅读期及其他缓存页面) |
| 活动横幅在展示期开始后仍未出现在网站上，或在结束后仍在显示 | 活动横幅 | [免费阅读期](#免费阅读期及其他缓存页面) |
| 活动价格开始后，章节的网站页面仍显示原价，或在活动结束后仍显示活动价格 | 活动价格 | [免费阅读期](#免费阅读期及其他缓存页面) |
| 读者的代币记录中没有显示未使用就过期的代币 | 代币过期 | [其他定时任务](#其他定时任务) |
| 系列的发布后免费规则使章节免费的那天过后，章节仍有价格 | 发布后免费 | [其他定时任务](#其他定时任务) |
| 预约的公告过了时间仍未发出 | 定时公告 | [其他定时任务](#其他定时任务) |
| 页面一直显示更改之前的内容 | 发件箱中的缓存重新验证 | [发件箱](#发件箱邮件推送和缓存重新验证) |
| 邮件或推送通知始终未送达 | 发件箱 | [发件箱](#发件箱邮件推送和缓存重新验证) |
| 排行榜、系列评分或推荐不再变化 | 统计与排行榜任务链 | [统计数据与排行榜](#统计数据与排行榜) |
| 在租户的结算日没有结算月份 | 版税结算 | [其他定时任务](#其他定时任务) |
| 在Google Play上购买的章节退款后仍可阅读 | Google Play退款同步 | [其他定时任务](#其他定时任务) |
| 搜索没有切换到新保存的引擎 | 搜索索引构建 | [搜索](./7-search.md#构建失败时) |
| 租户管理员发起的支付对账始终未完成 | 支付对账 | [其他定时任务](#其他定时任务) |
| 读者的数据下载一直处于等待状态 | 数据下载 | [其他定时任务](#其他定时任务) |
| 从平台控制台或用`publiractl tenant delete`删除的租户仍显示为**正在删除**或`deleting` | 租户删除 | [其他定时任务](#其他定时任务) |
| 旧记录没有被删除 | 清除任务 | [其他定时任务](#其他定时任务) |

这些任务都首先需要`publira worker`正在运行并已就绪：worker进程停止的安装实例仍能提供所有页面，但不发布、不发送、也不重建任何东西。worker进程上的`GET /readyz`会为它登录的每个数据库登录名列出一项检查，因此停止响应的登录名会在那里显示出来。在按队列拆分worker进程的安装实例上，每个任务还需要一个处理其队列的正在运行的worker进程，详见[只处理部分任务的worker进程](#只处理部分任务的worker进程)。

### 任务失败记录在哪里

worker进程会将每次失败记录到日志中，日志行会注明任务名称。每次定时任务的运行还会在数据库的`river_job`表中留下一行，worker进程在该表中排队自己的工作，因此可以从该表看出任务是否运行过以及何时运行。

这一行对失败的说明取决于任务。发布、免费阅读期、日期切换、置顶公告、定时系列、活动横幅、活动价格、代币过期、发布后免费和定时公告这些任务，即使运行中有部分失败，也会完成这次运行：每个任务都会记录无法完成的部分，并留到一分钟后的下一次运行，因此它们的行显示为已完成，失败只出现在日志中。其他所有任务都会在其行中记录失败的运行，在`errors`列中保留每次尝试的错误，并注明中断时所处的租户和日期。请以数据库的[管理登录名](../2-deployments/2-installing.md#准备服务)连接，使用`psql`查询：

```sql
SELECT kind, state, attempt, finalized_at, errors
FROM river_job
WHERE state IN ('retryable', 'discarded')
ORDER BY id DESC
LIMIT 20;
```

`retryable`表示等待再次尝试的运行，`discarded`表示已用完尝试次数的运行。已完成或已取消的行会在一天后删除，已丢弃的行会在一周后删除，因此请在出现症状后尽快查看。发件箱有自己的记录，详见[下文](#查看被放弃的内容)。

## 定时发布

工作人员预约的章节会在时间到达后由worker进程发布，同时向该系列的关注者发送通知，并丢弃将其列为预约状态的缓存页面。worker进程每分钟查找一次到期的章节，因此章节会在预定时间后大约一分钟内上线。

发布失败时，会在同一次运行中重试几次。所有尝试都失败时，章节保持**已预约**，worker进程会写入一条标题为“有章节发布失败”的通知，发给租户控制台中的租户管理员，以及平台控制台**通知**下的每位运营人员。每个章节的这种通知只写入一次。worker进程在之后的每次运行中都会重试该章节，因此原因一旦解决——数据库出现故障、迁移尚未运行——章节就会自行发布。工作人员不必等待：在租户控制台中该章节页面的**发布设置**下输入当前时间，就会在该请求中发布章节，无需worker进程。但其关注者仍由worker进程通过[发件箱](#发件箱邮件推送和缓存重新验证)通知。

## 免费阅读期及其他缓存页面

有六个任务负责让Web应用的缓存页面在某个时间点过去后保持正确：

- **免费阅读期**。处于**免费阅读期**条目内的章节，从期间开始的那一刻起就显示为免费，期间结束后又恢复收费，这一过程不涉及任何任务：每次读取都会将期间与当前时间比较。该任务修复的是网站在边界之前缓存的页面，它会在每个期间的两端将这些页面标记为过时。
- **租户的日期切换**。在每个租户自己的午夜（按租户的时区），它将网站的每周更新表标记为过时，这是唯一一个内容取决于租户日历日期的页面。
- **置顶公告**。公告的**停止展示的时间**过后，它将公告从横幅中撤下，并将横幅标记为过时。
- **定时系列**。以将来的**发布日期和时间**保存的系列从该时间起公开，这一过程不涉及任何任务：每次读取都会将该时间与当前时间比较。该任务修复的是网站在系列仍处于隐藏状态时缓存的系列列表、作者页面和该系列自身的页面，它会在时间过后将这些页面标记为过时。在同一次运行中，它会将系列隐藏期间发布的章节的发布日期设为该时间，并将这些章节的通知交给[发件箱](#发件箱邮件推送和缓存重新验证)。
- **活动横幅**。已发布的活动横幅从其展示期开始显示到结束，这一过程不涉及任何任务：每次读取都会将展示期与当前时间比较。该任务修复的是网站在边界之前缓存的横幅，它会在每个已发布横幅展示期的两端将其标记为过时。
- **活动价格**。适用活动价格的章节从活动开始到结束都以该价格显示和收费，这一过程不涉及任何任务：每次读取和每次结账都会将活动与当前时间比较。该任务修复的是网站在边界之前缓存的章节页面和系列页面，它会在每个活动的两端将这些页面标记为过时。

每个任务每分钟运行一次。它们都不会自己丢弃缓存：每个任务都将丢弃操作记录为发件箱中的一个条目，再由worker进程发送给Web应用，因此，如果worker进程设置了`PUBLIRA_REVALIDATE_TOKEN`，页面却仍然过时，那就是发件箱的问题，详见[下文](#发件箱邮件推送和缓存重新验证)。

没有设置`PUBLIRA_REVALIDATE_TOKEN`就启动的worker进程会关闭缓存重新验证。此时这些任务完全不记录丢弃操作，但仍会将每个边界和每个系列的时间视为已过，并撤下每个横幅，因此发件箱中没有可以重试的内容，之后带上令牌重启worker进程也无法找回这些丢弃操作。本应被丢弃的页面会一直保留其缓存内容，直到对同一内容的下一次更改将其丢弃，或其缓存过期。请在第一个需要准时生效的边界之前，在`publira server`和`publira worker`上设置该令牌，详见[安装](../2-deployments/2-installing.md#生成密钥)。

这些任务没有`publiractl job`命令，也不需要：每个任务在每次运行时（包括worker进程启动后的第一次运行）都会处理所有已经过去的时间点。

## 统计数据与排行榜

统计数据、排行榜、系列评分和推荐在每天结束后（按租户自己的时区）根据阅读活动生成。由四个任务依次完成，构成一条任务链：

1. **阅读投影**（`project-episode-reads`）将每次读完记录为一个分析事件。
2. **每日统计**（`aggregate-content-stats`）为每个已结束的日期重建每个系列和章节的浏览、读完、购买、评分、收藏和评论数，以及读者在每个章节中读到了多远。网站显示的系列评分就是据此计算的。它还会记录当天有哪些已登录读者在哪些系列中浏览、读完或购买了章节，控制台正是据此跟踪某一周注册的读者。升级到引入这些记录的版本时，会为分析事件仍被保留的每一天生成这些记录；当时已被清除的日期没有这些记录，之后也无法补上。
3. **排行榜**（`aggregate-rankings`）重建网站**排行榜**页面显示的每日和每周排行榜。
4. **推荐**（`build-recommend-features`）重建每位读者的推荐所依据的快照。

任务链每小时启动一次，每个环节结束时会启动下一个环节。由于每个租户的午夜落在不同的小时，租户的一天会在结束后大约一小时内重建，再加上任务链运行所需的时间。因此，租户午夜过后几个小时排行榜仍未变化是正常的；一整天都没有变化则不正常。

worker进程会按租户记住每个环节最后完成的日期，并从其下一天开始。某一天失败时，该租户会停在那里，其他租户则继续进行：错误记录在失败环节的`river_job`行中，该次运行最多尝试三次，下一个整点的运行会从失败的那一天重新开始。原因解决后，该租户会自行补上，按顺序处理每个错过的日期。

## 其他定时任务

| 任务 | 频率 | 作用 |
| --- | --- | --- |
| 发布后免费 | 每分钟 | 为系列的发布后免费规则所覆盖的每个已发布的收费章节添加一个免费阅读期：自章节发布起已过了设定的天数，并且它不属于规则保持收费的最新章节。该期间从那一天开始，如果当时有手动设置且仍未结束的期间，则从该期间结束时开始；如果该期间被删除，则移回那一天。它一直持续到规则不再覆盖该章节为止：以关闭状态保存规则，或以排除该章节的数值保存规则，会立即将其移除；章节因其他原因脱离规则时，例如成为最新章节之一或被下架，下一次运行会将其移除。与期间开始或结束时一样，章节的页面会在同一次运行中被标记为过时。与让缓存页面准时更新的任务一样，它没有`publiractl job`命令 |
| 定时公告 | 每分钟 | 在时间过后发出工作人员预约的每条公告，详见[公告](../4-console/3-setup/4-announcements.md#预约公告)：将其标记为已发出（这样读者才能看到），将其通知交给[发件箱](#发件箱邮件推送和缓存重新验证)，并将读者的公告页面标记为过时，以横幅显示的公告还会将横幅标记为过时。与让缓存页面准时更新的任务一样，它没有`publiractl job`命令 |
| 代币过期 | 每分钟 | 每当一次代币发放在过期时仍有未使用的代币，就在读者的代币记录中写入一条记录，说明这些代币的去向。代币在过期的那一刻就不再计入余额，这一过程不涉及任何任务，并且永远不会恢复。与让缓存页面准时更新的任务一样，它没有`publiractl job`命令 |
| 版税结算（`close-royalty-statements`） | 每小时 | 在租户的结算日到来后，为设置为**自动结算**的租户结算其应结算的每个月份。已经结算的月份，无论是手动结算还是之前的运行结算的，都保持原样 |
| Google Play退款同步（`sync-google-play-voided-purchases`） | 每小时 | 为每个开启了Google Play商店的租户读取Google Play在过去30天内退款的购买，并将其收回，详见[销售章节](../4-console/4-selling-episodes.md#退款) |
| 搜索索引构建（`build-search-index`） | 每30秒 | 在新保存的搜索引擎上构建索引，并将搜索切换过去，详见[搜索](./7-search.md#迁移到另一个引擎) |
| 支付对账（`reconcile-payments`） | 每10秒 | 执行租户管理员发起的每次对账，从租户的支付服务商或商店读取该期间的付款，详见[销售章节](../4-console/4-selling-episodes.md#与支付服务商对账)。被数据来源拒绝的运行会记录为失败，由租户管理员重新发起，而不会重试。已停止的worker进程执行到一半的运行会在两小时后重新处理 |
| 数据下载（`build-data-exports`） | 每10秒 | 准备读者申请的每份数据副本，将其保存到存储桶中，并告知读者已准备就绪，详见[读者账户](../4-console/2-readers/1-accounts.md#读者下载的个人数据)。在未设置对象存储时提出的申请会记录为失败，由读者重新申请，而不会重试。已停止的worker进程处理到一半的申请会在15分钟后重新处理 |
| 租户删除（`erase-tenants`） | 每分钟 | 按[删除租户](./2-tenants.md#删除租户)所述，删除运营人员从平台控制台或用`publiractl tenant delete`删除的每个租户的数据：其在每张表中的行、存储桶中的对象、搜索引擎索引中的文档，以及留在Valkey中的转换后图片和速率限制计数器，最后删除租户本身，此后其主机不再属于任何租户。删除会记录在平台控制台的**审计日志**中，每位运营人员都会在**通知**下收到一条标题为“租户已删除”的通知。因错误而中断的运行会让租户保持`deleting`，像已暂停的租户一样被拒绝，每位运营人员会收到一条标题为“租户删除失败”的通知，每个租户一次；一分钟后的下一次运行会从剩余部分继续删除，错误内容在worker进程的日志中。未获得`PUBLIRA_REDIS_URL`的worker进程不会删除Valkey中的转换后图片和计数器，而是让它们自行过期：图片在缓存有效期结束时过期，计数器在其时间窗口结束时过期 |
| 清除任务（`purge-*`） | 每小时或每24小时 | 删除超过保留期限的已撤回评论、分析事件和排行榜快照，详见[平台默认值与策略](./9-platform-policies.md#保留期限)；删除两步验证登录已用完的验证挑战；删除读者的数据下载（准备就绪七天后），以及已删除账户的数据下载；删除任何租户都不再使用、且已存在一天以上的图片 |

## 只处理部分任务的worker进程

以`--queue`启动的worker进程只运行其指定队列中的任务，其他任务留给指定了那些队列的worker进程，详见[按队列拆分worker进程](../2-deployments/7-scaling-out.md#按队列拆分worker进程)。本页的任务分布在七个队列中，`river_job`中的名称与之相同，只有`outbox`在其中名为`default`：

| 队列 | 任务 |
| --- | --- |
| `outbox` | [发件箱](#发件箱邮件推送和缓存重新验证)：邮件、推送通知、缓存重新验证，以及搜索引擎的索引更新 |
| `ticker` | 定时发布、免费阅读期、租户的日期切换、置顶公告、定时系列、活动横幅、活动价格、代币过期、发布后免费和定时公告 |
| `maintenance` | 统计与排行榜任务链、版税结算、Google Play退款同步和清除任务 |
| `search_index` | 搜索索引构建 |
| `payment_reconciliation` | 支付对账 |
| `data_export` | 数据下载 |
| `tenant_erasure` | 租户删除 |

每个队列都需要至少一个处理它的正在运行的worker进程。无论负责调度任务的worker进程自己处理哪些队列，它都会调度所有任务，因此队列没有任何正在运行的worker进程处理的任务不会丢失，但也没有任何东西运行它：它会在`river_job`中等待，直到处理其队列的worker进程启动，然后像[停机后](#停机后)那样运行。每个worker进程在启动时都会记录它留给其他进程的队列，日志为`worker leaves queues to other replicas`，并以`not_hosted`列出这些队列。任务在等待的队列会显示在`river_job`中：

```sql
SELECT queue, kind, count(*), min(scheduled_at)
FROM river_job
WHERE state = 'available' AND scheduled_at < now() - interval '5 minutes'
GROUP BY queue, kind;
```

这里的每一行都是一个已到期五分钟、却没有任何worker进程领取的任务：请启动一个处理其`queue`的worker进程，或将该队列添加到某个正在运行的worker进程的`--queue`中。

## 停机后

已停止的worker进程，或在数据库无法正常工作的情况下运行的worker进程，在此期间什么也不做，工作会在数据库中等待，而不会丢失。再次启动时：

| 任务 | 启动时 |
| --- | --- |
| 发件箱 | 发送所有正在等待的条目。已停止的worker进程处理到一半的条目会在15分钟后重新处理 |
| 定时发布 | 发布所有时间已过的章节，并通知其关注者 |
| 免费阅读期、租户的日期切换、置顶公告、定时系列 | 将边界在此期间已过的所有页面标记为过时，并撤下所有时间已到的横幅 |
| 发布后免费 | 从相应日期起开放在此期间到达该日期的所有章节 |
| 定时公告 | 发出所有时间已过的公告，并通知其读者 |
| 统计与排行榜任务链 | 按顺序重建每个租户错过的每一天，但分析事件已超过保留期限，或已按之前保存的较短期限被清除的日期除外：这些日期会被记录为缺失并跳过，无法重建 |
| 版税结算 | 结算所有已到应结算时间的月份 |
| 搜索索引构建 | 构建待处理的索引 |
| 支付对账 | 执行在此期间发起的所有对账 |
| 数据下载 | 准备在此期间申请的所有副本 |
| 租户删除 | 删除在此期间被删除的所有租户的数据，并完成已停止的worker进程未做完的删除 |
| 清除任务 | 只有在当前小时或当天内尚未完成过时才运行，按时钟计算，而不是从worker进程启动时算起；之后第一次运行会删除在此期间过期的所有内容 |
| Google Play退款同步 | 与清除任务一样，只有在当前小时内尚未完成过时才运行。停机超过30天的worker进程会错过Google Play不再列出的退款 |

正是这种等待间隔，使得重启或部署不会变成对每张表和整个存储桶的一次全面扫描。

## 发件箱：邮件、推送和缓存重新验证

请求留待之后处理的每个副作用——邮件、推送通知、缓存页面的丢弃、搜索引擎的索引更新——都会与引起它的更改在同一事务中写入发件箱。因此，更改绝不会在没有其副作用的情况下被保存，worker进程会在几秒内发送该条目。

失败的条目会被重试，每次失败后的等待时间加倍：先是一秒，然后两秒，再是四秒。第十次尝试失败后，即第一次尝试约九分钟后，该条目会被永久放弃：它变为**dead**，不会再被发送。永远不可能成功的条目，例如发往已删除账户的邮件，会被立即放弃。worker进程不认识的类型的条目并不算失败：在升级期间，这是只有新版本才会写入的条目，因此worker进程会将其留给新版本的worker进程，每分钟检查一次，只有在写入一天后才会放弃。失败的含义取决于条目：

- **邮件**在SMTP服务器（或启用后的`email-renderer`）拒绝或无法连接时失败，详见[邮件](./6-email.md#安装实例发送的邮件)。
- **发往手机的推送通知**在租户未保存Firebase凭据时会被跳过而不是失败，因此保存凭据后也不会重试。浏览器通知只有在开启Web Push后才会发送，详见[Web Push](./8-web-push.md)。
- **缓存重新验证**在Web应用停止运行时失败。没有`PUBLIRA_REVALIDATE_TOKEN`的worker进程，会在每次尝试时让`publira server`或`publiractl`记录的每个丢弃操作失败；它自身任务的丢弃操作则完全不会被记录，详见[免费阅读期](#免费阅读期及其他缓存页面)。
- **Webhook发送**（`event_type`为`webhook_delivery`）把一个事件发送到租户管理员保存的端点，详见[API密钥与Webhook](../4-console/10-api-keys-and-webhooks.md#重试与重新发送)。它在该端点停止运行或以`2xx`以外的任何状态响应时失败；当端点以除`408`和`429`以外的其他`4xx`响应，或其主机解析到私有地址、环回地址、链路本地地址或共享地址时，会被立即放弃。端点是租户运行的服务器，因此发送失败需要由租户而不是安装实例来修复。如果端点的签名密钥无法用`PUBLIRA_SECRET_ENCRYPTION_KEYS`中的任何密钥解密，该发送会等待，且不消耗尝试次数，直到该密钥恢复或签名密钥被重新生成。

`publira worker`上的`PUBLIRA_OUTBOX_MAX_ATTEMPTS`设置尝试次数。等待时间会不断加倍，两次尝试之间最长可达一小时，因此只需增加几次尝试，条目就能撑过长得多的故障。无论`PUBLIRA_OUTBOX_MAX_ATTEMPTS`如何设置，Webhook发送都有自己的20次尝试额度，约八小时，因为它发往的服务器停止运行的时间可能比安装实例自身的服务更长。

worker进程通过HTTPS把Webhook发送到每个端点指定的任意主机和端口，因此限制worker进程出站流量的安装实例必须允许这些流量，Webhook才能送达。

### 查看被放弃的内容

worker进程会将其放弃的每个条目以`outbox event dead`记录在日志中，开启指标后还会计入`publira.outbox.events.dead`指标，详见[监控](./11-monitoring.md#发件箱)；请针对其中任一项设置告警。条目本身连同最后一次错误会保留在`outbox_events`表中：

```sql
SELECT event_type, tenant_id, attempts, last_error, updated_at
FROM outbox_events
WHERE status = 'dead'
ORDER BY updated_at DESC
LIMIT 20;
```

已放弃的条目无法重新发送，Webhook发送除外。其影响取决于它的`event_type`：

- **邮件**永远不会送达。读者需要重新申请密码重置或确认邮件，管理员邀请则需重新发送，详见[租户的工作人员](./3-tenant-staff.md)。
- **推送通知**永远不会送达，通知会保留在读者在网站和应用中的通知列表中。
- **缓存重新验证**会让其指定的页面继续显示之前的内容，直到对同一内容的下一次更改再次将其丢弃，或其缓存过期。
- **Webhook发送**会在租户控制台的**API密钥与Webhook**中列为**已放弃**，租户管理员可在端点修复后在那里重新发送它。

## 手动运行任务

`publiractl job <job>`运行一次维护任务后退出。它运行的是与worker进程的定时运行相同的代码，而不是其副本，因此行为与定时运行相同。它用于定时计划不会做的事情：

- **补算**：重建任务链已经处理过的某个指定日期的统计数据。
- **试运行**：在清除任务删除之前，统计它会删除多少内容。
- **立即应用更改**：刚保存的较短保留期限，现在就执行清除，而不是等到下一次每日运行。
- **调试**失败的运行，同时查看其日志。

请使用安装实例所运行版本的镜像，并将`PUBLIRA_CONTENT_STATS_DB_URL`设置为`publira_content_stats`的连接：

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job purge-content-events
```

在[Docker Compose](../2-deployments/3-docker-compose.md)安装实例上，`docker compose run --rm publiractl job purge-content-events`已经带有该连接。图片清除、数据下载及其清除、Google Play退款同步、支付对账、搜索索引构建和租户删除，在其使用的凭据保存在安装实例中时（例如存储桶的访问密钥、租户的支付服务商和商店凭据，或搜索引擎的密码），还需要`PUBLIRA_SECRET_ENCRYPTION_KEYS`和`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`。租户删除还需要与`publira server`相同的`PUBLIRA_REDIS_URL`，以便删除Valkey中的转换后图片和计数器。

任务将日志输出到标准输出，运行失败时以`1`退出。逐个处理租户的任务会先处理完其他租户再退出，其日志会注明每个失败的租户。

### 试运行

每个清除任务都有一个让它只计数而不删除的变量，例如`purge-content-events`的`PUBLIRA_CONTENT_EVENTS_PURGE_DRY_RUN=true`；每个清除任务对应的名称请参阅其参考。计数结果在日志中：

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  -e PUBLIRA_CONTENT_EVENTS_PURGE_DRY_RUN=true \
  publira/publiractl:<tag> job purge-content-events
```

清除任务在开始时读取保留期限，因此试运行统计的是按当前保存的期限会删除的内容。保存了一个短得多的期限后，请在正式运行之前先试运行一次，看看清除会一并删除多少内容。`purge-orphan-images`的试运行会报告存储桶中没有任何图片行引用、且已存在至少一天的对象；在[恢复](../2-deployments/9-backup-and-restore.md#worker进程会补做的工作)之后，这些对象包括备份之后上传的图片。

### 重建某一天的统计数据

任务链绝不会回头处理已经完成的日期，因此当其背后的数据之后被更正时，该日期的统计数据不会再次重建。要重建某一天，在进行了这样的更正之后，或者在发布说明要求时，请按顺序运行这四个环节，并以租户自己的日历指定日期：

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job project-episode-reads
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  -e PUBLIRA_CONTENT_STATS_DATE=2026-10-01 \
  publira/publiractl:<tag> job aggregate-content-stats
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job aggregate-rankings
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job build-recommend-features
```

一次运行会为所有租户重建该日期。这里的排行榜和推荐会为每个租户的昨天重建，因为网站只显示最新的排行榜，而截至昨天的每周排行榜涵盖最近七天；只有在要重建更早的排行榜时，才需要通过`PUBLIRA_CONTENT_RANKING_DATE`和`PUBLIRA_RECOMMEND_FEATURES_DATE`为它们指定日期。

内容事件保留期限已不再覆盖该日期的租户会被排除在这次运行之外，与worker进程跳过这种日期的方式相同：该租户当天的分析事件已经不存在，因此其统计数据会保持原样，而不会根据剩余的数据重建。在清除任务删除该日期之后才延长期限的租户也是如此：更长的期限不会找回已删除的事件。运行时会将每个这样的租户记录为已跳过，并仍为其他所有租户重建该日期。

手动运行不会改变worker进程对每个租户处理进度的记录，因此worker进程既不会因此跳过某一天，也不会重复处理某一天。

### 哪些任务可以安全地重复运行

每个任务都可以再次运行，也可以与worker进程自身的运行同时进行：

| 任务 | 再次运行时 |
| --- | --- |
| `project-episode-reads` | 所有读完都已记录后，不再写入任何内容 |
| `aggregate-content-stats`、`aggregate-rankings`、`build-recommend-features` | 以相同的结果替换其生成的内容。针对同一租户和日期运行其中一个任务两次时，两者会互相等待，第二次运行会在30秒后失败，而不是两者都写入 |
| 每个`purge-*` | 找不到剩余可删除的内容 |
| `close-royalty-statements` | 发现所有应结算的月份都已结算。首次运行只会真正结算下一次定时运行会结算的月份：即设置为**自动结算**且结算日已到的租户的月份 |
| `sync-google-play-voided-purchases` | 不会再次收回任何内容 |
| `build-search-index` | 没有需要进行的构建，或worker进程已在构建时，不做任何事 |
| `reconcile-payments` | 没有等待中的对账时，不做任何事。worker进程正在执行的对账不会被再次处理 |
| `build-data-exports` | 没有读者在等待副本时，不做任何事。worker进程正在准备的副本不会被再次处理 |
| `erase-tenants` | 没有等待删除的租户，或worker进程正在删除时，不做任何事 |

唯一的例外是时机：在复制存储桶的备份时，请不要运行`purge-orphan-images`或`purge-data-exports`，详见[备份与恢复](../2-deployments/9-backup-and-restore.md#1-停止worker进程)。

发布、免费阅读期、日期切换和置顶公告任务没有自己的命令。要让它们执行，请让worker进程运行起来。
