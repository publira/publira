安装实例保存着每个租户的支付服务商和邮件服务器的凭据、每位读者的个人数据，以及用于加密它们的密钥。本页面向负责保护这些内容的运营人员：说明安装实例依靠什么将它们相互隔离，以及每个密钥可以放在哪里。如何替换每个密钥、两步验证和审计日志能为您提供什么，以及安装实例前面的Web应用防火墙和速率限制应该做什么，请参阅[本节内容](#本节内容)下的各页。

## 数据如何相互隔离

### 数据库角色

没有任何进程以`publiractl db`命令所用的[管理登录名](../../2-deployments/2-installing.md#准备服务)连接PostgreSQL。安装实例的每个部分都以`publiractl db roles`创建的六个角色之一连接，每个角色只能访问该部分所需的内容，详见[数据库角色](../../2-deployments/2-installing.md#数据库角色)。为读者和租户工作人员提供服务的角色受行级安全约束，只能访问请求所指定的租户，因此这些路径中的缺陷无法读取其他租户的行；运营人员的密码哈希和平台的邮件凭据，除`publira_platform`和发送平台邮件的worker进程角色之外，任何角色都无法访问。租户控制台的角色可以读取平台邮件的发件地址，但读取不到平台邮件设置中的其他任何内容。

只有在每个进程只持有自己角色的连接URL、不持有其他任何连接URL时，这一点才成立。请只将管理登录名的密码交给`publiractl db`命令，绝不要将进程的连接URL设置为该登录名或它不使用的角色。

### 控制台API

`publira server`在公开API旁的`/rpc`下提供租户控制台和平台控制台的API，使用的是边缘转发到的同一个端口。只有在边缘转发它们的地方才能访问这些API，而按照[路由](../../2-deployments/4-edge/index.md#路由)配置的边缘不会将它们转发到任何地方：`web-admin`和`web-platform`通过私有网络调用它们，边缘则在每个主机上都以`404`响应这些请求。在此之后，这些API的每个请求在执行之前都会被拒绝，除非它携带运营人员的会话或Web服务令牌；少数在会话存在之前执行的请求——登录、重置密码和确认邮箱地址——会按客户端限制，或由服务器自身把关；创建平台控制台的第一位运营人员需要Web服务令牌，而只有平台控制台的服务器会发送它。因此，在能够访问`publira server`的人与每个租户的目录和平台的读者列表之间，挡在中间的就是Web服务令牌：请只将它交给下表列出的进程。

正如[概览](../../2-deployments/1-overview.md#安装实例运行什么)所述，以`publira server --role storefront`运行租户域名所访问的进程，在边缘规则之外仍然值得这样做。两者是不同的防护层：边缘让控制台的API不暴露在互联网上，而`--role storefront`让控制台的数据库登录名和Web服务令牌不进入读者访问的进程，因此无论是该进程中的缺陷，还是终究转发了控制台路径的边缘，都无法接触到它们。

### 每个密钥可以放在哪里

只将每个密钥交给读取它的进程。不需要某个值的进程，只会多一个可能泄露它的地方。

| 密钥 | 设置在 | 绝不设置在 | 持有者能做什么 |
| --- | --- | --- | --- |
| 密钥加密密钥 | `publira server`、`publira worker`、`publiractl` | Web应用 | 在获得数据库副本的情况下，打开安装实例保存的所有凭据 |
| 访问令牌签名密钥`PUBLIRA_AUTH_JWT_SECRET` | `publira server` | 其他所有进程 | 为任何读者、工作人员或运营人员签发会话 |
| 每个Web应用的会话密钥`PUBLIRA_AUTH_SECRET` | 该Web应用 | `publira server`、`publira worker` | 读取和伪造该应用的会话Cookie，其中携带用户的访问令牌 |
| 缓存重新验证令牌 | `publira server`、`publira worker`以及每个Web应用 | `publiractl` | 随意丢弃任何缓存页面，次数不限 |
| Web服务令牌 | `publira server`、`web-admin`、`web-platform` | `web-storefront`、`publira worker` | 读取任何租户的目录（包括未发布的系列），以及平台的租户、运营人员和读者 |
| 管理登录名的密码 | `publiractl db`命令 | 所有长期运行的进程 | 数据库中的一切 |
| 每个角色的密码 | 以该角色连接的进程 | 其他进程 | 该角色能访问的内容 |

各Web应用可以共用一个会话密钥，但请像Compose文件那样为每个应用分别设置：这样替换其中一个时，只会让该应用的用户退出登录。

### 将密钥交给publiractl

`publiractl`绝不以参数接收密钥。在平台能够以文件形式挂载密钥的地方，例如Kubernetes和Docker的`/run/secrets/`下，请使用该密钥的`--<name>-file`选项以文件形式提供。文件可以设置为只有运行`publiractl`的那个用户可读，并存放在tmpfs上。而环境变量中的值会被持有它的进程所启动的每个进程继承，并且可以从`/proc/<pid>/environ`、`docker inspect`或编排系统对任务的描述，以及记录环境的崩溃报告或调试转储中读取。

只有在平台只能以环境变量设置密钥时，例如[Amazon ECS](../../2-deployments/6-ecs-fargate/index.md)，才使用该密钥的`--<name>-env`选项。

### 每个安装实例一套密钥

为每个安装实例重新生成一整套密钥：生产环境、预发布环境以及每位开发人员的机器。共用访问令牌签名密钥的两个安装实例，会接受对方为两边都存在的账户ID签发的会话，而从生产环境备份恢复的预发布数据库中，所有账户都是这种情况。

从生产环境恢复的副本只有使用生产环境的加密密钥才能读取其保存的凭据，而有了这些密钥，它就持有生产环境的SMTP账户、支付服务商密钥以及其租户保存的所有其他凭据。请只在允许存放生产环境密钥的地方运行这样的副本，并为它设置独立的访问令牌签名密钥、会话密钥、令牌和角色密码。

## 发往自有网络的Webhook

[Webhook端点](../../4-console/10-api-keys-and-webhooks.md#webhook端点)的目标URL由租户选择，而`publira worker`在您的网络内部发送这些投递。因此，发往解析到私有地址、环回地址、链路本地地址或共享地址的主机的投递会被放弃，以免租户访问到您从未公开的内容。

如果出版方的接收端运行在您自己的网络中，请在worker上将`PUBLIRA_WEBHOOK_ALLOWED_ADDRESSES`设置为接收端所在的地址或CIDR范围，以逗号或空格分隔，例如`10.20.0.15, 10.30.0.0/24`。此后，安装实例上的任何租户都可以向这些地址投递，因此请只列出接收端，而不是整个网络，并且绝不要包含Publira自身进程、数据库或云服务提供商元数据服务的地址。覆盖所有地址的范围（例如`0.0.0.0/0`）以及既不是地址也不是范围的值都会被拒绝，这两种情况都会使worker在启动时停止。

此设置只改变投递可以到达的位置。端点的URL仍须为`https`，worker仍会验证接收端的证书。如果接收端的证书由您自己的证书颁发机构签发，则需要让worker信任该机构：将一个PEM证书文件挂载到worker的容器中，并通过`SSL_CERT_FILE`指定它。该文件会取代系统的根证书，因此如果有租户向公开的接收端投递，请同时包含公共根证书。

## 报告漏洞

Publira自身的漏洞请按照[安全策略](https://github.com/publira/publira/security/policy)的说明私下报告，绝不要在公开的Issue中报告。
