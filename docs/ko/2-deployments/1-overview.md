Publira 설치 환경은 상시 실행되는 네 개의 프로세스, 이들이 의존하는 몇 가지 서비스, 그리고 직접 실행하는 명령줄 도구 하나로 이루어집니다. 이 페이지에서는 테넌트 하나를 서비스하는 가장 작은 설치 환경을 설명합니다. 테넌트의 공개 사이트와 콘솔을 제공하며, 플랫폼 콘솔이 아니라 `publiractl`로 관리하는 구성입니다.

## 설치 환경이 실행하는 것

| 프로세스 | 제공하는 것 | 요청을 보내는 쪽 |
| --- | --- | --- |
| `web-storefront` | 모든 테넌트의 공개 사이트 | 엣지. 각 테넌트의 도메인으로 |
| `web-admin` | 테넌트 콘솔 | 엣지. 각 테넌트의 콘솔 호스트로. 테넌트에 다른 호스트를 지정하지 않았다면 `admin.<domain>` |
| `publira server` | `/rpc` 아래의 API와 이미지 전송을 하나의 포트로 | 엣지는 `/rpc` 아래의 공개 API와 `/images`로, `web-storefront`와 `web-admin`은 `/rpc`로 |
| `publira worker` | 발신 메일과 푸시 알림, 캐시 재검증, 모든 예약 작업 | 없음. 헬스 체크에만 응답합니다 |

모든 프로세스가 `GET /livez`와 `GET /readyz`에 응답하므로 오케스트레이터가 이를 프로브로 사용할 수 있습니다. 웹 앱은 하나의 이미지로, `publira server`와 `publira worker`는 또 다른 이미지로 빌드됩니다. [이미지 빌드 안내](https://github.com/publira/publira/blob/main/infra/docker/README.md)에 그 목록이 있습니다.

한 대의 호스트에서 서버와 워커를 각각 한 개보다 많이 실행할 일이 없는 설치 환경에서는 둘을 하나의 프로세스로 실행할 수 있습니다. `publira server --with-worker`는 두 프로세스가 하는 일을 모두 같은 두 포트에서 수행하며, 두 프로세스의 환경 변수를 모두 읽습니다. 대신 두 가지를 포기하게 됩니다. 첫째, 서버와 워커를 따로 확장할 수 없습니다. 둘째, 인터넷에 노출된 프로세스가 워커의 데이터베이스 로그인 세 개도 갖게 되는데, 그중에는 작업 큐의 테이블을 소유하고 자기 테이블을 생성할 수 있는 로그인도 있습니다. [Docker Compose](./3-docker-compose.md) 설치 환경은 둘을 하나로 실행합니다. 이 중 어느 하나라도 중요하다면, 즉 둘을 따로 확장하고 싶거나 워커의 로그인을 인터넷에 노출된 프로세스에서 떼어 두고 싶다면 둘을 분리해서 실행하세요.

`publira server`는 하나의 포트에서 대기하므로, Cloud Run처럼 서비스마다 포트를 하나만 노출하는 플랫폼에서도 그대로 하나의 서비스로 실행할 수 있습니다. 또한 로드 밸런서 뒤에 `--role storefront`를 지정한 두 번째 `publira server` 서비스를 둘 수도 있습니다. 이 서비스는 테넌트 사이트의 공개 API와 이미지만 제공합니다. 테넌트의 도메인과, 공개 API만 호출하는 `web-storefront`의 요청은 이 서비스로 보내세요. 그러면 독자에게 응답하는 프로세스는 요청마다 하나의 테넌트로 한정되는 스토어프런트용 로그인으로만 데이터베이스에 로그인하며, 어느 콘솔의 로그인도, 웹 앱이 콘솔을 호출할 때 쓰는 자격 증명도 갖지 않습니다. 첫 번째 서비스는 계속 `web-admin`, `web-platform`, 콘솔 호스트를 담당합니다. 각 역할이 무엇을 제공하고 무엇을 읽는지는 [배포 레퍼런스](https://github.com/publira/publira/blob/main/infra/deploy/README.md#long-lived-processes)에 나와 있습니다.

이미지 전송과 공개 API는 각각 별도의 호스트 이름과 별도의 로드 밸런서를 두어 따로 접근하게 할 수도 있습니다. 테넌트 사이트의 이미지는 테넌트에 지정한 이미지 호스트에서, 공개 API는 웹 앱과 모바일 앱이 가리키는 호스트에서 제공됩니다. 둘 다 `--role storefront` 프로세스이므로 프로세스는 아무것도 바뀌지 않고, 호스트 이름과 그 앞의 로드 밸런서만 바뀝니다. 자세한 내용은 [이미지와 공개 API를 따로 제공하기](./7-scaling-out.md#이미지와-공개-api를-따로-제공하기)에서 설명합니다.

어떤 프로세스도 자체 상태를 갖지 않습니다. 설치 환경이 저장하는 것은 PostgreSQL과 오브젝트 스토리지에, 프로세스들이 실행 중에 공유하는 것은 Valkey에 있으며, 세션은 브라우저가 돌려보내는 쿠키입니다. 따라서 어떤 프로세스든 여러 개를 실행할 수 있고, 엣지는 요청을 분산할 때 스티키 세션이 필요하지 않습니다. 설치 환경이 커질 때 무엇을 더 실행해야 하는지, 그리고 그 전에 무엇을 공유해야 하는지는 [스케일 아웃](./7-scaling-out.md)에서 설명합니다.

## 의존하는 서비스

| 서비스 | 사용하는 쪽 | 보관하는 것 |
| --- | --- | --- |
| 엣지: 로드 밸런서, 리버스 프록시, 또는 그 앞에 놓인 CDN | 브라우저와 모바일 앱 | 각 호스트와 경로를 올바른 프로세스로 보내는 라우팅, 그리고 TLS |
| PostgreSQL | 모든 프로세스 | 설치 환경이 저장하는 모든 것 |
| Valkey 또는 Redis 프로토콜을 지원하는 서버 | `publira server`, `web-storefront`, `web-admin` | 이미지 변환 캐시, 요청 제한 카운터, 웹 앱의 공유 캐시 |
| S3 호환 오브젝트 스토리지 | `publira server`, `publira worker` | 업로드된 모든 이미지 |
| SMTP 서버 | `publira worker` | 없음. 독자 회원가입이나 비밀번호 재설정처럼 설치 환경이 보내는 메일을 전달합니다 |

데이터베이스와 버킷은 직접 만듭니다. 그 안의 모든 것은 Publira가 만듭니다. 엣지는 관리형 로드 밸런서든 직접 운영하는 프록시든 플랫폼이 프로세스 앞에 제공하는 것이면 무엇이든 됩니다. 어떤 것이든 엣지가 해야 할 일은 [엣지](./4-edge/index.md#엣지가-해야-하는-일)에 나와 있습니다. 저장소에 있는 Traefik, nginx, Caddy 샘플 구성은 이를 구현하는 한 가지 방법입니다.

## 직접 실행하는 명령

`publiractl`은 릴리스마다 데이터베이스 마이그레이션과 역할을 적용하고, 새 설치 환경을 설정하며, 이후 플랫폼 설정을 변경합니다. 이를 주기적으로 실행할 필요는 없습니다. 반복되는 작업은 모두 `publira worker`가 스스로 예약합니다.

## 추가할 수 있는 프로세스

| 프로세스 | 추가되는 것 |
| --- | --- |
| `email-renderer` | 모든 메일에 HTML 파트를 추가합니다. 이 프로세스가 없으면 같은 메일이 일반 텍스트로 발송됩니다 |
| `web-platform` | 운영자가 `publiractl` 대신 브라우저에서 테넌트와 플랫폼 설정을 관리하는 플랫폼 콘솔 |
