テナントのサイトへのリンク（シリーズ、エピソード、お知らせ、サイトのメールにある確認用やパスワード再設定用のリンク）は、アプリがインストールされていれば、ブラウザーではなくアプリで開きます。AndroidとiOSがこれを許可するのは、サイトがそのアプリを保証していることを確認できたあとだけです。そのために、サイトに次の2つのファイルを要求します。

- Android用の`https://<tenant.host>/.well-known/assetlinks.json`
- iOS用の`https://<tenant.host>/.well-known/apple-app-site-association`

サイトは、テナント管理画面の**外部連携** › **アプリリンク**に保存された内容から、両方のファイルを作成します。Webサーバーにアップロードするものはありません。

同じ2つのファイルは、アプリがサイトのパスキーを使うことも保証します。読者が登録したパスキーはテナントのホストに属し、AndroidとiOSは、そのホストのファイルがアプリを指定している場合にだけ、アプリにそのホストのパスキーを使わせます。`assetlinks.json`ではリンク用の`delegate_permission/common.handle_all_urls`の隣にある`delegate_permission/common.get_login_creds`のリレーション、`apple-app-site-association`では`applinks`の隣にある`webcredentials`のエントリーです。サイトは指定したすべてのアプリについて両方を書き出すため、パスキーのために追加で入力するものはありません。Androidアプリのパスキーによるログインは、サイトではなくアプリの署名証明書の名義でサーバーに届きます。サーバーがそれを受け付けるのは、ここにフィンガープリントが保存されている証明書からの場合だけなので、登録されていない鍵で署名したビルドはサイトのパスキーを使えません。

同じページは、インストール環境のほかの部分に対してもアプリを指定します。アプリ内課金のApp StoreとGoogle Playの部分はここで指定したアプリで販売し、Sign in with Appleはここで指定したアプリを信頼します。そのため、アプリでそのどちらかを試す前に、このページを入力してください。

## 入力するタイミング

Androidのフィンガープリントは自分で選べるものではありません。Play App Signingでは、インストールされるアプリにGoogleが署名する鍵のフィンガープリントで、Play Consoleでアプリを作成し、最初のApp Bundleをアップロードすると表示されます。iOS側はいつ入力してもかまいません。Android側は、Play Consoleに鍵が表示されてから入力します。

値は常に、ストアが配布するアプリ、つまり[ビルドと署名](./2-building.md)のストア用ビルドのものです。公開済みのアプリと1文字でも違う値を入れると、そのアプリのリンクはブラウザーで開くようになり、不一致はどこにも報告されません。

## アプリを入力する

テナント管理画面で**外部連携** › **アプリリンク**を開きます。

### Android

**リンクをテナントのAndroidアプリで開く**にチェックを入れ、次の項目を入力します。

| フィールド | 値の取得元 |
| --- | --- |
| **アプリケーションID** | マニフェストの`android.applicationId`です。Google Playでは、アプリのストアのアドレスにある`id=`として同じ値が表示されます |
| **SHA-256署名証明書フィンガープリント** | Play Consoleのアプリの**App signing**ページにある**app signing key certificate**のSHA-256フィンガープリントです。アップロード鍵のものではありません。Playが配信するものに署名するのはアップロード鍵ではないためです |

フィンガープリントは、コロンで区切られた32組の16進数の数字（`AA:BB:…`）で、このフィールドには1行に1つずつ最大10個まで入力できます。別の方法で署名したビルドでもリンクを開きたい場合は、2つ目のフィンガープリントを入れます。テスト用にインストールする、アップロード鍵で署名したリリースAPKや、鍵のローテーション中の新しい鍵などです。アップロード鍵のフィンガープリントは、次のコマンドの出力の`SHA256:`の行です。

```bash
keytool -list -v -keystore ~/example-reader/upload.jks -alias upload
```

### iOS

**リンクをテナントのiOSアプリで開く**にチェックを入れ、次の項目を入力します。

| フィールド | 値の取得元 |
| --- | --- |
| **Apple Team ID** | Apple Developerのウェブサイトの**Membership details**にある10文字のTeam IDです。アプリのビルドに使った`PUBLIRA_IOS_DEVELOPMENT_TEAM`と同じです |
| **バンドルID** | マニフェストの`ios.bundleIdentifier`です。App Store Connectでは、**App Information**のBundle IDとして同じ値が表示されます |

**アプリリンクを保存**を選びます。チェックを入れなかったプラットフォームには`404`が返り、そのプラットフォームにアプリがないことを伝えます。アプリを持たないテナントは、どちらにもチェックを入れません。

マニフェストの`tenant.host`に対応するフィールドはここにはありません。すでに決まっているからです。AndroidとiOSはリンクが指すホストに問い合わせ、アプリが主張するのはそのホストだけです。したがって、このホストはテナントのサイトを提供しているホストである必要があります。

## リンクを確認する

まず、サイトが両方のファイルを提供していることを確認します。

```bash
curl -i https://reader.example.com/.well-known/assetlinks.json
curl -i https://reader.example.com/.well-known/apple-app-site-association
```

どちらも、保存したIDを含めて`200`を返します。`assetlinks.json`はAndroidアプリについて両方のリレーションを挙げ、`apple-app-site-association`は`applinks`と`webcredentials`の両方の下でiOSアプリを指定しています。どちらのスマートフォンもリダイレクトを経由して届いたファイルは拒否するため、インストール環境の前にあるリバースプロキシは、テナントのホスト自体でHTTPSを使ってこれらのパスに応答する必要があります。

Androidでは、アプリのインストール時または更新時にスマートフォンがサイトを確認します。ビルドをインストールしてから、スマートフォンがどう判断したかを確認します。

```bash
adb shell pm get-app-links com.example.reader
```

確認に成功していれば、テナントのホストが`verified`として表示されます。管理画面で値を修正したあとは、`adb shell pm verify-app-links --re-verify com.example.reader`でスマートフォンにもう一度確認させます。

iOSでは、スマートフォンではなくAppleのサーバーがファイルを取得し、スマートフォンはアプリのインストール時にAppleのサーバーからそれを受け取ります。そのため、管理画面での変更がスマートフォンに届くまでには時間がかかることがあります。しばらくしてからアプリを再インストールすると反映されます。

どちらのスマートフォンでも、メールやメモにあるテナントのサイトのシリーズへのリンクをタップします。アプリでシリーズが開きます。ブラウザーのアドレスバーに入力したリンクはブラウザーで開いたままになります。これは両プラットフォームの仕様で、確認の失敗ではありません。
