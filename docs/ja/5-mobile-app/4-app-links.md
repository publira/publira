テナントのサイトへのリンクは、アプリがインストールされていればブラウザーではなくアプリで開きます。対象は、シリーズ、エピソード、お知らせへのリンクと、サイトから送るメールに含まれる確認用やパスワード再設定用のリンクです。AndroidとiOSでこの動作が許可されるのは、サイトがそのアプリを認めていることを確認できた場合だけです。確認のために、AndroidとiOSはサイトに次の2つのファイルを要求します。

- Android用の`https://<tenant.host>/.well-known/assetlinks.json`
- iOS用の`https://<tenant.host>/.well-known/apple-app-site-association`

サイトは、テナント管理画面の**外部連携** › **アプリリンク**に保存した内容から、この2つのファイルを生成します。Webサーバーにファイルをアップロードする必要はありません。

この2つのファイルは、アプリがサイトのパスキーを使うことも認めます。読者が登録したパスキーはテナントのホストに属します。AndroidとiOSは、ホストのファイルでアプリが指定されている場合にだけ、そのアプリにホストのパスキーを使わせます。指定するのは、`assetlinks.json`ではリンク用の`delegate_permission/common.handle_all_urls`と並ぶ`delegate_permission/common.get_login_creds`のリレーション、`apple-app-site-association`では`applinks`と並ぶ`webcredentials`のエントリーです。サイトは指定したすべてのアプリについてこの両方を書き出すので、パスキーのために追加で入力するものはありません。Androidアプリからのパスキーによるログインは、サイトではなくアプリの署名証明書の名義でサーバーに届きます。サーバーはここにフィンガープリントを保存した証明書からのログインしか受け付けないため、登録していない鍵で署名したビルドではサイトのパスキーを使えません。

このページで指定したアプリは、Publiraのほかの機能でも使われます。アプリ内課金のApp StoreとGoogle Playの設定はここで指定したアプリで販売し、Sign in with Appleはここで指定したアプリを信頼します。そのため、アプリでこれらを試す前に、このページを入力しておいてください。

## 入力するタイミング

Androidのフィンガープリントは自分で決める値ではありません。Play App Signingを使う場合は、インストールされるアプリにGoogleが署名する鍵のフィンガープリントを入力します。この鍵は、Play Consoleでアプリを作成し、最初のApp Bundleをアップロードすると表示されます。iOS側はいつ入力してもかまいません。Android側は、Play Consoleに鍵が表示されてから入力します。

入力する値は、常にストアが配布するアプリ、つまり[ビルドと署名](./2-building.md)で作成したストア向けビルドのものです。公開しているアプリと1文字でも違うと、そのアプリのリンクはブラウザーで開くようになり、しかも不一致はどこにも報告されません。

## アプリを入力する

テナント管理画面で**外部連携** › **アプリリンク**を開きます。

### Android

**リンクをテナントのAndroidアプリで開く**にチェックを入れ、次の項目を入力します。

| フィールド | 値の確認場所 |
| --- | --- |
| **アプリケーションID** | マニフェストの`android.applicationId`です。Google Playでは、アプリのストアのアドレスにある`id=`の値と同じです |
| **SHA-256署名証明書フィンガープリント** | Play Consoleのアプリの**App signing**ページにある、**app signing key certificate**のSHA-256フィンガープリントです。アップロード鍵のフィンガープリントではありません。Playが配信するアプリの署名には、アップロード鍵は使われないためです |

フィンガープリントは、`AA:BB:…`のように2桁の16進数32組をコロンで区切ったものです。1行に1つずつ、最大10個まで入力できます。ほかの方法で署名したビルドでもリンクを開きたい場合は、そのフィンガープリントも追加します。たとえば、テスト用にインストールする、アップロード鍵で署名したリリースAPKや、鍵のローテーション中の新しい鍵です。アップロード鍵のフィンガープリントは、次のコマンドの出力の`SHA256:`の行にあります。

```bash
keytool -list -v -keystore ~/example-reader/upload.jks -alias upload
```

### iOS

**リンクをテナントのiOSアプリで開く**にチェックを入れ、次の項目を入力します。

| フィールド | 値の確認場所 |
| --- | --- |
| **Apple Team ID** | Apple Developerのウェブサイトの**Membership details**にある10文字のTeam IDです。アプリのビルドで指定した`PUBLIRA_IOS_DEVELOPMENT_TEAM`と同じ値です |
| **バンドルID** | マニフェストの`ios.bundleIdentifier`です。App Store Connectでは、**App Information**のBundle IDに同じ値が表示されます |

**アプリリンクを保存**を選びます。チェックを入れていないプラットフォームには`404`が返り、そのプラットフォームのアプリがないことが伝わります。アプリを持たないテナントでは、どちらにもチェックを入れません。

マニフェストの`tenant.host`を入力する欄はありません。この値はすでに決まっているからです。AndroidとiOSはリンク先のホストに問い合わせ、アプリが扱うと宣言しているのもそのホストだけです。したがって、`tenant.host`はテナントのサイトを提供しているホストである必要があります。

## リンクを確認する

まず、サイトが2つのファイルを返すことを確認します。

```bash
curl -i https://reader.example.com/.well-known/assetlinks.json
curl -i https://reader.example.com/.well-known/apple-app-site-association
```

どちらも、保存したIDを含む内容が`200`で返ります。`assetlinks.json`にはAndroidアプリについて2つのリレーションが、`apple-app-site-association`には`applinks`と`webcredentials`の両方にiOSアプリが記載されています。どちらのスマートフォンも、リダイレクトを経由して取得したファイルは受け付けません。そのため、Publiraの前に置くリバースプロキシは、テナントのホストのままHTTPSでこれらのパスに応答する必要があります。

Androidでは、アプリのインストール時と更新時にスマートフォンがサイトを確認します。ビルドをインストールしてから、スマートフォンの判定結果を確認します。

```bash
adb shell pm get-app-links com.example.reader
```

確認に成功していれば、テナントのホストが`verified`と表示されます。管理画面で値を修正したあとは、`adb shell pm verify-app-links --re-verify com.example.reader`でスマートフォンにもう一度確認させます。

iOSでは、スマートフォンではなくAppleのサーバーがファイルを取得し、スマートフォンはアプリのインストール時にAppleのサーバーからその内容を受け取ります。そのため、管理画面での変更がスマートフォンに届くまでには時間がかかることがあります。しばらくしてからアプリを再インストールすると、変更が反映されます。

どちらのスマートフォンでも、メールやメモに貼ったテナントのサイトのシリーズへのリンクをタップすると、アプリでシリーズが開きます。ブラウザーのアドレスバーに入力したリンクは、ブラウザーで開いたままです。これはAndroidとiOSの仕様で、確認に失敗しているわけではありません。
