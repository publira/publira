リリースによって、プロセスが前提とするデータベースのスキーマが変わることがあります。そのため、Publiraのアップグレードは新しいイメージで再起動するだけでは済みません。先にデータベースを新しくします。新しいリリースの`publiractl`イメージでスキーマとデータベースのロールを更新し、そのあとで新しいリリースのプロセスを起動します。このページでは、この順序と各手順の確認方法、マイグレーションが失敗したときの対処を説明します。

手順は、[インストール](./2-installing.md)の手順で自分で構築したPubliraを前提にしています。リポジトリのComposeファイルで動かしている場合も手順は同じで、使うコマンドだけが違います。そのコマンドは[Docker Composeで動かしている場合](#docker-composeで動かしている場合)で説明します。

## 始める前に

### リリースノートを読む

各リリースはリポジトリのタグとして作られ、リリースノートとともにリポジトリの[Releases](https://github.com/publira/publira/releases)ページで公開されます。いま動かしているリリースより後のリリースすべてについて、アップグレード先のリリースまでノートを読んでください。リリースを飛ばしてもスキーマの面では問題ありません。`db migrate`は途中のリリースのマイグレーションもすべて1回の実行で適用するからです。ただし、ノートで求められている作業は何も自動では行われません。

リリースノートの冒頭には**Upgrade notes**があります。ここには、そのリリースの変更のうちオペレーターに作業を求めるものが、その変更を加えたプルリクエストごとにすべて挙げられています。該当する変更がないときは、ないことが書かれています。挙げられるのは次のような変更です。

- **環境変数の追加、名前の変更、廃止。** 新しいリリースのプロセスを起動する前に設定します。
- **データベースのロールの追加。** まだないロールを作るには、`db roles`にそのロールのパスワードを渡す必要があります。インストール時と同じ方法でパスワードを生成し、そのロール用のフラグで渡します。
- **リバースプロキシに必要な設定の変更。** たとえば、あるパスの転送先が別のプロセスに変わる場合です。新しいリリースの[リバースプロキシの設定](./4-edge/index.md#リバースプロキシで必要な設定)に書かれているとおりに、使っているリバースプロキシにも同じ変更を加えます。[リバースプロキシの設定例](./4-edge/1-sample-configurations.md)をもとに設定を作った場合は、`git diff <current tag> <new tag> -- infra/proxy/`で設定例の変更を確認し、自分の設定に反映します。
- **新たに動かす必要のあるプロセスやサービス。**
- **時間のかかるマイグレーションや、利用の多いテーブルをロックするマイグレーション。** 実行する時間帯を選べるように挙げられています。

これらが挙げられるのはメジャーリリースだけです。`1.0.0`より前は、マイナーリリースでも挙げられます。`1.0.0`より前のパッチリリースでも、このページの手順はすべて実行してください。パッチリリースにもマイグレーションが含まれることがあり、そのプロセスは`db migrate`で更新していないスキーマの上では失敗します。そのため、プロセスを入れ替える前に`db migrate`と`db roles`を実行します。リリースの種類ごとに何が変わりうるか、どのリリースに修正が提供されるかは[リリース](./10-releases.md)で説明しています。

### 新しいリリースのイメージを取得する

何かを変更する前に、新しいリリースのすべてのイメージ`ghcr.io/publira/<name>:<new version>`を、それを動かすホストに取得しておきます。こうすると、マイグレーションを適用してからプロセスを再起動するまでの時間が、プロセスの起動にかかる時間だけで済みます。自分でビルドしたイメージを使っている場合は、新しいリリースのタグに自分の変更を反映してイメージをビルドし、ホストが取得するレジストリにプッシュします。

`publiractl`も新しいリリースのものを使います。`publiractl`にはそのリリースのマイグレーションとロールの定義が含まれています。あるリリースのプロセスが必要とするのはそのリリースのスキーマで、それより前のスキーマでは動きません。

このページの例では、`ghcr.io/publira/publiractl:<new version>`のように公開されているイメージを指定しています。バージョンはリリースのGitタグから`v`を除いたもので、`v0.2.0`なら`0.2.0`です。自分でビルドしたイメージを使っている場合は、代わりにそのイメージを指定します。

### 先にプロセスを停止するかどうかを決める

あるリリースのプロセスは、その直後のリリースのプロセスと並行して動けます。そのため次のリリースへのアップグレードでは、2つのリリースが同時に動く次の2つの時点でも、サービスを止めずに済みます。

- **`db migrate`から再起動までのあいだ**は、いま動かしているリリースのプロセスが、新しいリリースのスキーマとロールの上で動きます。どのリリースも、1つ前のリリースが読むテーブル、カラム、権限をすべて残し、削除はそれより後のリリースで行います。そのため、このあいだにプロセスの処理が失敗することはありません。
- **プロセスを入れ替えているあいだ**は、2つのリリースのWebアプリと`publira server`が互いに呼び出し合います。これは、どの順序で入れ替えても、インスタンスを1つずつ入れ替えても、どれをロールバックしても同じです。2つのリリースのワーカーはアウトボックスを共有します。いま動かしているリリースのワーカーは、新しいリリースだけが書き込む種類のエントリーを送らずに残し、新しいリリースのワーカーに任せます。いま動かしているリリースがすでに行っていたことはすべてそのまま動き、新しいリリースで加わる機能は、両側が新しいリリースになってから動きます。

この保証が及ぶのは、いま動かしているリリースの直後のリリースだけです。リリースを飛ばすと、動いているプロセスが、途中のリリースで廃止されたカラムを読んだりAPIを呼び出したりすることがあります。その場合は先にプロセスを停止するか、1つずつリリースを上げてください。

また、動かしたままのプロセスは、バックアップを取ったあとも書き込みを続けます。そのあとでマイグレーションが失敗してバックアップに戻すと、バックアップ以降の書き込みはすべて失われます。そのあいだの会員登録、購入、コメント、編集がすべて失われ、決済サービスですでに課金済みの購入も含まれます。

バックアップの前にプロセスを停止すれば、これを避けられます。バックアップのあとに書き込むものがないので、バックアップにすべての書き込みが含まれます。その代わり、バックアップから新しいリリースのプロセスが起動するまで、サービスは止まります。これらの書き込みを失うことが許されない場合は、必ず先に停止してください。エピソードを販売しているなら、毎回これに当たります。

## アップグレード

### 1. データベースをバックアップする

プロセスを停止すると決めた場合は、バックアップの前にここで停止します。

`publiractl`はスキーマを新しくすることしかできず、一度適用したマイグレーションを元に戻す手段はありません。いま動かしているリリースに戻すには、ここで取るバックアップを使います。

```bash
pg_dump --format=custom --file=publira-before-upgrade.dump --dbname="$PUBLIRA_DB_URL"
```

`PUBLIRA_DB_URL`は、`db migrate`が使う[管理用ログイン](./2-installing.md#サービスを用意する)の接続URLです。`pg_dump`は、PostgreSQLサーバーと同じかそれより新しいメジャーバージョンのものを使います。マネージドPostgreSQLのスナップショットでもかまいません。マイグレーションはオブジェクトストレージ、Valkey、シークレットには何も変更を加えないので、マイグレーションの直前にバックアップするのはデータベースだけで足ります。バックアップは、新しいリリースがしばらく問題なく動くまで残しておいてください。

### 2. マイグレーションを適用する

```bash
docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db migrate
```

開始時のバージョンと、完了時のバージョンがログに出力されます。

```text
time=2026-11-20T09:41:02.118Z level=INFO msg=migrating from_version=20261006125036
time=2026-11-20T09:41:03.402Z level=INFO msg=migrated from_version=20261006125036 to_version=20261120093000
```

リリースにマイグレーションがない場合は2つのバージョンが同じになり、この場合も終了コード0で終わります。

新しいプロセスより先にマイグレーションを実行するのは、プロセスが起動時にスキーマを確認しないからです。古いスキーマのまま起動すると、プロセスは正常に起動したように見えますが、リリースで追加されたテーブルやカラムを使うリクエストがすべて失敗します。

### 3. ロールを更新する

```bash
docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db roles
```

フラグを付けずに実行すると、どのロールもパスワードは変わりません。コマンドは、ロールを新しいリリースの定義どおりにするだけです。具体的には、マイグレーションで作られたばかりのテーブルへの権限を与え、ロールがアクセスできる範囲についてリリースで変わったほかの点も反映します。ロールごとに`publira_public: kept its password`のような行を1行ずつ出力します。この手順を飛ばすと、新しいプロセスは、リリースで追加されたすべてのテーブルで権限エラーになります。

リリースでロールが追加された場合は、[ロールの作成](./2-installing.md#2-ロールを作成する)と同じく、そのロールのパスワードを`--<name>-password-file`フラグで渡します。渡さないと、コマンドは必要なフラグを示して終了し、何も作成しません。

### 4. プロセスを入れ替える

すべてのプロセスを新しいリリースのイメージに入れ替えます。リリースノートで設定を求められた変数があれば、あわせて設定します。順序は次のとおりです。

1. **`email-renderer`**(動かしている場合)。どちらのリリースのワーカーも、描画するテンプレートを見つけられるようにするためです。
2. **`publira worker`、`publira server`、`web-storefront`、`web-admin`**(動かしている場合は`web-platform`も)。順序は問わず、インスタンスを1つずつ入れ替えてもかまいません。オーケストレーターが順に入れ替えているあいだも、サービスは止まりません。新しいリリースだけが送る種類のメールや通知は、新しいワーカーのインスタンスが取り出すまでアウトボックスで待ちます。いま動かしているリリースのインスタンスは、そうしたエントリーを1回につき1分間取り置きます。そのため、古いインスタンスが最後の1つまで停止すると、1分以内にエントリーを新しいワーカーが取り出せるようになり、そのあとはほかのエントリーと同じように送られます。ワーカーは起動時に自分のジョブキューのマイグレーションを適用するので、ジョブキューのテーブルのための手順は必要ありません。

`publira server --with-worker`を動かしている場合も、同じようにインスタンスを入れ替えます。1つずつ入れ替えてもかまいません。手順1でプロセスを停止した場合は、すべてのプロセスを起動します。

### 5. 動作を確認する

- どのプロセスも`GET /readyz`に準備完了と応答すること。
- `db version`がリリースの最新のマイグレーションを示し、dirty状態でないこと。

  ```bash
  docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db version
  ```

  ```text
  version 20261120093000
  dirty false
  ```

  このバージョンは、新しいタグの`db/migrations/`にある最も新しいファイルの、先頭のタイムスタンプです。

- テナント管理画面にログインでき、テナントのサイトが開くこと。

## マイグレーションが失敗したとき

`db migrate`は0以外の終了コードで終わり、PostgreSQLが返したエラーとともに`failed to migrate`をログに出力します。`db version`はdirty状態を示します。

```text
version 20261120093000
dirty true
```

このとき、データベースは次の状態です。

- 失敗したマイグレーションより前のマイグレーションは、すべて適用されたままです。
- PostgreSQLがマイグレーションを拒否した場合、失敗したマイグレーションはロールバックされています。マイグレーションのファイルは1つのトランザクションとして実行されるので、そのファイルの文は1つも残りません。例外は`CREATE INDEX CONCURRENTLY`でインデックスを作るマイグレーションです。これはトランザクションの外で実行されるので、失敗するとその名前の無効なインデックスが残ります。
- 接続が切れた場合は、応答が届く前に、失敗したマイグレーションがコミットされていた可能性があります。どちらなのかは`db migrate`にはわかりません。
- 記録されているバージョンは失敗したマイグレーションのもので、dirtyの印が付いています。この印を消すまで、`db migrate`は再実行を拒否します。

動かしていたプロセスは、`db migrate`から再起動までのあいだと同じく、そこまでに適用されたマイグレーションの上で動き続けます。新しいリリースのプロセスは、この状態のデータベースで起動しないでください。

### 原因を取り除いて再実行する

PostgreSQLがマイグレーションを拒否したのか、接続が切れたのかは、ログで見分けられます。PostgreSQLが拒否した場合、`failed to migrate`の行の末尾には、`(details: ERROR: canceling statement due to statement timeout (SQLSTATE 57014))`のようにPostgreSQLが返したエラーとSQLSTATEが出ます。接続が切れた場合は、代わりにネットワークのエラーが出て、SQLSTATEは付きません。

ディスクがいっぱいになった、利用の多いテーブルを待つあいだに文がタイムアウトしたなど、マイグレーションそのものではない原因でPostgreSQLが拒否した場合は、原因を取り除きます。そのうえで、記録を失敗したマイグレーションの1つ前に戻し、`db migrate`を再実行します。

1. 失敗したマイグレーションの1つ前のマイグレーションのバージョンを調べます。新しいリリースをチェックアウトしたディレクトリのルートで次を実行すると、最初の行に表示されます。

   ```bash
   ls db/migrations | grep '\.up\.sql$' | grep -B1 '^20261120093000_'
   ```

   同じ一覧は、GitHubで新しいタグの`db/migrations/`を開いても確認できます。

2. 失敗したマイグレーションがインデックスを`CONCURRENTLY`で作るものなら、残った無効なインデックスを管理用ログインで削除します。

   ```sql
   DROP INDEX CONCURRENTLY IF EXISTS <index name>;
   ```

3. 管理用ログインで記録を戻します。

   ```sql
   UPDATE schema_migrations SET version = <previous version>, dirty = false;
   ```

4. `db migrate`を再実行します。失敗したマイグレーションから実行が始まります。成功したら、[手順3](#3-ロールを更新する)から続けます。

接続が切れた場合は、まず新しいタグにある失敗したマイグレーションの`.up.sql`ファイルを読み、その変更がデータベースにあるかを調べます。マイグレーションは1つのトランザクションとして実行されるので、変更はすべてあるか、まったくないかのどちらかです。

- **まったくない場合。** マイグレーションはロールバックされています。上の手順に従います。
- **すべてある場合。** マイグレーションはコミットされています。記録を1つ前ではなく、失敗したマイグレーションそのものに設定します(`UPDATE schema_migrations SET version = <failed version>, dirty = false;`)。そのうえで`db migrate`を再実行し、それ以降のマイグレーションを続けます。
- **判断できない場合。** 行を書き換えるだけで、調べられる跡を残さないマイグレーションがこれに当たります。この場合は、次の節の手順で元のリリースに戻します。このようなマイグレーションを2回実行すると、同じ行を2回書き換えてしまうおそれがあります。

### 元のリリースに戻す

マイグレーション自体に問題がある場合や、原因がわからない場合、適用されたかどうか判断できない場合は、バックアップを復元して、それまで動かしていたリリースを使い続けます。復元すると、バックアップ以降の書き込みはすべて失われます。アップグレード中もプロセスを動かしていた場合は、そのあいだの書き込みが失われます。失敗は、`db migrate`のログと`db version`の出力を添えて[Issue](https://github.com/publira/publira/issues)で報告してください。

1. プロセスを停止します。プロセスが接続しているあいだは、データベースを削除できません。
2. データベースを削除し、最初に作成したときと同じ所有者と設定で、空のデータベースを作り直します。
3. バックアップを復元します。

   ```bash
   pg_restore --dbname="$PUBLIRA_DB_URL" publira-before-upgrade.dump
   ```

   ロールはデータベースではなくPostgreSQLサーバーに属しているので、データベースを削除しても残ります。ロールへの権限はバックアップに含まれています。

4. 動かしていたリリースのプロセスを起動します。

マネージドPostgreSQLのスナップショットを使う場合は、上の手順の代わりに、プロバイダーが案内する方法で復元します。

## Docker Composeで動かしている場合

[Docker Compose](./3-docker-compose.md)で動かしている場合は、上の手順をすべて`docker compose`で実行します。新しいリリースのComposeファイルは専用のディレクトリに置き、いま使っているディレクトリと並べます。手順1でそのディレクトリを作ったら、以降のコマンドはそこで実行します。プロジェクト名は固定なので、どちらのディレクトリで実行しても`docker compose`は同じコンテナとボリュームを操作します。

### 1. 新しいリリースをダウンロードする

いま使っているディレクトリの1つ上のディレクトリで、次を実行します。`<current version>`と`<new version>`は2つのリリースのバージョンで、タグから`v`を除いたものです。

```bash
curl -fsSLO https://github.com/publira/publira/releases/download/v<new version>/publira-deploy-<new version>.tar.gz
tar -xzf publira-deploy-<new version>.tar.gz
diff publira-deploy-<current version>/.env.example publira-deploy-<new version>/.env.example
cp -p publira-deploy-<current version>/.env publira-deploy-<new version>/.env
cd publira-deploy-<new version>
```

diffには、新しいリリースのComposeファイルで追加された変数と、読まれなくなった変数がすべて表示されます。追加された変数を`.env`に書き足してください。必須の変数が空のままだと、どの`docker compose`コマンドもその変数名を示して止まります。次に、`.env`の`PUBLIRA_IMAGE_TAG`を新しいバージョンに変えます。このバージョンもdiffに表示されています。`cp -p`でコピーすると、`.env`は自分だけが読める状態のまま保たれます。古いディレクトリに残る`.env`はいま動かしているリリースを指したままなので、マイグレーションが失敗したときはこれを使って元に戻せます。

リリースノートに、そのリリースでComposeファイルからサービスがなくなると書かれている場合は、古いディレクトリで`docker compose stop <service>`を実行してそのサービスを停止します。古いComposeファイルにはまだそのサービスがありますが、新しいComposeファイルにはありません。停止しないと、そのサービスは[手順5](#5-新しいリリースを起動する)で削除されるまで、古いリリースのまま新しいリリースのスキーマに対して動き続けます。

リポジトリをチェックアウトして動かしている場合は、代わりに新しいタグを取得し、`infra/deploy/`で新しいタグをチェックアウトします。`diff`の代わりに、チェックアウトの前に`git diff <current tag> <new tag> -- .env.example`を実行します。`.env`はGitで管理していないので、そのまま残ります。リリースでなくなるサービスは、チェックアウトの前に停止します。チェックアウトからリリースのアーカイブに切り替える場合は、`publira-deploy-<current version>`の代わりにチェックアウトの`infra/deploy/`を使って、上の手順を実行します。

### 2. イメージを取得する

```bash
docker compose pull
docker compose pull publiractl
```

1つ目のコマンドで、動かしているすべてのプロセスのイメージを、いま設定したバージョンで取得します。2つ目のコマンドでは`publiractl`を取得します。`publiractl`は常駐させないので、1つ目のコマンドでは取得されません。どちらのコマンドもビルドは行いません。

自分でビルドしたイメージを使っている場合は、代わりに新しいリリースのタグをチェックアウトし、自分の変更を反映してビルドします。ビルドしたイメージは`PUBLIRA_IMAGE_REGISTRY`が指すレジストリにプッシュします。ホスト上で`task docker:verify:full`を使ってビルドしたイメージは、プッシュする必要はありません。

### 3. データベースをバックアップする

[プロセスを先に停止する](#先にプロセスを停止するかどうかを決める)と決めた場合は、まず停止します。`web-platform`や`email-renderer`を動かしている場合は、それらも指定します。

```bash
docker compose stop server web-storefront web-admin
```

次にバックアップを取ります。

```bash
docker compose exec -T postgres pg_dump -U postgres --format=custom publira > publira-before-upgrade.dump
```

`-T`を付けるのは、ダンプが端末を経由して壊れるのを防ぐためです。

### 4. マイグレーションを適用し、ロールを更新する

```bash
docker compose run --rm publiractl db migrate
docker compose run --rm publiractl db roles
```

リリースでロールが追加された場合は、インストール時と同じように`--<name>-password-file /run/secrets/<name>-db-password`でパスワードを渡します。`.env.example`のdiffに表示された変数も`.env`に設定しておきます。

### 5. 新しいリリースを起動する

```bash
docker compose up -d --remove-orphans
docker compose ps
```

`up -d`は、イメージか設定が変わったコンテナをすべて作り直します。プロキシは新しいディレクトリの`Caddyfile`をマウントするようになるので、プロキシも作り直されます。`--remove-orphans`は、新しいリリースのComposeファイルにないサービスのコンテナを削除します。プロキシが取得した証明書は`caddy-data`ボリュームに残ります。

リポジトリをチェックアウトして動かしている場合は、`up -d`のあとに`docker compose restart proxy`も実行します。プロキシは`Caddyfile`を1つのファイルとしてマウントしていますが、`git checkout`はそのファイルを同じパスの新しいファイルに置き換えます。そのため、プロキシを動かしたままにすると、古いリリースのルーティングを読み続けます。

そのあと、[手順5](#5-動作を確認する)と同じように動作を確認します。`db version`は`docker compose run --rm publiractl db version`として実行します。確認が済んだら、古いディレクトリはもう要りません。古いディレクトリの`.env`にはすべてのシークレットが入っているので、ホストにコピーを残さないよう、ディレクトリごと、または中の`.env`を削除してください。

### Docker Composeでマイグレーションが失敗したとき

[原因を取り除いて再実行する](#原因を取り除いて再実行する)手順のSQLは、`postgres`コンテナの`psql`からスーパーユーザーで1文ずつ実行します。

```bash
docker compose exec postgres psql -U postgres -d publira -c "UPDATE schema_migrations SET version = <previous version>, dirty = false"
```

元のリリースに戻す場合は、次を実行します。

```bash
docker compose stop server web-storefront web-admin
docker compose exec postgres psql -U postgres -d postgres -c 'DROP DATABASE publira' -c 'CREATE DATABASE publira'
docker compose exec -T postgres pg_restore -U postgres -d publira < publira-before-upgrade.dump
cd ../publira-deploy-<current version>
docker compose up -d --remove-orphans
```

古いディレクトリの`.env`は元のリリースを指したままなので、`up -d`で元のリリースが起動し、プロキシも古い`Caddyfile`で動きます。リポジトリをチェックアウトして動かしている場合は、`cd`の代わりに`git checkout <current tag>`を実行し、`PUBLIRA_IMAGE_TAG`を元のリリースに戻します。さらに`up -d`のあとで`docker compose restart proxy`を実行します。
