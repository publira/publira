リリースによって、そのプロセスが前提とするデータベースのスキーマが変わることがあるので、インストール環境のアップグレードは新しいイメージで再起動するだけでは済みません。最初にデータベースを進めます。新しいリリースの`publiractl`イメージがスキーマとデータベースのロールを新しくし、その後で初めて新しいリリースのプロセスがその上で起動します。このページでは、その順序、各手順の確認方法、マイグレーションが失敗したときの対処を説明します。

手順は、[インストール](./2-installing.md)で稼働させる、自分で運用するインストール環境を前提に書かれています。リポジトリのComposeファイルから動かすインストール環境は、独自のコマンドで同じ手順を実行します。それは[Docker Composeのインストール環境の場合](#docker-composeのインストール環境の場合)にあります。

## 始める前に

### リリースノートを読む

各リリースはリポジトリのタグで、そのリリースノートとともにリポジトリの[Releases](https://github.com/publira/publira/releases)ページで公開されます。いま動かしているリリースより後の、アップグレード先までのすべてのリリースのノートを読んでください。スキーマについては、`db migrate`が途中のすべてのリリースのマイグレーションを1回の実行で適用するので、リリースを飛ばしてもかまいません。ただし、ノートがあなたに求めることは何も自動では適用されません。

リリースノートの冒頭には**Upgrade notes**があり、そのリリースに含まれる、あなたに何かを求める変更を、それを行ったプルリクエストごとにすべて挙げています。そうした変更がない場合は、そう書かれています。挙げられるのは次の変更です。

- **追加、名前の変更、または読まれなくなった環境変数。** 新しいリリースのプロセスが起動する前に設定します。
- **新しいデータベースのロール。** `db roles`には、まだ存在しないロールのパスワードが必要です。インストール時と同じ方法で生成し、そのロールのフラグで渡します。
- **エッジが行うべきことの変更。** あるパスを別のプロセスにルーティングするなどです。新しいリリースの[エッジ](./4-edge/index.md#エッジが行うべきこと)に書かれているとおりに、あなたのエッジにも同じ変更を加えます。エッジを[サンプル設定](./4-edge/1-sample-configurations.md)のいずれかから作った場合は、`git diff <current tag> <new tag> -- infra/proxy/`でサンプルの変更を確認し、自分のコピーに反映できます。
- **インストール環境がこれまで動かしていなかった、動かす必要のあるプロセスやサービス。**
- **長時間かかる、または利用の多いテーブルをロックするマイグレーション。** 実行するタイミングを選べるようにするためです。

これらのいずれかを挙げるのはメジャーリリースだけです。`1.0.0`より前は、マイナーリリースがそれに当たります。`1.0.0`より前のパッチリリースでも、このページのすべての手順を実行します。パッチリリースもマイグレーションを含むことがあり、そのプロセスは`db migrate`が進めていないスキーマでは失敗するので、プロセスを置き換える前に`db migrate`と`db roles`を実行します。それぞれの種類のリリースが変更しうることと、修正を受けるリリースは[リリース](./10-releases.md)にあります。

### 新しいリリースのイメージを取得する

何かを変更する前に、新しいリリースのすべてのイメージ`ghcr.io/publira/<name>:<new version>`を、それを動かすホストに取得します。こうすると、マイグレーションの適用からプロセスの再起動までの時間は、プロセスの起動にかかる時間だけになります。自分でビルドしたイメージを動かすインストール環境では、新しいリリースのタグから、自分の変更を反映してイメージをビルドし、ホストが取得する場所にプッシュします。

`publiractl`も新しいリリースのものを使います。このイメージはそのリリースのマイグレーションとロールの定義を含んでおり、リリースのプロセスが必要とするのはそのリリースのスキーマで、それより前のものではありません。

このページの例では、`ghcr.io/publira/publiractl:<new version>`のように公開されたイメージを指定しています。バージョンはリリースのGitタグから`v`を除いたもので、`v0.2.0`なら`0.2.0`です。自分でビルドするインストール環境では、代わりに自分のイメージを指定します。

### 先にプロセスを停止するかどうかを決める

あるリリースのプロセスは、その直後のリリースのプロセスと並んで動くので、次のリリースへのアップグレードでは、2つのリリースが同時に動く2つの時点のどちらでも、インストール環境にサービスを続けさせることができます。

- **`db migrate`から再起動までのあいだ**は、いま動かしているリリースのプロセスが、新しいリリースのスキーマとロールの上でサービスを提供します。リリースは、その前のリリースが読むテーブル、カラム、権限をすべて残し、それらの削除は後のリリースに任せるので、そのプロセスが行うことは何も失敗しません。
- **プロセスを置き換えているあいだ**は、2つのリリースのWebアプリと`publira server`が互いを呼び出します。どの順序で置き換えても、1つのコピーずつ置き換えても、どれをロールバックしても同じです。2つのリリースのワーカーはアウトボックスを共有します。いま動かしているリリースのワーカーは、新しいリリースだけが書き込む種類のエントリーを、新しいリリースのワーカーが送るために残しておきます。いま動かしているリリースがすでに行っていたことはすべて動き続け、新しいリリースが追加するものは両側が新しいリリースになってから動きます。

この保証が及ぶのは、いま動かしているリリースの直後のリリースだけです。リリースを飛ばす場合、動かしているプロセスが、途中のリリースで廃止されたカラムを読んだりAPIを呼び出したりすることがあるので、先にプロセスを停止するか、1つのリリースずつアップグレードしてください。

動かしたままのプロセスは、バックアップを取った後も書き込みを続けます。その後でマイグレーションが失敗してバックアップに戻ると、それ以降に書き込まれたものはすべて破棄されます。その間に行われた会員登録、購入、コメント、編集のすべてで、決済サービスがすでに請求した購入も含まれます。

バックアップの前にプロセスを停止すれば、これを避けられます。バックアップの後には何も書き込まないので、バックアップにすべての書き込みが含まれます。その場合、インストール環境はバックアップから新しいリリースのプロセスが起動するまで停止します。それらの書き込みを失うことが許されないときは必ず先に停止してください。エピソードを販売するインストール環境では、それは毎回です。

## アップグレード

### 1. データベースをバックアップする

プロセスを停止すると決めた場合は、バックアップの前にここで停止します。

`publiractl`はスキーマを進めるだけで、一度適用したマイグレーションを元に戻す手段はありません。ここで取るバックアップが、いま動かしているリリースに戻る方法です。

```bash
pg_dump --format=custom --file=publira-before-upgrade.dump --dbname="$PUBLIRA_DB_URL"
```

`PUBLIRA_DB_URL`は、`db migrate`が使う[管理用ログイン](./2-installing.md#サービスを用意する)の接続で、`pg_dump`はPostgreSQLサーバーと同じかそれより新しいメジャーバージョンである必要があります。マネージドPostgreSQLのスナップショットでも同じ役割を果たせます。マイグレーションはオブジェクトストレージ、Valkey、シークレットを何も変えないので、その直前にバックアップすべきなのはデータベースです。バックアップは、新しいリリースがしばらくサービスを提供するまで残しておいてください。

### 2. マイグレーションを適用する

```bash
docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db migrate
```

開始時のバージョンと、完了時に到達したバージョンがログに出力されます。

```text
time=2026-11-20T09:41:02.118Z level=INFO msg=migrating from_version=20261006125036
time=2026-11-20T09:41:03.402Z level=INFO msg=migrated from_version=20261006125036 to_version=20261120093000
```

リリースにマイグレーションがない場合は両方のバージョンが同じになり、その場合も終了コード0で終了します。

新しいプロセスより先にマイグレーションを実行するのは、プロセスが起動時にスキーマを確認しないからです。古いスキーマの上で起動すると、プロセスは正常に起動したように見え、その後リリースが追加したテーブルやカラムに触れるリクエストがすべて失敗します。

### 3. ロールを最新にする

```bash
docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db roles
```

フラグを付けなければ、どのロールもパスワードを維持し、コマンドはロールを新しいリリースが定義する状態にするだけです。マイグレーションが作成したばかりのテーブルへの権限と、リリースがロールのアクセスできる範囲について変えたそのほかのものです。ロールごとに`publira_public: kept its password`のような行を1行ずつ出力します。この手順を飛ばすと、新しいプロセスはリリースが追加したすべてのテーブルで権限エラーになります。

リリースがロールを追加する場合は、[ロールを作成する](./2-installing.md#2-ロールを作成する)と同じく、そのロールのパスワードを`--<name>-password-file`フラグで渡します。渡さないと、コマンドは必要なフラグを示して終了し、何も作成しません。

### 4. プロセスを置き換える

すべてのプロセスを、リリースノートで設定を求められた変数とともに、新しいリリースのイメージに次の順序で置き換えます。

1. **`email-renderer`**（動かしている場合）。どちらのリリースのワーカーも、描画するテンプレートを見つけられるようにするためです。
2. 「**`publira worker`、`publira server`、`web-storefront`、`web-admin`**」と、動かしている場合は`web-platform`。順序は問わず、必要なら1つのコピーずつ置き換えてかまいません。オーケストレーターが順に置き換えるあいだも、インストール環境はサービスを提供し続けます。新しいリリースだけが送る種類のメールや通知は、新しいワーカーのコピーが取り出すまでアウトボックスで待ちます。いま動かしているリリースのコピーはそうしたエントリーを1回につき1分間脇に置くので、そのコピーの最後の1つが停止すると、エントリーは1分以内に新しいワーカーが取り出せるようになり、その後ほかのエントリーと同じく送られます。ワーカーは起動時に自分のジョブキューのマイグレーションを適用するので、そのテーブルのための手順は必要ありません。

`publira server --with-worker`を動かすインストール環境も、同じ方法で、必要なら1つずつコピーを置き換えます。手順1でプロセスを停止した場合は、すべてを起動します。

### 5. インストール環境を確認する

- どのプロセスも`GET /readyz`に準備完了と応答します。
- `db version`が、リリースの最新のマイグレーションを示し、dirty状態ではないことを報告します。

  ```bash
  docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db version
  ```

  ```text
  version 20261120093000
  dirty false
  ```

  バージョンは、新しいタグの`db/migrations/`にある最新のファイルの先頭のタイムスタンプです。

- テナント管理画面にログインでき、テナントのサイトが開きます。

## マイグレーションが失敗したとき

`db migrate`は0以外の終了コードで終了し、PostgreSQLが返したエラーとともに`failed to migrate`をログに出力します。`db version`はdirty状態を報告します。

```text
version 20261120093000
dirty true
```

そのとき、データベースは次の状態になっています。

- 失敗したマイグレーションより前のマイグレーションはすべて適用されており、適用されたままです。
- PostgreSQLが失敗したマイグレーションを拒否した場合、そのマイグレーションはロールバックされています。マイグレーションのファイルは1つのトランザクションとして実行されるので、その文は何も残りません。例外は`CREATE INDEX CONCURRENTLY`でインデックスを作成するマイグレーションで、これはトランザクションの外で実行されます。失敗すると、その名前の無効なインデックスが残ります。
- 接続が切れた場合は、失敗したマイグレーションが、応答が失われる前にコミットされていた可能性があり、`db migrate`にはどちらなのか判断できません。
- 記録されるバージョンは失敗したマイグレーションのもので、dirtyの印が付きます。`db migrate`は、この印が消されるまでもう一度実行することを拒否します。

動かしていたプロセスは、`db migrate`から再起動までのあいだと同じく、それまでに適用されたマイグレーションの上で動き続けます。新しいリリースのプロセスはその上で起動しないでください。

### 原因を直してからもう一度実行する

2つの場合はログで見分けられます。PostgreSQLがマイグレーションを拒否した場合、`failed to migrate`の行は、`(details: ERROR: canceling statement due to statement timeout (SQLSTATE 57014))`のように、PostgreSQLが返したエラーとそのSQLSTATEで終わります。接続が切れた場合は、代わりにネットワークエラーが示され、SQLSTATEはありません。

ディスクがいっぱいになった、利用の多いテーブルを待って文がタイムアウトしたなど、マイグレーションの外にある原因でPostgreSQLがマイグレーションを拒否した場合は、原因を直し、記録を失敗したマイグレーションの1つ前に戻して、もう一度`db migrate`を実行します。

1. 失敗したマイグレーションの1つ前のマイグレーションのバージョンを調べます。新しいリリースのチェックアウトのルートで次を実行すると、それが最初に表示されます。

   ```bash
   ls db/migrations | grep '\.up\.sql$' | grep -B1 '^20261120093000_'
   ```

   同じ一覧は、GitHubの新しいタグの`db/migrations/`にもあります。

2. 失敗したマイグレーションがインデックスを`CONCURRENTLY`で作成するものなら、管理用ログインで、残った無効なインデックスを削除します。

   ```sql
   DROP INDEX CONCURRENTLY IF EXISTS <index name>;
   ```

3. 管理用ログインで、記録を元に戻します。

   ```sql
   UPDATE schema_migrations SET version = <previous version>, dirty = false;
   ```

4. もう一度`db migrate`を実行します。失敗したマイグレーションから始まります。成功したら、[手順3](#3-ロールを最新にする)から続けます。

接続が切れた場合は、まず新しいタグの`.up.sql`ファイルを読み、失敗したマイグレーションによる変更がデータベースにあるかを調べます。マイグレーションは1つのトランザクションとして実行されるので、変更はすべてあるか、何もないかのどちらかです。

- **何もない場合**：マイグレーションはロールバックされています。上の手順に従います。
- **すべてある場合**：マイグレーションはコミットされています。記録を1つ前ではなく失敗したマイグレーション自体に設定し（`UPDATE schema_migrations SET version = <failed version>, dirty = false;`）、もう一度`db migrate`を実行して、その後のマイグレーションを続けます。
- **判断できない場合**：行を変更するだけで、調べられるものを何も残さないマイグレーションなどです。下の手順で、動かしていたリリースに戻ります。そのようなマイグレーションを2回実行すると、同じ行を2回変更してしまう可能性があります。

### 動かしていたリリースに戻る

マイグレーション自体に問題がある場合や、原因が見つからない場合、適用されたかどうか判断できない場合は、バックアップを復元し、動かしていたリリースを引き続き動かします。復元するとバックアップ以降に書き込まれたものはすべて破棄されるので、アップグレード中もプロセスを動かし続けていた場合は、その間の書き込みは失われます。失敗は、`db migrate`のログと`db version`の出力を添えて[Issue](https://github.com/publira/publira/issues)で報告してください。

1. プロセスを停止します。プロセスが接続を保持しているあいだは、データベースを削除できません。
2. データベースを削除し、最初に作成したときと同じ所有者と設定で、空のデータベースとしてもう一度作成します。
3. そこにバックアップを復元します。

   ```bash
   pg_restore --dbname="$PUBLIRA_DB_URL" publira-before-upgrade.dump
   ```

   ロールはデータベースではなくPostgreSQLサーバーに属するので、削除の後も残り、その権限はバックアップに含まれています。

4. 動かしていたリリースのプロセスを起動します。

マネージドPostgreSQLのスナップショットは、上の手順の代わりに、プロバイダーが説明する方法で復元します。

## Docker Composeのインストール環境の場合

[Docker Compose](./3-docker-compose.md)のインストール環境では、上のすべての手順を`docker compose`で実行します。新しいリリースのComposeファイルは、いまインストール環境を動かしているディレクトリと並べて、専用のディレクトリに置きます。手順1でそれを作成したら、各コマンドはそこから実行します。プロジェクト名は固定なので、`docker compose`はどちらのディレクトリからでも同じコンテナとボリュームに届きます。

### 1. 新しいリリースをダウンロードする

いまインストール環境を動かしているディレクトリを含むディレクトリで、`<current version>`と`<new version>`を2つのリリースのバージョン（タグから`v`を除いたもの）にして、次を実行します。

```bash
curl -fsSLO https://github.com/publira/publira/releases/download/v<new version>/publira-deploy-<new version>.tar.gz
tar -xzf publira-deploy-<new version>.tar.gz
diff publira-deploy-<current version>/.env.example publira-deploy-<new version>/.env.example
cp -p publira-deploy-<current version>/.env publira-deploy-<new version>/.env
cd publira-deploy-<new version>
```

diffには、新しいリリースがComposeファイルに追加した変数と、読まなくなった変数がすべて表示されます。新しい変数を`.env`に追加してください。必須の変数を空のままにすると、どの`docker compose`コマンドも停止し、その変数を示します。次に、`.env`の`PUBLIRA_IMAGE_TAG`を新しいバージョンに設定します。これもdiffに表示されます。`cp -p`は`.env`をあなただけが読める状態に保ちます。古いディレクトリに残ったコピーは引き続きいま動かしているリリースを指定しており、マイグレーションが失敗したときに戻る手段になります。

リリースノートに、そのリリースでComposeファイルからサービスが削除されると書かれている場合は、そのサービスをまだ含んでいる古いディレクトリから`docker compose stop <service>`で停止します。新しいComposeファイルにはそのサービスが含まれないので、停止しないと、[手順5](#5-新しいリリースを起動する)で削除されるまで、動かしていたリリースのまま新しいリリースのスキーマに対して動き続けます。

チェックアウトから動かすインストール環境では、代わりに新しいタグを取得して`infra/deploy/`でチェックアウトし、`diff`の代わりにチェックアウトの前に`git diff <current tag> <new tag> -- .env.example`を実行します。その`.env`は追跡されていないのでそのまま残り、リリースが削除するサービスはチェックアウトの前に停止します。そのようなインストール環境をアーカイブに移すには、`publira-deploy-<current version>`の代わりにその`infra/deploy/`を使って上の手順を実行します。

### 2. イメージを取得する

```bash
docker compose pull
docker compose pull publiractl
```

1つ目のコマンドは、インストール環境が動かすすべてのプロセスのイメージを、いま設定したバージョンで取得します。2つ目は`publiractl`を取得します。これは常駐させることがないので、1つ目のコマンドでは取得されません。何もビルドはしません。

自分でビルドしたイメージを動かすインストール環境では、代わりに新しいリリースのタグのチェックアウトから、自分の変更を反映してイメージをビルドし、`PUBLIRA_IMAGE_REGISTRY`が指す場所にプッシュします。ホスト自身で`task docker:verify:full`を使ってビルドしたイメージは、プッシュする必要はありません。

### 3. データベースをバックアップする

[プロセスを停止する](#先にプロセスを停止するかどうかを決める)と決めた場合は、先に停止します。`web-platform`と`email-renderer`を動かしている場合はそれらも指定します。

```bash
docker compose stop server web-storefront web-admin
```

次にバックアップを取ります。

```bash
docker compose exec -T postgres pg_dump -U postgres --format=custom publira > publira-before-upgrade.dump
```

`-T`を付けると、ダンプが端末を経由しないので、破損しません。

### 4. マイグレーションを適用し、ロールを最新にする

```bash
docker compose run --rm publiractl db migrate
docker compose run --rm publiractl db roles
```

リリースがロールを追加する場合は、インストール時と同じ方法で、`--<name>-password-file /run/secrets/<name>-db-password`としてパスワードを渡し、`.env.example`のdiffに表示された変数を`.env`に設定します。

### 5. 新しいリリースを起動する

```bash
docker compose up -d --remove-orphans
docker compose ps
```

`up -d`は、イメージまたは設定が変わったすべてのコンテナを作り直します。プロキシは新しいディレクトリの`Caddyfile`をマウントするようになるので、これに含まれます。`--remove-orphans`は、新しいリリースのComposeファイルにもうないサービスのコンテナを削除します。プロキシが取得した証明書は`caddy-data`ボリュームに残ります。

チェックアウトから動かすインストール環境では、`up -d`の後に`docker compose restart proxy`も実行します。プロキシは`Caddyfile`を単一のファイルとしてマウントしており、`git checkout`はそのファイルを同じパスの新しいファイルに置き換えるので、動かしたままのプロキシは動かしていたリリースのルーティングを読み続けます。

その後、`db version`を`docker compose run --rm publiractl db version`として実行し、[手順5](#5-インストール環境を確認する)と同じくインストール環境を確認します。確認が済めば、古いディレクトリはもう必要ありません。その`.env`にはインストール環境のすべてのシークレットが含まれているので、ホストに2つ目のコピーを残さず、ディレクトリまたはその中の`.env`を削除してください。

### Composeでマイグレーションが失敗したとき

[原因を直してからもう一度実行する](#原因を直してからもう一度実行する)のSQLを、`postgres`コンテナの`psql`を通じてスーパーユーザーとして、1文ずつ実行します。

```bash
docker compose exec postgres psql -U postgres -d publira -c "UPDATE schema_migrations SET version = <previous version>, dirty = false"
```

代わりに動かしていたリリースに戻すには、次を実行します。

```bash
docker compose stop server web-storefront web-admin
docker compose exec postgres psql -U postgres -d postgres -c 'DROP DATABASE publira' -c 'CREATE DATABASE publira'
docker compose exec -T postgres pg_restore -U postgres -d publira < publira-before-upgrade.dump
cd ../publira-deploy-<current version>
docker compose up -d --remove-orphans
```

古いディレクトリの`.env`は引き続き動かしていたリリースを指定しているので、`up -d`はそれをもう一度起動し、プロキシは古い`Caddyfile`で動きます。チェックアウトから動かすインストール環境では、`cd`の代わりに`git checkout <current tag>`を実行し、`PUBLIRA_IMAGE_TAG`を動かしていたリリースに戻し、`up -d`の後に`docker compose restart proxy`を実行します。
