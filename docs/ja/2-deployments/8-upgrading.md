リリースによって、プロセスが前提にするデータベースのスキーマが変わることがあります。そのため、Publiraのアップグレードは新しいイメージで再起動するだけでは済みません。先にデータベースを進めます。新しいリリースの`publiractl`イメージでスキーマとデータベースのロールを更新し、そのあとで新しいリリースのプロセスを起動します。このページでは、この順序と各手順の確かめ方、マイグレーションが失敗したときの対処を説明します。

手順は、[インストール](./2-installing.md)の手順で自分で構築したPubliraを前提にしています。リポジトリのComposeファイルで動かしている場合も手順は同じで、使うコマンドだけが違います。そのコマンドは[Docker Composeで動かしている場合](#docker-composeで動かしている場合)で説明しています。

## 始める前に

### リリースノートを読む

リリースはリポジトリのタグで、リリースノートと一緒にリポジトリの[Releases](https://github.com/publira/publira/releases)ページで公開しています。いま動かしているリリースより後のリリースすべてについて、アップグレード先のリリースまでノートを読んでください。リリースを飛ばしても、スキーマは問題ありません。`db migrate`が途中のリリースのマイグレーションも1回の実行ですべて適用するからです。ただ、ノートで求められている作業は自動では行われません。

リリースノートの冒頭には**Upgrade notes**があります。ここには、そのリリースの変更のうちオペレーターに作業を求めるものが、変更を加えたプルリクエストごとに残らず並びます。該当する変更がなければ、ないと書かれています。並ぶのは次のような変更です。

| 変更 | すること |
| --- | --- |
| 環境変数の追加、名前の変更、廃止 | 新しいリリースのプロセスを起動する前に設定します |
| データベースのロールの追加 | `db roles`でまだないロールを作るには、そのロールのパスワードが必要です。インストールのときと同じ方法で生成し、そのロールのフラグで渡します |
| リバースプロキシに必要な設定の変更(あるパスの転送先が別のプロセスに変わるなど) | 新しいリリースの[リバースプロキシで必要な設定](./4-edge/index.md#リバースプロキシで必要な設定)に従って、自分のリバースプロキシにも同じ変更を加えます。[設定例](./4-edge/1-sample-configurations.md)をもとにしているなら、`git diff <current tag> <new tag> -- infra/proxy/`で設定例の変更を確認し、自分の設定に取り込みます |
| 新たに動かす必要のあるプロセスやサービス | そのプロセスやサービスを動かします |
| 時間のかかるマイグレーションや、利用の多いテーブルをロックするマイグレーション | 実行する時間帯を選びます |

これらが並ぶのはメジャーリリースだけで、`1.0.0`より前ならマイナーリリースもです。ただし、`1.0.0`より前のパッチリリースでも、このページの手順はすべて実行してください。パッチリリースにもマイグレーションが入ることがあり、そのプロセスは`db migrate`で進めていないスキーマでは失敗します。プロセスを入れ替える前に`db migrate`と`db roles`を実行するのはそのためです。リリースの種類ごとに何が変わりうるか、どのリリースに修正が提供されるかは[リリース](./10-releases.md)で説明しています。

### 新しいリリースのイメージを取得する

何かを変える前に、新しいリリースのすべてのイメージ`ghcr.io/publira/<name>:<new version>`を、それを動かすホストにpullしておきます。こうしておけば、マイグレーションを適用してからプロセスを再起動するまでの時間が、プロセスの起動にかかる時間だけで済みます。自分でビルドしたイメージを使っているなら、新しいリリースのタグに自分の変更を移してビルドし、ホストがpullする場所にプッシュします。

`publiractl`も新しいリリースのものを使います。`publiractl`にはそのリリースのマイグレーションとロールの定義が入っていて、あるリリースのプロセスにはそのリリースのスキーマが必要です。それより前のスキーマでは動きません。

このページの例では、`ghcr.io/publira/publiractl:<new version>`のように公開イメージを指定しています。バージョンはリリースのGitのタグから`v`を除いたもので、`v0.2.0`なら`0.2.0`です。自分でビルドしたイメージを使っているなら、代わりにそのイメージを指定します。

### 先にプロセスを停止するかどうかを決める

あるリリースのプロセスは、すぐ次のリリースのプロセスと並んで動けます。そのため、次のリリースへのアップグレードでは、2つのリリースが同時に動く次の2つの場面でも、サービスを止めずに済みます。

- `db migrate`から再起動までの間は、いま動かしているリリースのプロセスが、新しいリリースのスキーマとロールの上で動きます。どのリリースも、1つ前のリリースが読むテーブル、カラム、権限をすべて残し、削除はもっと後のリリースに任せます。そのため、この間にプロセスの処理が失敗することはありません。
- プロセスを入れ替えている間は、2つのリリースのWebアプリと`publira server`が互いを呼び出します。どの順に入れ替えても、インスタンスを1つずつ入れ替えても、どれをロールバックしても構いません。2つのリリースのワーカーはアウトボックスを共有します。いま動かしているリリースのワーカーは、新しいリリースだけが書く種類のエントリーを送らずに残し、新しいリリースのワーカーに任せます。いまのリリースでできていたことはすべてそのまま動き、新しいリリースで加わる機能は、両方の側が新しいリリースになってから動きます。

この保証が届くのは、いま動かしているリリースのすぐ次のリリースまでです。リリースを飛ばすと、動いているプロセスが、途中のリリースで廃止されたカラムを読んだりAPIを呼び出したりすることがあります。その場合は先にプロセスを止めるか、リリースを1つずつ上げてください。

動かしたままのプロセスは、バックアップのあとも書き込みを続けます。そのあとでマイグレーションが失敗してバックアップに戻すと、バックアップ以降の書き込みはすべて消えます。その間の会員登録、購入、コメント、編集がすべて失われ、決済プロバイダーがすでに課金した購入も例外ではありません。

バックアップの前にプロセスを止めれば、これは避けられます。バックアップのあとに書き込むものがないので、すべての書き込みがバックアップに入ります。その代わり、バックアップから新しいリリースのプロセスが起動するまで、サービスは止まります。これらの書き込みを失えないなら、必ず先に止めてください。エピソードを販売しているなら、毎回そうなります。

## アップグレード

### 1. データベースをバックアップする

プロセスを止めると決めたなら、バックアップの前にここで止めます。

`publiractl`はスキーマを進めることしかできず、一度適用したマイグレーションを元に戻す手段はありません。いま動かしているリリースに戻るには、ここで取るバックアップを使います。

```bash
pg_dump --format=custom --file=publira-before-upgrade.dump --dbname="$PUBLIRA_DB_URL"
```

`PUBLIRA_DB_URL`は、`db migrate`が使う[管理用ログイン](./2-installing.md#サービスを用意する)の接続URLです。`pg_dump`は、PostgreSQLサーバーと同じかそれより新しいメジャーバージョンのものを使ってください。マネージドのPostgreSQLのスナップショットでも構いません。マイグレーションはオブジェクトストレージ、Valkey、シークレットには手を付けないので、直前にバックアップするのはデータベースだけで足ります。バックアップは、新しいリリースがしばらく問題なく動くまで残しておいてください。

### 2. マイグレーションを適用する

```bash
docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db migrate
```

開始時のバージョンと、終わったときのバージョンがログに出ます。

```text
time=2026-11-20T09:41:02.118Z level=INFO msg=migrating from_version=20261006125036
time=2026-11-20T09:41:03.402Z level=INFO msg=migrated from_version=20261006125036 to_version=20261120093000
```

リリースにマイグレーションがなければ2つのバージョンは同じで、その場合も終了コード0で終わります。

新しいプロセスより先にマイグレーションを実行するのは、プロセスが起動時にスキーマを確かめないからです。古いスキーマのまま起動すると、プロセスは正常に起動したように見えて、リリースで加わったテーブルやカラムに触れるリクエストがすべて失敗します。

### 3. ロールを更新する

```bash
docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db roles
```

フラグを付けずに実行すると、どのロールもパスワードはそのままで、ロールを新しいリリースの定義に合わせるだけです。マイグレーションで作られたばかりのテーブルへの権限を与え、ロールがアクセスできる範囲についてリリースで変わったことも反映します。出力は`publira_public: kept its password`のように、ロールごとに1行です。この手順を飛ばすと、新しいプロセスはリリースで加わったどのテーブルでも権限のエラーになります。

リリースでロールが加わったなら、[ロールを作成する](./2-installing.md#2-ロールを作成する)と同じく、そのロールのパスワードを`--<name>-password-file`フラグで渡します。渡さなければ、コマンドは必要なフラグを示して終了し、何も作りません。

### 4. プロセスを入れ替える

すべてのプロセスを新しいリリースのイメージに入れ替えます。リリースノートで設定を求められた変数があれば、一緒に設定してください。順序は次のとおりです。

1. `email-renderer`を動かしているなら、最初に入れ替えます。どちらのリリースのワーカーも、描画するテンプレートを見つけられるようにするためです。
2. 続いて`publira worker`、`publira server`、`web-storefront`、`web-admin`を入れ替えます。`web-platform`を動かしているなら、それも一緒です。順序は問わず、インスタンスを1つずつ入れ替えても構いません。オーケストレーターが順に入れ替えている間も、サービスは止まりません。

新しいリリースだけが送る種類のメールや通知は、新しいワーカーのインスタンスが取り出すまでアウトボックスで待ちます。いま動かしているリリースのインスタンスは、そうしたエントリーを1回につき1分間脇に置きます。古いインスタンスが最後の1つまで止まれば、1分以内に新しいワーカーがエントリーを取り出せるようになり、あとはほかのエントリーと同じように送られます。ワーカーは起動時に自分のジョブキューのマイグレーションを適用するので、ジョブキューのテーブルのための手順はいりません。

`publira server --with-worker`を動かしている場合も、同じようにインスタンスを入れ替えます。1つずつ入れ替えても構いません。手順1でプロセスを止めたなら、すべて起動します。

### 5. 動作を確認する

次の3つを確かめます。

- どのプロセスも`GET /readyz`に準備完了と応答します。
- `db version`がリリースの最新のマイグレーションを示し、dirtyになっていません。

  ```bash
  docker run --rm -e PUBLIRA_DB_URL ghcr.io/publira/publiractl:<new version> db version
  ```

  ```text
  version 20261120093000
  dirty false
  ```

  このバージョンは、新しいタグの`db/migrations/`でいちばん新しいファイルの、先頭のタイムスタンプです。

- テナント管理画面にログインでき、テナントのサイトが開きます。

## マイグレーションが失敗したとき

`db migrate`は0以外の終了コードで終わり、PostgreSQLが返したエラーと一緒に`failed to migrate`をログに出します。`db version`はdirtyを示します。

```text
version 20261120093000
dirty true
```

このとき、データベースは次の状態です。

- 失敗したマイグレーションより前のマイグレーションは、すべて適用されたままです。
- PostgreSQLがマイグレーションを拒否したのなら、失敗したマイグレーションはロールバックされています。マイグレーションのファイルは1つのトランザクションで実行されるので、その文は1つも残りません。例外は`CREATE INDEX CONCURRENTLY`でインデックスを作るマイグレーションです。これはトランザクションの外で実行されるので、失敗するとその名前の無効なインデックスが残ります。
- 接続が切れたのなら、応答が届く前に、失敗したマイグレーションがコミットされていたかもしれません。どちらだったのかは`db migrate`にはわかりません。
- 記録されているバージョンは失敗したマイグレーションのもので、dirtyの印が付いています。この印を消すまで、`db migrate`は再実行を拒みます。

動かしていたプロセスは、`db migrate`から再起動までの間と同じく、そこまでに適用されたマイグレーションの上で動き続けます。新しいリリースのプロセスは、この状態のデータベースで起動しないでください。

### 原因を取り除いて再実行する

PostgreSQLが拒否したのか、接続が切れたのかは、ログで見分けられます。PostgreSQLが拒否したなら、`failed to migrate`の行の末尾に`(details: ERROR: canceling statement due to statement timeout (SQLSTATE 57014))`のように、PostgreSQLが返したエラーとSQLSTATEが出ます。接続が切れたなら、代わりにネットワークのエラーが出て、SQLSTATEは付きません。

ディスクがいっぱいになった、利用の多いテーブルを待つ間に文がタイムアウトしたなど、マイグレーションの外にある原因でPostgreSQLが拒否したなら、原因を取り除きます。そのうえで記録を失敗したマイグレーションの1つ前に戻し、`db migrate`を再実行します。

1. 失敗したマイグレーションの1つ前のバージョンを調べます。新しいリリースをチェックアウトしたディレクトリのルートで次を実行すると、最初の行に出ます。

   ```bash
   ls db/migrations | grep '\.up\.sql$' | grep -B1 '^20261120093000_'
   ```

   同じ一覧は、GitHubで新しいタグの`db/migrations/`を開いても見られます。

2. 失敗したマイグレーションがインデックスを`CONCURRENTLY`で作るものなら、残った無効なインデックスを管理用ログインで削除します。

   ```sql
   DROP INDEX CONCURRENTLY IF EXISTS <index name>;
   ```

3. 管理用ログインで記録を戻します。

   ```sql
   UPDATE schema_migrations SET version = <previous version>, dirty = false;
   ```

4. `db migrate`を再実行します。失敗したマイグレーションから始まり、成功したら[手順3](#3-ロールを更新する)から続けます。

接続が切れたなら、まず新しいタグにある失敗したマイグレーションの`.up.sql`ファイルを読み、その変更がデータベースにあるかどうかを調べます。マイグレーションは1つのトランザクションで実行されるので、変更はすべてあるか、まったくないかのどちらかです。

- 変更がまったくなければ、マイグレーションはロールバックされています。上の手順に従ってください。
- 変更がすべてあれば、マイグレーションはコミットされています。記録を1つ前ではなく失敗したマイグレーションそのものに設定し(`UPDATE schema_migrations SET version = <failed version>, dirty = false;`)、`db migrate`を再実行して、それより後のマイグレーションを続けます。
- 行を書き換えるだけで調べる手がかりを残さないマイグレーションのように、どちらか判断できないなら、次の節の手順で元のリリースに戻します。そうしたマイグレーションを2回実行すると、同じ行を2回書き換えてしまうおそれがあります。

### 元のリリースに戻す

マイグレーション自体に問題があるときや、原因がわからないとき、適用されたかどうか判断できないときは、バックアップを復元して、それまでのリリースを使い続けます。復元するとバックアップ以降の書き込みはすべて消えるので、アップグレード中もプロセスを動かしていたなら、その間の書き込みは失われます。失敗は、`db migrate`のログと`db version`の出力を添えて[Issue](https://github.com/publira/publira/issues)で報告してください。

1. プロセスを止めます。プロセスが接続している間は、データベースを削除できません。
2. データベースを削除し、最初に作ったときと同じ所有者と設定で、空のデータベースを作り直します。
3. バックアップを復元します。

   ```bash
   pg_restore --dbname="$PUBLIRA_DB_URL" publira-before-upgrade.dump
   ```

   ロールはデータベースではなくPostgreSQLサーバーのものなので、データベースを削除しても残ります。ロールへの権限はバックアップに入っています。

4. 動かしていたリリースのプロセスを起動します。

マネージドのPostgreSQLのスナップショットなら、上の手順の代わりに、提供元が案内する方法で復元します。

## Docker Composeで動かしている場合

[Docker Compose](./3-docker-compose.md)で動かしているなら、上の手順をすべて`docker compose`で実行します。新しいリリースのComposeファイルは専用のディレクトリに置き、いま使っているディレクトリと並べます。手順1でそのディレクトリを作ったら、以降のコマンドはそこで実行します。プロジェクト名は固定なので、どちらのディレクトリで実行しても`docker compose`は同じコンテナとボリュームを扱います。

### 1. 新しいリリースをダウンロードする

いま使っているディレクトリが入っているディレクトリで、次を実行します。`<current version>`と`<new version>`は2つのリリースのバージョンで、タグから`v`を除いたものです。

```bash
curl -fsSLO https://github.com/publira/publira/releases/download/v<new version>/publira-deploy-<new version>.tar.gz
tar -xzf publira-deploy-<new version>.tar.gz
diff publira-deploy-<current version>/.env.example publira-deploy-<new version>/.env.example
cp -p publira-deploy-<current version>/.env publira-deploy-<new version>/.env
cd publira-deploy-<new version>
```

diffには、新しいリリースのComposeファイルで加わった変数と、読まれなくなった変数がすべて出ます。加わった変数を`.env`に書き足してください。必須の変数が空のままだと、どの`docker compose`のコマンドもその変数を示して止まります。続いて、`.env`の`PUBLIRA_IMAGE_TAG`を新しいバージョンに変えます。このバージョンもdiffに出ています。`cp -p`でコピーすれば、`.env`は自分だけが読める権限のままです。古いディレクトリに残した`.env`はいま動かしているリリースを指したままなので、マイグレーションが失敗したときに戻る道になります。

そのリリースでComposeファイルからサービスがなくなるとリリースノートにあれば、古いディレクトリで`docker compose stop <service>`を実行して、そのサービスを止めます。古いComposeファイルにはまだそのサービスがありますが、新しいComposeファイルにはありません。止めておかないと、そのサービスは[手順5](#5-新しいリリースを起動する)で削除されるまで、古いリリースのまま新しいリリースのスキーマに対して動き続けます。

リポジトリをチェックアウトして動かしているなら、代わりに新しいタグを取得して`infra/deploy/`でチェックアウトします。`diff`の代わりに、チェックアウトの前に`git diff <current tag> <new tag> -- .env.example`を実行します。`.env`はGitで管理していないので、そのまま残ります。リリースでなくなるサービスは、チェックアウトの前に止めます。チェックアウトからリリースのアーカイブに移るなら、`publira-deploy-<current version>`の代わりにチェックアウトの`infra/deploy/`を使って上の手順を実行します。

### 2. イメージを取得する

```bash
docker compose pull
docker compose pull publiractl
```

1つ目のコマンドは、動かしているすべてのプロセスのイメージを、いま設定したバージョンでpullします。`publiractl`は常駐させないので1つ目のコマンドには含まれず、2つ目のコマンドでpullします。どちらもビルドはしません。

自分でビルドしたイメージを使っているなら、代わりに新しいリリースのタグをチェックアウトし、自分の変更を移してビルドします。ビルドしたイメージは`PUBLIRA_IMAGE_REGISTRY`が指す場所にプッシュします。ホスト上で`task docker:verify:full`でビルドしたイメージなら、プッシュはいりません。

### 3. データベースをバックアップする

[先にプロセスを停止する](#先にプロセスを停止するかどうかを決める)と決めたなら、まず止めます。`web-platform`や`email-renderer`を動かしているなら、それも指定します。

```bash
docker compose stop server web-storefront web-admin
```

次にバックアップを取ります。

```bash
docker compose exec -T postgres pg_dump -U postgres --format=custom publira > publira-before-upgrade.dump
```

`-T`を付けるのは、ダンプが端末を通って壊れるのを防ぐためです。

### 4. マイグレーションを適用し、ロールを更新する

```bash
docker compose run --rm publiractl db migrate
docker compose run --rm publiractl db roles
```

リリースでロールが加わったなら、インストールのときと同じように`--<name>-password-file /run/secrets/<name>-db-password`でパスワードを渡します。そのとき、`.env.example`のdiffに出た変数を`.env`に設定しておきます。

### 5. 新しいリリースを起動する

```bash
docker compose up -d --remove-orphans
docker compose ps
```

`up -d`は、イメージか設定が変わったコンテナをすべて作り直します。プロキシも新しいディレクトリの`Caddyfile`をマウントするようになるので、作り直されます。`--remove-orphans`は、新しいリリースのComposeファイルにないサービスのコンテナを削除します。プロキシが取得した証明書は`caddy-data`ボリュームに残ります。

リポジトリをチェックアウトして動かしているなら、`up -d`のあとに`docker compose restart proxy`も実行します。プロキシは`Caddyfile`を1つのファイルとしてマウントしていて、`git checkout`はそのファイルを同じパスの新しいファイルに置き換えます。プロキシを動かしたままにすると、古いリリースのルーティングを読み続けてしまいます。

そのあと、[手順5](#5-動作を確認する)と同じように動作を確認します。`db version`は`docker compose run --rm publiractl db version`で実行します。確認が済めば、古いディレクトリはもういりません。そこの`.env`にはPubliraのすべてのシークレットが入っているので、ホストにコピーを残さないよう、ディレクトリごと、または中の`.env`を削除してください。

### Docker Composeでマイグレーションが失敗したとき

[原因を取り除いて再実行する](#原因を取り除いて再実行する)のSQLは、`postgres`コンテナの`psql`からスーパーユーザーで1文ずつ実行します。

```bash
docker compose exec postgres psql -U postgres -d publira -c "UPDATE schema_migrations SET version = <previous version>, dirty = false"
```

元のリリースに戻すなら、次を実行します。

```bash
docker compose stop server web-storefront web-admin
docker compose exec postgres psql -U postgres -d postgres -c 'DROP DATABASE publira' -c 'CREATE DATABASE publira'
docker compose exec -T postgres pg_restore -U postgres -d publira < publira-before-upgrade.dump
cd ../publira-deploy-<current version>
docker compose up -d --remove-orphans
```

古いディレクトリの`.env`は元のリリースを指したままなので、`up -d`で元のリリースが起動し、プロキシも古い`Caddyfile`で動きます。リポジトリをチェックアウトして動かしているなら、`cd`の代わりに`git checkout <current tag>`を実行し、`PUBLIRA_IMAGE_TAG`を元のリリースに戻して、`up -d`のあとに`docker compose restart proxy`を実行します。
