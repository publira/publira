Publiraは、常駐する4つのプロセスと、それらが依存するいくつかのサービス、手動で実行する1つのコマンドラインツールで構成されます。このページでは、1つのテナントの公開サイトと管理画面を提供する最小構成を説明します。この構成では、Publiraをプラットフォーム管理画面ではなく`publiractl`で管理します。

## Publiraで動かすプロセス

| プロセス | 提供するもの | 接続元 |
| --- | --- | --- |
| `web-storefront` | すべてのテナントの公開サイト | リバースプロキシ(各テナントのドメイン) |
| `web-admin` | テナント管理画面 | リバースプロキシ(各テナントの管理画面のホスト。テナントに別のホストを割り当てていなければ`admin.<domain>`) |
| `publira server` | `/rpc`配下のAPIと画像配信(どちらも1つのポートで提供) | リバースプロキシ(`/rpc`配下の公開APIと`/images`)、`web-storefront`と`web-admin`(`/rpc`) |
| `publira worker` | メールとプッシュ通知の送信、キャッシュの再検証、すべての定期ジョブ | なし(ヘルスチェックに応答するだけです) |

どのプロセスも`GET /livez`と`GET /readyz`に応答するので、オーケストレーターから死活監視できます。Webアプリは共通の1つのイメージから、`publira server`と`publira worker`はもう1つのイメージからビルドされます。イメージの一覧は[イメージのビルド手順](https://github.com/publira/publira/blob/main/infra/docker/README.md)にあります。

1台のホストで動かし、サーバーもワーカーも2つ以上動かすことがない構成であれば、両者を1つのプロセスにまとめられます。`publira server --with-worker`は、2つのプロセスの処理をすべて同じ2つのポートで行い、両方の環境変数を読みます。ただし、失うものが2つあります。1つは、サーバーとワーカーを別々にスケールできなくなることです。もう1つは、インターネットに面したプロセスがワーカー用の3つのデータベースログインも持つことです。そのうちの1つはジョブキューのテーブルを所有し、自分でテーブルを作成することもできます。[Docker Compose](./3-docker-compose.md)の構成では、両者を1つのプロセスで動かしています。別々にスケールしたい場合や、ワーカーのログインをインターネットに面したプロセスに持たせたくない場合は、2つを分けて動かしてください。

`publira server`が待ち受けるポートは1つなので、Cloud Runのようにサービスごとに1つのポートを公開するプラットフォームでも、そのまま1つのサービスとして動かせます。さらに、`--role storefront`を付けた2つ目の`publira server`サービスをロードバランサーの背後で動かし、テナントのドメインと`web-storefront`をそちらに向けることもできます。`--role storefront`のプロセスは公開APIとテナントのサイトの画像だけを提供し、`web-storefront`が呼び出すのも公開APIだけです。この構成では、読者向けのリクエストを処理するプロセスはストアフロント用のログインだけでデータベースに接続し、そのログインはリクエストごとに1つのテナントに制限されます。このプロセスは、テナント管理画面とプラットフォーム管理画面のどちらのログインも、Webアプリが管理画面のAPIを呼び出すときの認証情報も持ちません。1つ目のサービスは、引き続き`web-admin`と`web-platform`、管理画面のホストからのリクエストを処理します。各ロールが提供するものと読む環境変数は[デプロイのリファレンス](https://github.com/publira/publira/blob/main/infra/deploy/README.md#long-lived-processes)にあります。

画像配信と公開APIは、それぞれ専用のホスト名とロードバランサーを用意して、別々に提供することもできます。テナントのサイトの画像はテナントに割り当てた画像用のホストで、公開APIはWebアプリとモバイルアプリの接続先に設定したホストで提供します。どちらも`--role storefront`のプロセスなので、プロセス側の変更はありません。変わるのはホスト名と、その前に置くロードバランサーだけです。詳しくは[画像と公開APIを別々に提供する方法](./7-scaling-out.md#画像と公開apiを別々に提供する)を参照してください。

どのプロセスも自身では状態を持ちません。Publiraが保存するデータはPostgreSQLとオブジェクトストレージに、実行中のプロセスが共有するデータはValkeyにあり、セッションはブラウザーが送り返すCookieです。そのため、どのプロセスも複数動かせ、ロードバランサーはスティッキーセッションなしでリクエストを振り分けられます。Publiraの規模が大きくなったときに何を増やすか、その前に何を共有しておく必要があるかは[スケールアウト](./7-scaling-out.md)で説明します。

## 依存するサービス

| サービス | 利用するもの | 保持するもの |
| --- | --- | --- |
| リバースプロキシ(ロードバランサー、リバースプロキシ、またはその前に置くCDN) | ブラウザーとモバイルアプリ | ホストとパスに応じてリクエストを適切なプロセスへ送るルーティングと、TLS |
| PostgreSQL | すべてのプロセス | Publiraが保存するすべてのデータ |
| Valkey、またはRedisプロトコルに対応した任意のサーバー | `publira server`、`web-storefront`、`web-admin` | 画像変換のキャッシュ、レート制限のカウンター、Webアプリの共有キャッシュ |
| S3互換のオブジェクトストレージ | `publira server`、`publira worker` | アップロードされたすべての画像 |
| SMTPサーバー | `publira worker` | なし(読者の会員登録やパスワードの再設定など、Publiraが送るメールを配送します) |

データベースとバケットは自分で作成してください。その中身はすべてPubliraが作成します。Publiraの前には、マネージドのロードバランサーや自分で運用するプロキシなど、プラットフォームが用意するものを何でも使えます。何を使う場合でも、必要な設定は[リバースプロキシで必要な設定](./4-edge/index.md#リバースプロキシで必要な設定)で説明しています。リポジトリにあるTraefik、nginx、Caddyのサンプル設定は、その実現方法の一例です。

## 手動で実行するコマンド

`publiractl`は、リリースのたびにデータベースのマイグレーションとロールを適用するほか、新しく構築したPubliraの初期設定と、その後のプラットフォーム設定の変更に使います。定期実行の仕組みを用意する必要はありません。繰り返し実行するジョブは、すべて`publira worker`が自分でスケジュールします。

## 追加できるプロセス

| プロセス | 追加される機能 |
| --- | --- |
| `email-renderer` | すべてのメールにHTMLパートが付きます。このプロセスがない場合、同じメールがプレーンテキストで送られます |
| `web-platform` | プラットフォーム管理画面。オペレーターは`publiractl`の代わりにブラウザーでテナントとプラットフォームの設定を管理できます |
