Publiraは、常駐する4つのプロセスと、それらが依存するいくつかのサービス、手動で実行する1つのコマンドラインツールでできています。このページでは、テナントの公開サイトと管理画面を提供できる最小の構成を説明します。この構成では、プラットフォーム管理画面を使わず`publiractl`でPubliraを管理します。

## Publiraで動かすプロセス

| プロセス | 提供するもの | 接続元 |
| --- | --- | --- |
| `web-storefront` | すべてのテナントの公開サイト | 各テナントのドメインへのリクエストを転送するリバースプロキシ |
| `web-admin` | テナント管理画面 | 各テナントの管理画面のホストへのリクエストを転送するリバースプロキシ。管理画面のホストは、別のホストを割り当てていなければ`admin.<domain>`です |
| `publira server` | `/rpc`配下のAPIと画像配信。どちらも1つのポートで提供します | `/rpc`配下の公開APIと`/images`へのリクエストを転送するリバースプロキシと、`/rpc`を呼び出す`web-storefront`と`web-admin` |
| `publira worker` | メールとプッシュ通知の送信、キャッシュの再検証、すべての定期ジョブ | なし。ヘルスチェックに応答するだけです |

どのプロセスも`GET /livez`と`GET /readyz`に応答するので、オーケストレーターから死活を確認できます。Webアプリは1つのイメージから、`publira server`と`publira worker`は別のもう1つのイメージからビルドします。イメージの一覧は[イメージのビルド手順](https://github.com/publira/publira/blob/main/infra/docker/README.md)にあります。

1台のホストで動かし、サーバーもワーカーも1つずつしか動かさないのであれば、両者を1つのプロセスにまとめられます。`publira server --with-worker`は2つのプロセスの仕事をすべて同じ2つのポートでこなし、両方の環境変数を読みます。ただし、引き換えに2つのことを諦めることになります。まず、サーバーとワーカーを別々にスケールできなくなります。次に、インターネットに面したプロセスがワーカー用の3つのデータベースログインも持つことになります。そのうちの1つはジョブキューのテーブルを所有し、自分でテーブルを作ることもできるログインです。[Docker Compose](./3-docker-compose.md)の構成は両者を1つのプロセスで動かしています。別々にスケールしたい場合や、ワーカーのログインをインターネットに面したプロセスから遠ざけたい場合は、2つを分けて動かしてください。

`publira server`が待ち受けるポートは1つなので、Cloud Runのようにサービスごとに1つのポートを公開するプラットフォームでも、そのまま1つのサービスとして動かせます。ロードバランサーの背後に`--role storefront`を付けた2つ目の`publira server`サービスを置き、テナントのドメインと`web-storefront`の接続先をそちらに向けることもできます。`--role storefront`のプロセスが提供するのは公開APIとテナントのサイトの画像だけで、`web-storefront`が呼び出すのも公開APIだけです。この構成にすると、読者のリクエストを処理するプロセスはストアフロント用のログインでしかデータベースに接続しません。このログインがリクエストごとに扱えるテナントは1つに限られます。また、このプロセスはどちらの管理画面のログインも持たず、Webアプリが管理画面のAPIを呼び出すときの認証情報も持ちません。1つ目のサービスは、引き続き`web-admin`と`web-platform`、管理画面のホストからのリクエストを処理します。各ロールが提供するものと読む環境変数は[デプロイのリファレンス](https://github.com/publira/publira/blob/main/infra/deploy/README.md#long-lived-processes)にまとめています。

画像配信と公開APIは、それぞれ専用のホスト名とロードバランサーを用意して、別々に提供することもできます。テナントのサイトの画像はテナントに割り当てた画像用のホストで、公開APIはWebアプリとモバイルアプリの接続先に設定したホストで提供します。どちらも`--role storefront`のプロセスなので、プロセスには何も変更が要りません。変わるのはホスト名と、その前に置くロードバランサーだけです。詳しくは[画像と公開APIを別々に提供する方法](./7-scaling-out.md#画像と公開apiを別々に提供する)を参照してください。

どのプロセスも自分では状態を持ちません。Publiraが保存するものはPostgreSQLとオブジェクトストレージに、プロセスが実行中に共有するものはValkeyにあり、セッションはブラウザーが送り返すCookieです。そのため、どのプロセスも複数動かせます。ロードバランサーがリクエストを振り分けるのにスティッキーセッションも必要ありません。規模が大きくなったときに何を増やせばよいか、その前に何を共有しておくべきかは[スケールアウト](./7-scaling-out.md)で説明します。

## 依存するサービス

| サービス | 利用するもの | 保持するもの |
| --- | --- | --- |
| リバースプロキシ。ロードバランサー、リバースプロキシ、その前に置くCDNのいずれか | ブラウザーとモバイルアプリ | ホストとパスに応じて適切なプロセスへリクエストを送るルーティングと、TLS |
| PostgreSQL | すべてのプロセス | Publiraが保存するすべてのデータ |
| ValkeyかRedisプロトコルに対応したサーバー | `publira server`、`web-storefront`、`web-admin` | 画像変換のキャッシュ、レート制限のカウンター、Webアプリの共有キャッシュ |
| S3互換のオブジェクトストレージ | `publira server`、`publira worker` | アップロードされたすべての画像 |
| SMTPサーバー | `publira worker` | なし。読者の会員登録やパスワードの再設定など、Publiraが送るメールを配送します |

データベースとバケットは自分で作成してください。その中に必要なものはすべてPubliraが作ります。リバースプロキシには、マネージドのロードバランサーや自分で運用するプロキシなど、プラットフォームで使えるものを何でも使えます。何を使うにしても、満たすべき要件は[リバースプロキシで必要な設定](./4-edge/index.md#リバースプロキシで必要な設定)で説明しています。リポジトリにあるTraefik、nginx、Caddyの設定例は、その要件を満たす方法の一例です。

## 手動で実行するコマンド

`publiractl`は、リリースのたびにデータベースのマイグレーションとロールを適用するのに使います。新しく構築したPubliraの初期設定と、その後のプラットフォーム設定の変更にも使います。定期的に実行する仕組みを用意する必要はありません。繰り返し実行するジョブは、すべて`publira worker`が自分でスケジュールします。

## 追加できるプロセス

| プロセス | 追加されるもの |
| --- | --- |
| `email-renderer` | すべてのメールにHTMLパートが付きます。このプロセスがなければ、同じメールをプレーンテキストで送ります |
| `web-platform` | プラットフォーム管理画面です。オペレーターは`publiractl`の代わりにブラウザーで、テナントとプラットフォームの設定を管理できます |
