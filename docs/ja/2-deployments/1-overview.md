Publiraのインストール環境は、常駐する4つのプロセス、それらが依存するいくつかのサービス、そして手で実行する1つのコマンドラインツールでできています。このページでは、1つのテナントにサービスを提供する最小のインストール環境を説明します。テナントの公開サイトと管理画面を提供し、プラットフォーム管理画面ではなく`publiractl`から管理する構成です。

## インストール環境が動かすもの

| プロセス | 提供するもの | アクセス元 |
| --- | --- | --- |
| `web-storefront` | すべてのテナントの公開サイト | エッジ（各テナントのドメイン） |
| `web-admin` | テナント管理画面 | エッジ（各テナントの管理画面ホスト。別のホストが与えられていなければ`admin.<domain>`） |
| `publira server` | `/rpc`配下のAPIと画像配信（1つのポート） | エッジ（`/rpc`配下の公開APIと`/images`）、`web-storefront`と`web-admin`（`/rpc`） |
| `publira worker` | メールとプッシュ通知の送信、キャッシュの再検証、すべての定期ジョブ | なし。ヘルスチェックに応答するだけです |

どのプロセスも`GET /livez`と`GET /readyz`に応答するので、オーケストレーターがプロセスを監視できます。Webアプリは1つのイメージから、`publira server`と`publira worker`は別のイメージからビルドされます。それらは[イメージのビルド手順](https://github.com/publira/publira/blob/main/infra/docker/README.md)に一覧があります。

1台のホストで動かし、サーバーやワーカーを複数動かすことのないインストール環境では、両者を1つのプロセスとして動かせます。`publira server --with-worker`は、両方のプロセスが行うことをすべて同じ2つのポートで行い、両方の変数を読みます。その代わりに2つのことを諦めることになります。サーバーとワーカーを別々にスケールさせられなくなります。また、インターネットに面したプロセスがワーカーの3つのデータベースログインも保持することになり、その中にはジョブキューのテーブルを所有し、自らテーブルを作成できるログインも含まれます。[Docker Compose](./3-docker-compose.md)のインストール環境は両者を1つのプロセスとして動かします。別々にスケールさせたい場合や、ワーカーのログインをインターネットに面したプロセスから切り離したい場合など、そのどちらかが重要なときは、2つを分けて動かしてください。

`publira server`は1つのポートで待ち受けるため、Cloud Runのようにサービスごとに1つのポートを公開するプラットフォームでは、そのまま1つのサービスとして動かせます。また、ロードバランサーの背後に`--role storefront`を付けた2つ目の`publira server`サービスを動かし、テナントのドメインと、公開APIだけを呼び出す`web-storefront`をそちらに振り向けることもできます。このロールのプロセスは公開APIとテナントのサイトの画像だけを提供します。こうすると、読者にサービスを提供するプロセスは、リクエストごとに1つのテナントに限定されたストアフロントのログインとしてのみデータベースにログインし、どちらの管理画面のログインも、Webアプリが管理画面のAPIを呼び出すときの認証情報も保持しません。1つ目のサービスは引き続き`web-admin`、`web-platform`、管理画面のホストにサービスを提供します。各ロールが提供するものと読む変数は、[デプロイのリファレンス](https://github.com/publira/publira/blob/main/infra/deploy/README.md#long-lived-processes)に一覧があります。

画像配信と公開APIは、それぞれ専用のホスト名と専用のロードバランサーで分けて提供することもできます。テナントのサイトの画像はテナントに与えた画像ホストで、公開APIはWebアプリとモバイルアプリの接続先にしたホストで提供します。どちらも`--role storefront`のプロセスなので、プロセスについては何も変わらず、変わるのはホスト名とその前のロードバランサーだけです。[画像と公開APIを分けて提供する](./7-scaling-out.md#画像と公開apiを分けて提供する)で説明しています。

どのプロセスも独自の状態を保持しません。インストール環境が保存するものはPostgreSQLとオブジェクトストレージに、プロセスが稼働中に共有するものはValkeyにあり、セッションはブラウザーが送り返すCookieです。そのため、どのプロセスも複数動かすことができ、エッジはリクエストをそれらに振り分けるためのスティッキーセッションを必要としません。[スケールアウト](./7-scaling-out.md)では、インストール環境の成長に合わせて何を増やすか、そしてその前に何を共有する必要があるかを説明しています。

## 依存するサービス

| サービス | 利用するもの | 保持するもの |
| --- | --- | --- |
| エッジ：ロードバランサー、リバースプロキシ、またはそれらの前に置くCDN | ブラウザーとモバイルアプリ | 各ホストとパスを適切なプロセスに送るルーティングと、TLS |
| PostgreSQL | すべてのプロセス | インストール環境が保存するすべてのもの |
| Valkey、またはRedisプロトコルを話す任意のサーバー | `publira server`、`web-storefront`、`web-admin` | 画像変換のキャッシュ、レート制限のカウンター、Webアプリの共有キャッシュ |
| S3互換のオブジェクトストレージ | `publira server`、`publira worker` | アップロードされたすべての画像 |
| SMTPサーバー | `publira worker` | なし。読者の会員登録やパスワードの再設定など、インストール環境が送るメールを配送します |

データベースとバケットはあなたが作成し、その中身はすべてPubliraが作成します。エッジは、マネージドのロードバランサーや自分で運用するプロキシなど、プラットフォームがプロセスの前に用意するものなら何でもかまいません。どれを使う場合でも、それが行うべきことは[エッジ](./4-edge/index.md#エッジが行うべきこと)に書かれています。リポジトリにあるTraefik、nginx、Caddyのサンプル設定は、それを実現する方法の1つです。

## 手で実行するコマンド

`publiractl`は、リリースのたびにデータベースのマイグレーションとロールを適用し、新しいインストール環境をセットアップし、その後のプラットフォームの設定を変更します。タイマーで実行する必要はありません。`publira worker`が繰り返し実行するジョブをすべて自分でスケジュールします。

## 追加できるプロセス

| プロセス | 追加されるもの |
| --- | --- |
| `email-renderer` | すべてのメールのHTMLパート。これがない場合、同じメールがプレーンテキストで送られます |
| `web-platform` | プラットフォーム管理画面。オペレーターは`publiractl`ではなくブラウザーからテナントとプラットフォームの設定を管理できます |
