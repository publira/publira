インストール環境がリクエストなしに行うことは、すべて`publira worker`が行います。現在時刻に予約されたエピソードの公開、変更によって古くなったキャッシュ済みページのWebアプリへの通知、メールとプッシュ通知の送信、統計とランキングの再構築、保持期間を過ぎたものの削除です。ほかにタイマーで動かす必要のあるものはなく、ホストのcronもKubernetesのCronJobも必要ありません。このページでは、何がいつ動くか、ある症状の背後にどのジョブがあるかを見分ける方法、そして`publiractl job`でジョブを手で実行する方法を説明します。

各ジョブの実行間隔、それを調整する変数、ジョブの一覧は、[`publira worker`のリファレンス](https://github.com/publira/publira/blob/main/server/cmd/publira/README.md#publira-worker)と[`publiractl job`のリファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#job)にあります。このページでは繰り返しません。

## 症状の背後にあるジョブ

目にしている症状から始めて、それを受け持つジョブを確認してください。

| 目にしている症状 | ジョブ | 確認する場所 |
| --- | --- | --- |
| エピソードが予定時刻を過ぎても**予約済み**のまま | 予約公開 | [予約公開](#予約公開) |
| エピソードのサイト上のページが、無料公開期間中なのに有料と表示している、または期間が終わったのに無料と表示している | 無料公開期間 | [無料公開期間](#無料公開期間とその他のキャッシュ済みページ) |
| ストアフロントの曜日別の更新作品が、昨日を今日として表示したまま | テナントの日付の切り替え | [無料公開期間](#無料公開期間とその他のキャッシュ済みページ) |
| サイトのバナーが**掲出を終える日時**を過ぎても表示されたまま | バナーに掲出するお知らせ | [無料公開期間](#無料公開期間とその他のキャッシュ済みページ) |
| シリーズが**公開日時**を過ぎても、サイトの一覧に表示されない | 公開予約されたシリーズ | [無料公開期間](#無料公開期間とその他のキャッシュ済みページ) |
| キャンペーンバナーが、掲載期間が始まってもサイトに表示されない、または期間が終わっても表示されたまま | キャンペーンバナー | [無料公開期間](#無料公開期間とその他のキャッシュ済みページ) |
| エピソードのサイト上のページが、キャンペーン価格が始まっても通常価格を表示している、または終わってもキャンペーン価格を表示している | キャンペーン価格 | [無料公開期間](#無料公開期間とその他のキャッシュ済みページ) |
| 読者のコイン履歴に、使われないまま失効したコインが表示されない | コインの失効 | [その他の定期ジョブ](#その他の定期ジョブ) |
| シリーズの公開後に無料のルールによって無料になる日を過ぎても、エピソードが有料のまま | 公開後に無料 | [その他の定期ジョブ](#その他の定期ジョブ) |
| ページが、変更前の内容を表示し続ける | アウトボックス内のキャッシュの再検証 | [アウトボックス](#アウトボックスメールプッシュ通知キャッシュの再検証) |
| メールやプッシュ通知が届かない | アウトボックス | [アウトボックス](#アウトボックスメールプッシュ通知キャッシュの再検証) |
| ランキング、シリーズの評価、おすすめが更新されなくなる | 統計とランキングの連鎖 | [統計とランキング](#統計とランキング) |
| テナントの締め日に月が締められない | 印税の締め | [その他の定期ジョブ](#その他の定期ジョブ) |
| Google Playで購入されたエピソードが、返金後も読めるまま | Google Playの返金の同期 | [その他の定期ジョブ](#その他の定期ジョブ) |
| 新しく保存した検索エンジンに検索が移らない | 検索インデックスの構築 | [検索](./7-search.md#構築が失敗したとき) |
| 古いレコードが削除されない | パージ | [その他の定期ジョブ](#その他の定期ジョブ) |

どのジョブも、まず`publira worker`が動いていて準備ができている必要があります。ワーカーが止まっているインストール環境はすべてのページを提供しますが、何も公開せず、何も送らず、何も再構築しません。ワーカーの`GET /readyz`は、ワーカーがログインする各データベースログインについてチェックを1つずつ示すので、応答しなくなったログインはそこに名前が出ます。ワーカーをキューごとに分けているインストール環境では、各ジョブには、そのジョブのキューを受け持つワーカーが動いていることも必要です。[一部のジョブを受け持つワーカー](#一部のジョブを受け持つワーカー)で説明しています。

### ジョブの失敗が記録される場所

ワーカーはすべての失敗をログに書き、そのログ行にはジョブの名前が出ます。定期ジョブの各実行は、ワーカーが自身の処理をキューに入れるデータベースの`river_job`テーブルにも行を残すので、このテーブルを見れば、ジョブがそもそも実行されたか、いつ実行されたかがわかります。

その行が失敗について何を示すかは、ジョブによって異なります。公開、無料公開期間、日付の切り替え、バナーに掲出するお知らせ、公開予約されたシリーズ、キャンペーンバナー、キャンペーン価格、コインの失効、公開後に無料の各ジョブは、途中で何かが失敗しても実行を最後まで終えます。それぞれ終えられなかったものをログに書き、1分後の次の実行に回すため、行は完了として記録され、失敗はログにしか残りません。それ以外のジョブは失敗した実行をその行に記録し、すべての試行のエラーを`errors`カラムに残します。エラーには、止まったテナントと日付が示されます。データベースの[管理用ログイン](../2-deployments/2-installing.md#サービスを用意する)で接続した`psql`で照会してください。

```sql
SELECT kind, state, attempt, finalized_at, errors
FROM river_job
WHERE state IN ('retryable', 'discarded')
ORDER BY id DESC
LIMIT 20;
```

`retryable`は次の試行を待っている実行、`discarded`は試行回数を使い切った実行です。完了した行やキャンセルされた行は1日後に、破棄された行は1週間後に削除されるので、症状が出たらすぐに確認してください。アウトボックスは独自の記録を持っており、[後述](#断念されたものを確認する)します。

## 予約公開

スタッフが予約したエピソードは、その時刻を過ぎるとワーカーが公開します。あわせて、シリーズのフォロワーへの通知と、そのエピソードを公開予定として掲載していたキャッシュ済みページの破棄も行います。ワーカーは公開時刻を迎えたエピソードを毎分探すので、エピソードは予定時刻からおよそ1分以内に公開されます。

公開に失敗すると、同じ実行の中で何度か再試行されます。すべての試行が失敗すると、エピソードは**予約済み**のまま残り、ワーカーは「エピソードの公開に失敗しました」という通知を、テナントの管理者向けにはテナント管理画面に、すべてのオペレーター向けにはプラットフォーム管理画面の**通知**に書き込みます。この通知は、エピソードごとに1回だけ書き込まれます。ワーカーはその後の実行のたびにそのエピソードを再試行するので、原因（失敗していたデータベース、実行されていなかったマイグレーションなど）が直れば、エピソードは自動的に公開されます。スタッフはそれを待つ必要はありません。テナント管理画面のエピソードのページで、**公開設定**に現在時刻を入力すると、ワーカーを介さずにそのリクエストの中でエピソードが公開されます。その場合も、フォロワーへの通知は[アウトボックス](#アウトボックスメールプッシュ通知キャッシュの再検証)を通じてワーカーが行います。

![プラットフォーム管理画面の通知。「エピソードの公開に失敗しました」という未読の通知が、エピソード、そのシリーズ、そのテナントの名前とともに表示され、「既読にする」と「すべて既読にする」がある。](./scheduled-jobs-notifications.png)

## 無料公開期間とその他のキャッシュ済みページ

6つのジョブが、過ぎた時刻の境目に合わせてWebアプリのキャッシュ済みページを正しい状態に保ちます。

- **無料公開期間。** **無料公開期間**の範囲内にあるエピソードは、期間が始まった瞬間から無料として読まれ、期間が終わると再び有料になります。これにはジョブは関わりません。読み込みのたびに、期間と現在時刻を比較するからです。このジョブが直すのは、境目より前にサイトがキャッシュしたページで、各期間の始まりと終わりの両方でそれらを古いものとしてマークします。
- **テナントの日付の切り替え。** 各テナントのタイムゾーンでの午前0時に、ストアフロントの曜日別の更新作品を古いものとしてマークします。テナントの暦日によって内容が決まる唯一のページです。
- **バナーに掲出するお知らせ。** お知らせの**掲出を終える日時**を過ぎると、そのお知らせをバナーから外し、バナーを古いものとしてマークします。
- **公開予約されたシリーズ。** 未来の**公開日時**を指定して保存したシリーズは、その時刻から公開されます。これにはジョブは関わりません。読み込みのたびに、その時刻と現在時刻を比較するからです。このジョブが直すのは、シリーズがまだ非公開だった間にサイトがキャッシュしたシリーズ一覧、著者ページ、そのシリーズ自身のページで、時刻を過ぎるとそれらを古いものとしてマークします。同じ実行の中で、シリーズが非公開だった間に公開されたエピソードの公開日をその時刻に揃え、それらのお知らせを[アウトボックス](#アウトボックスメールプッシュ通知キャッシュの再検証)に渡します。
- **キャンペーンバナー。** 公開済みのキャンペーンバナーは、掲載期間の始まりから終わりまで表示されます。これにはジョブは関わりません。読み込みのたびに、掲載期間と現在時刻を比較するからです。このジョブが直すのは、境目より前にサイトがキャッシュしたバナーで、公開済みの各バナーの掲載期間の始まりと終わりの両方でそれらを古いものとしてマークします。
- **キャンペーン価格。** キャンペーン価格の対象になっているエピソードは、キャンペーンの始まりから終わりまで、その価格で表示され、その価格で請求されます。これにはジョブは関わりません。読み込みと購入手続きのたびに、キャンペーンと現在時刻を比較するからです。このジョブが直すのは、境目より前にサイトがキャッシュしたエピソードのページとシリーズのページで、各キャンペーンの始まりと終わりの両方でそれらを古いものとしてマークします。

いずれも毎分実行されます。どのジョブも自分でキャッシュを破棄するわけではありません。それぞれ破棄をアウトボックスのエントリーとして記録し、ワーカーがそれをWebアプリに送ります。そのため、ワーカーに`PUBLIRA_REVALIDATE_TOKEN`があるのにページが古いままなら、それはアウトボックスの問題です。[後述](#アウトボックスメールプッシュ通知キャッシュの再検証)します。

`PUBLIRA_REVALIDATE_TOKEN`なしで起動したワーカーでは、キャッシュの再検証が無効になります。その場合、これらのジョブは破棄をまったく記録しませんが、それでも各境目と各シリーズの時刻を過ぎたものとして扱い、各バナーを取り下げます。そのため、アウトボックスには再試行するものがなく、トークンを付けてワーカーを再起動しても、それらの破棄は戻ってきません。破棄されるはずだったページは、同じものへの次の変更によって破棄されるか、キャッシュの期限が切れるまで、キャッシュした内容を表示し続けます。時刻どおりに処理したい最初の境目より前に、[インストール](../2-deployments/2-installing.md#シークレットを生成する)で説明しているとおり、`publira server`と`publira worker`にトークンを設定してください。

これらのジョブには`publiractl job`のコマンドがなく、必要もありません。どのジョブも、実行されるたびに、過ぎたすべての時刻について処理を行うからです。ワーカーの起動後の最初の実行も同じです。

## 統計とランキング

統計、ランキング、シリーズの評価、おすすめは、テナント自身のタイムゾーンで1日が終わるたびに、閲覧のアクティビティから構築されます。4つのジョブが、1つの連鎖として順番にこれを行います。

1. **閲覧の投影**（`project-episode-reads`）は、完了したすべての閲覧を分析イベントとして記録します。
2. **日次統計**（`aggregate-content-stats`）は、終わった各日の閲覧数、読了数、購入数、評価、お気に入り、コメントをシリーズとエピソードごとに再構築し、読者が各エピソードのどこまで読んだかも再構築します。ストアフロントが表示するシリーズの評価は、これらから計算されます。また、ログインしている読者のうち誰がその日にエピソードを閲覧、読了、購入したか、それがどのシリーズだったかも記録します。管理画面は、ある週に会員登録した読者をこの記録によって追跡します。これらの記録を導入したリリースへのアップグレードでは、分析イベントがまだ保持されていたすべての日についてこれらを記録しました。その時点ですでにパージされていた日には記録がなく、あとから記録することもできません。
3. **ランキング**（`aggregate-rankings`）は、ストアフロントの**ランキング**ページが表示する日間と週間のランキングを再構築します。
4. **おすすめ**（`build-recommend-features`）は、各読者へのおすすめの元になるスナップショットを再構築します。

連鎖は毎時開始され、各段階は終わると次の段階を開始します。テナントごとに午前0時になる時刻が異なるため、テナントの1日は、終わってからおよそ1時間以内に、連鎖にかかる時間を加えた時間で再構築されます。そのため、テナントの午前0時から数時間たってもランキングが更新されていないのは正常ですが、1日更新されていないのは正常ではありません。

ワーカーは、テナントごとに各段階が最後に終えた日を覚えていて、その翌日から始めます。ある日が失敗すると、そのテナントはそこで止まりますが、ほかのテナントは続行します。エラーは失敗した段階の`river_job`の行にあり、実行は最大3回試行され、次の毎時の実行は失敗した日からやり直します。原因が直れば、そのテナントは逃したすべての日を順番に処理して、自動的に遅れを取り戻します。

## その他の定期ジョブ

| ジョブ | 頻度 | 行うこと |
| --- | --- | --- |
| 公開後に無料 | 毎分 | シリーズの公開後に無料のルールが及んだ、公開済みで有料の各エピソードに無料公開期間を追加します。及んだとは、エピソードの公開から設定された日数が過ぎ、かつルールが有料のまま残す最新のエピソードに含まれないことです。期間はその日から、またはその時点でまだ続いている手で設定した期間があればその終わりから始まり、その期間が削除されるとその日に戻ります。期間は、ルールがそのエピソードを対象にしなくなるまで続きます。ルールを無効にして保存したり、そのエピソードが外れる数値で保存したりすると、期間はすぐに取り除かれます。それ以外の理由でルールから外れたエピソード（最新のエピソードの中に移ったもの、公開を取り下げたものなど）からは、次の実行で取り除かれます。始まったり終わったりする期間と同じく、エピソードのページは同じ実行の中で古いものとしてマークされます。キャッシュ済みページを時刻どおりに保つジョブと同じく、`publiractl job`のコマンドはありません |
| コインの失効 | 毎分 | 未使用のコインを残したまま失効したコインの付与ごとに、読者のコイン履歴にエントリーを書き込み、コインの行方が履歴でわかるようにします。コインは失効した瞬間に残高に数えられなくなります。これにはジョブは関わらず、コインが戻ることもありません。キャッシュ済みページを時刻どおりに保つジョブと同じく、`publiractl job`のコマンドはありません |
| 印税の締め（`close-royalty-statements`） | 毎時 | **自動で締める**に設定したテナントについて、テナントの締め日が来たら、締めるべき各月を締めます。手で、または以前の実行によってすでに締められた月は、そのままにします |
| Google Playの返金の同期（`sync-google-play-voided-purchases`） | 毎時 | Google Playストアが有効なすべてのテナントについて、過去30日間にGoogle Playが返金した購入を読み取り、[エピソードの販売](../4-console/4-selling-episodes.md#返金)で説明しているとおりに取り消します |
| 検索インデックスの構築（`build-search-index`） | 30秒ごと | 新しく保存した検索エンジンにインデックスを構築し、検索をそちらに移します。[検索](./7-search.md#別のエンジンに移る)で説明しています |
| パージ（`purge-*`） | 毎時または24時間ごと | 保持期間を過ぎた、取り下げられたコメント、分析イベント、ランキングのスナップショットを削除します（[プラットフォームの既定値とポリシー](./9-platform-policies.md#保持期間)で説明しています）。また、2段階認証によるログインで使い終わったチャレンジと、どのテナントでも使われなくなってから1日たった画像も削除します |

## 一部のジョブを受け持つワーカー

`--queue`を付けて起動したワーカーは、指定したキューのジョブを実行し、それ以外は、それらを指定したワーカーに任せます。[キューごとにワーカーを分ける](../2-deployments/7-scaling-out.md#キューごとにワーカーを分ける)で説明しています。このページのジョブは4つのキューにあり、`river_job`も同じ名前で示します。ただし`outbox`だけは`default`と示します。

| キュー | ジョブ |
| --- | --- |
| `outbox` | [アウトボックス](#アウトボックスメールプッシュ通知キャッシュの再検証)：メール、プッシュ通知、キャッシュの再検証、検索エンジンのインデックスの更新 |
| `ticker` | 予約公開、無料公開期間、テナントの日付の切り替え、バナーに掲出するお知らせ、公開予約されたシリーズ、キャンペーンバナー、キャンペーン価格、コインの失効、公開後に無料 |
| `maintenance` | 統計とランキングの連鎖、印税の締め、Google Playの返金の同期、パージ |
| `search_index` | 検索インデックスの構築 |

どのキューにも、それを受け持つワーカーが少なくとも1つ動いている必要があります。ジョブをスケジュールするワーカーは、自分が受け持つキューにかかわらず、すべてのジョブをスケジュールします。そのため、動いているどのワーカーもキューを受け持っていないジョブは失われはしませんが、何もそれを実行しません。そのジョブは、そのキューを受け持つワーカーが起動するまで`river_job`で待ち、起動すると[停止後](#停止後)と同じように実行されます。各ワーカーは起動時に、ほかに任せるキューを`worker leaves queues to other replicas`としてログに書き、`not_hosted`にその名前を示します。ジョブが待っているキューは`river_job`でわかります。

```sql
SELECT queue, kind, count(*), min(scheduled_at)
FROM river_job
WHERE state = 'available' AND scheduled_at < now() - interval '5 minutes'
GROUP BY queue, kind;
```

ここに出る行は、実行時刻から5分たってもどのワーカーも取り上げていないジョブです。その`queue`を受け持つワーカーを起動するか、動いているワーカーの`--queue`にそのキューを加えてください。

## 停止後

止まっていたワーカー、または正常に動くデータベースなしで動いていたワーカーは、その間何もせず、処理は失われずにデータベースで待ちます。再び起動すると、次のようになります。

| ジョブ | 起動時 |
| --- | --- |
| アウトボックス | 待っていたすべてのエントリーを送ります。止まったワーカーが処理の途中だったエントリーは、15分後に再び取り上げられます |
| 予約公開 | 時刻を過ぎたすべてのエピソードを公開し、そのフォロワーに通知します |
| 無料公開期間、テナントの日付の切り替え、バナーに掲出するお知らせ、公開予約されたシリーズ | その間に境目を過ぎたすべてのページを古いものとしてマークし、時刻を過ぎたすべてのバナーを取り下げます |
| 公開後に無料 | その間にその日を過ぎたすべてのエピソードを、その日から無料にします |
| 統計とランキングの連鎖 | 各テナントが逃したすべての日を順番に再構築します。ただし、分析イベントがすでに保持期間を過ぎた日や、以前に保存したより短い保持期間でパージされた日は除きます。それらの日は欠けているものとしてログに書かれてスキップされ、再構築できません |
| 印税の締め | 締めるべきになったすべての月を締めます |
| 検索インデックスの構築 | 保留中のインデックスを構築します |
| パージ | 現在の時間帯または日に、まだ1回も完了していない場合にだけ実行されます。これはワーカーの起動時からではなく、時計で数えます。その最初の実行で、その間に期限切れになったものをすべて削除します |
| Google Playの返金の同期 | パージと同じく、現在の時間帯にまだ1回も完了していない場合にだけ実行されます。30日より長く止まっていたワーカーは、Google Playがもう一覧に載せていない返金を取りこぼします |

この待ち間隔があるので、再起動やデプロイのたびに、すべてのテーブルとバケット全体を総なめにすることになりません。

## アウトボックス：メール、プッシュ通知、キャッシュの再検証

リクエストがあとに残す副作用（メール、プッシュ通知、キャッシュ済みページの破棄、検索エンジンのインデックスの更新）は、すべて、それを引き起こした変更と同じトランザクションでアウトボックスに書き込まれます。そのため、変更が副作用なしに保存されることはなく、ワーカーは数秒以内にそのエントリーを送ります。

失敗したエントリーは再試行され、失敗するたびに待ち時間が2倍になります。1秒、2秒、4秒と続きます。10回目の試行が失敗すると（最初の試行からおよそ9分後）、そのエントリーは完全に断念されます。エントリーは**dead**になり、二度と送られません。削除されたアカウント宛てのメールのように、決して成功しないエントリーはすぐに断念されます。ワーカーが知らない種類のエントリーは、失敗したわけではありません。アップグレード中であれば、それは新しいリリースだけが書き込むエントリーなので、ワーカーはそれを新しいリリースのワーカーに任せ、毎分見直し、書き込まれてから1日たって初めて断念します。何を失敗とみなすかは、エントリーによって異なります。

- **メール**は、SMTPサーバー、または有効にしている場合は`email-renderer`が、拒否しているか到達できない間は失敗します。[メール](./6-email.md#インストール環境が送るメール)で説明しています。
- スマートフォンへの**プッシュ通知**は、テナントがFirebaseの認証情報を保存していない間は、失敗ではなくスキップされるため、あとから認証情報を保存しても再試行されません。ブラウザー通知は、Web Pushを有効にして初めて送られます。[Web Push](./8-web-push.md)で説明しています。
- **キャッシュの再検証**は、Webアプリが停止している間は失敗します。`PUBLIRA_REVALIDATE_TOKEN`がないワーカーは、`publira server`や`publiractl`が記録したすべての破棄を、すべての試行で失敗させます。ワーカー自身のジョブの破棄は、そもそも記録しません。[無料公開期間](#無料公開期間とその他のキャッシュ済みページ)で説明しています。

`publira worker`の`PUBLIRA_OUTBOX_MAX_ATTEMPTS`で試行回数を設定します。待ち時間は試行の間隔が最大1時間になるまで2倍になり続けるので、試行回数を少し増やすだけで、エントリーはずっと長い障害を乗り切れるようになります。

### 断念されたものを確認する

ワーカーは、断念した各エントリーを`outbox event dead`としてログに書き、メトリクスを有効にしている場合は`publira.outbox.events.dead`メトリクスでも数えます。[モニタリング](./11-monitoring.md#アウトボックス)で説明しています。どちらかでアラートを出してください。エントリー自体は、最後のエラーとともに`outbox_events`テーブルに残ります。

```sql
SELECT event_type, tenant_id, attempts, last_error, updated_at
FROM outbox_events
WHERE status = 'dead'
ORDER BY updated_at DESC
LIMIT 20;
```

deadのエントリーは再送できません。何が失われるかは、その`event_type`によって異なります。

- **メール**は届きません。読者はパスワードの再設定や確認メールを改めて依頼し、管理者の招待は再送します。[テナントのスタッフ](./3-tenant-staff.md)で説明しています。
- **プッシュ通知**は届きません。通知は、サイトとアプリの読者の一覧には残ります。
- **キャッシュの再検証**は、対象のページに、同じものへの次の変更によって再び破棄されるか、キャッシュの期限が切れるまで、以前の内容を表示させ続けます。

## ジョブを手で実行する

`publiractl job <job>`は、メンテナンスジョブを1回実行して終了します。ワーカーのスケジュールされた実行と同じコードを実行するもので、その複製ではないため、スケジュールされた実行と同じように動きます。スケジュールでは行わないことのためのコマンドです。

- **バックフィル**：連鎖がすでに通り過ぎた、指定した日の統計を再構築します。
- **ドライラン**：パージが削除する前に、削除する対象を数えます。
- **変更をすぐに適用する**：保存したばかりの短い保持期間によるパージを、次の日次の実行ではなく今すぐ行います。
- **デバッグ**：失敗する実行を、そのログを見ながら調べます。

インストール環境が動かしているリリースのイメージで、`PUBLIRA_CONTENT_STATS_DB_URL`に`publira_content_stats`の接続を設定して実行してください。

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job purge-content-events
```

[Docker Compose](../2-deployments/3-docker-compose.md)のインストール環境では、`docker compose run --rm publiractl job purge-content-events`にすでに接続が設定されています。画像のパージ、Google Playの返金の同期、検索インデックスの構築は、使う認証情報がインストール環境に保存されている場合（バケットのアクセスキー、テナントのGoogle Playサービスアカウントキー、検索エンジンのパスワードがそうです）、`PUBLIRA_SECRET_ENCRYPTION_KEYS`と`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`も必要です。

ジョブは標準出力にログを書き、実行が失敗すると`1`で終了します。テナントを1つずつ処理するジョブは、終了する前にほかのテナントを処理し終え、そのログには失敗した各テナントの名前が出ます。

### ドライラン

どのパージにも、削除する代わりに数えるようにする変数があります。たとえば`purge-content-events`では`PUBLIRA_CONTENT_EVENTS_PURGE_DRY_RUN=true`です。各パージの変数名はそのリファレンスにあります。数はログに出ます。

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  -e PUBLIRA_CONTENT_EVENTS_PURGE_DRY_RUN=true \
  publira/publiractl:<tag> job purge-content-events
```

パージは開始時に保持期間を読むので、ドライランは、今保存されている期間で削除されるものを数えます。ずっと短い期間を保存したら、本番の実行の前にドライランを実行して、パージがどれだけ削除するかを確認してください。`purge-orphan-images`のドライランは、バケット内のオブジェクトのうち、どの画像の行も指しておらず、1日以上たっているものを報告します。[リストア](../2-deployments/9-backup-and-restore.md#ワーカーが追いつく処理)のあとでは、バックアップを取ったあとにアップロードされた画像もそこに含まれます。

### ある日の統計を再構築する

連鎖は、一度終えた日を二度と処理し直さないので、あとからその元になったデータが修正されても、その日の統計は再構築されません。そのような修正のあとや、リリースノートで求められたときに再構築するには、4つの段階を順番に実行し、テナント自身の暦で日を指定してください。

```bash
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job project-episode-reads
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  -e PUBLIRA_CONTENT_STATS_DATE=2026-10-01 \
  publira/publiractl:<tag> job aggregate-content-stats
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job aggregate-rankings
docker run --rm -e PUBLIRA_CONTENT_STATS_DB_URL \
  publira/publiractl:<tag> job build-recommend-features
```

1回の実行で、すべてのテナントについてその日を再構築します。ここではランキングとおすすめは各テナントの昨日について再構築されます。ストアフロントは最新のランキングしか表示せず、昨日で終わる週間ランキングは直近7日間を対象にするからです。古いランキングを再構築するときに限り、`PUBLIRA_CONTENT_RANKING_DATE`と`PUBLIRA_RECOMMEND_FEATURES_DATE`で日付を指定してください。

コンテンツイベントの保持期間がもうその日を含まないテナントは、ワーカーがそのような日をスキップするのと同じように、実行から除外されます。そのテナントのその日の分析イベントはすでになくなっているので、残っているものから再構築するのではなく、統計をそのまま残します。パージがその日を削除したあとに期間を延ばしたテナントも同じです。期間を延ばしても、削除されたイベントは戻りません。実行は、そのような各テナントをスキップしたものとしてログに書き、ほかのすべてのテナントについてはその日を再構築します。

手での実行は、各テナントがどこまで進んだかというワーカーの記録を動かさないので、それによってワーカーが日を飛ばしたり繰り返したりすることはありません。

### 繰り返し実行しても安全なジョブ

どのジョブも、もう一度実行することができ、ワーカー自身の実行と並行して実行することもできます。

| ジョブ | もう一度実行したとき |
| --- | --- |
| `project-episode-reads` | すべての閲覧が記録済みなら、何も書き込みません |
| `aggregate-content-stats`、`aggregate-rankings`、`build-recommend-features` | 構築したものを同じ結果で置き換えます。同じテナントと日について同じジョブを2回実行すると、互いに待ち合わせ、両方が書き込むのではなく、2回目が30秒後に失敗します |
| すべての`purge-*` | 削除するものが残っていません |
| `close-royalty-statements` | 締めるべきすべての月がすでに締められています。最初の実行で実際に締めるのは、次のスケジュールされた実行が締めるはずの月だけです。つまり、**自動で締める**に設定したテナントのうち、締め日が来たテナントの月です |
| `sync-google-play-voided-purchases` | 同じものを二度取り消すことはありません |
| `build-search-index` | 構築の予定がないとき、またはワーカーがすでに構築しているときは何もしません |

唯一の例外はタイミングです。[バックアップと復元](../2-deployments/9-backup-and-restore.md#1-ワーカーを停止する)で説明しているとおり、バケットのバックアップをコピーしている間は`purge-orphan-images`を実行しないでください。

公開、無料公開期間、日付の切り替え、バナーに掲出するお知らせの各ジョブには、専用のコマンドがありません。これらを動かすには、ワーカーを動かしてください。
