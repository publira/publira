各テナントのサイトの検索は、すべてのテナントが共有する1つのエンジンでシリーズ、著者、レーベルを探します。インストールは最初データベースそのもので検索するので、ほかに用意するものはありません。結果を関連度順に並べたいインストールでは、OpenSearchかElasticsearchも選べます。このページでは、エンジンの違いと、別のエンジンへの切り替え方、エンジンが持つインデックスを説明します。

このページの`publiractl`コマンドは、コマンドの部分だけを示しています。[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明に従い、`PUBLIRA_PLATFORM_DB_URL`に`publira_platform`の接続先を設定して実行してください。`PUBLIRA_SECRET_ENCRYPTION_KEYS`と`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`には、各プロセスと同じ値を設定します。フラグの一覧は[`publiractl`のリファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#search)にあります。

## エンジンを選ぶ

| エンジン | `--engine` | 検索のしかた | 必要なもの |
| --- | --- | --- | --- |
| **PostgreSQL** | `sql` | 入力した文字列を含むタイトルや名前を見つけ、タイトル順か名前順に並べます | なし(インストールがすでに使っているデータベースです) |
| **OpenSearch** | `opensearch` | 結果を関連度順に並べます。ラテン文字の単語は1文字打ち間違えても見つけ、漢字、かな、ハングルで書かれたタイトルはその一部から見つけます。[独自のテキスト解析](#言語ごとにプラグインを使う)を設定した言語はその解析のとおりに検索するので、たとえば漢字で書かれた日本語のタイトルを、かなで入力した読みから見つけられます | OpenSearchのクラスター |
| **Elasticsearch** | `elasticsearch` | OpenSearchと同じように検索します | Elasticsearchのクラスター |

どのエンジンが結果を見つけても、ストアフロントが各結果について表示する内容はデータベースから読みます。そのため、エンジンへの反映が遅れていても、シリーズのタイトルや価格、表紙が古いまま表示されることはありません。絞り込みと並べ替えも、どのエンジンで同じようにできます。

どのエンジンも、シリーズは読者の言語で表示されるタイトルとあらすじから探します。英語で閲覧している読者は英語のタイトルでシリーズを見つけられますが、日本語のタイトルにしかない単語では見つけられません。英語のタイトルがないシリーズは、代わりに表示されるサイトの既定言語のタイトルで見つかります。著者とレーベルの名前はどの言語でも1つなので、読者の言語にかかわらずその名前で見つかります。

読者が検索より一覧から作品を探すことが多いカタログや、タイトルを正確に入力して探すカタログなら、PostgreSQLで十分です。読者が読みでタイトルを探したり綴りを間違えたりして、何も見つけられずにいるようなら、別のエンジンに切り替えてください。

## OpenSearchやElasticsearchを用意する

Publiraはエンジンを動かしません。自分で運用するクラスターかマネージドのクラスターを使い、次のものを用意してください。

### プラグイン

プラグインは必要なときにだけ入れます。既定のテキスト解析はOpenSearchとElasticsearchに標準で入っている機能だけで組まれているので、公式イメージのエンジンはそのままで使えます。プラグインが要るのは、プラグインを使った[独自のテキスト解析を設定する](#言語ごとにプラグインを使う)言語があるときだけです。

### URL

エンジンが応答する`http://`か`https://`のURLです。`publira server`、`publira worker`、`publiractl`のどれからも届く必要があります。

### ユーザー

エンジンが認証を求めるときは、ユーザーを用意します。PubliraはHTTPベーシック認証でログインし、認証情報は`https://`のURLにしか送りません。APIキーにも独自の認証局にも対応していないので、セキュリティを有効にしたエンジンには、サーバーがすでに信頼している証明書が必要です。ユーザーには、次に説明するインデックスのエイリアスで始まる名前のインデックスを作成、書き込み、削除する権限と、そのエイリアスを付け替える権限が必要です。

### インデックスのエイリアス

Publiraのインデックスの名前のもとになる名前で、指定しなければ`publira-catalog`です。Publiraは読者が選べる言語ごとに1つずつインデックスを持ち、それぞれにエイリアスの末尾に言語を付けた`publira-catalog-en`、`publira-catalog-ja`、`publira-catalog-zh-hans`のような名前のエイリアスを付けます。インデックスとエイリアスはPubliraが自分で作成します。1つのクラスターを複数のインストールで共有するときは、インストールごとに別のエイリアスを指定してください。2つのインストールが同じエイリアスを使うと、互いのカタログを上書きしてしまいます。

## エンジンをテストする

テストでは、エンジンにその種類と、すべてのノードに入っているプラグインを問い合わせ、製品名とバージョン、プラグインを表示します。エンジンが応答しないとき、認証情報を拒否されたとき、選んだものとは別の製品だったときは失敗します。プラグインの有無は結果を左右しません。既定のテキスト解析にはプラグインが要らず、独自の定義は保存するときにエンジンで確かめるからです。プラグインの一覧を取得するには、ほかでは使わないクラスター権限がユーザーに必要です。その権限のないユーザーでは、プラグインの一覧が空のままテストが成功します。

- プラットフォーム管理画面では、**検索**の**接続をテスト**が、保存する前のフォームの値をテストします。テストは`publira server`から実行されます。
- `publiractl search test`は、保存済みのエンジンを、`publiractl`を実行したマシンからテストします。テストに失敗すると、終了コード`1`で終了します。PostgreSQLではテストするものがないので、やはり`1`で終了します。

## 別のエンジンに切り替える

エンジンを保存しても、検索はすぐには新しいエンジンに切り替わりません。新しいエンジンのインデックスは空なので、まず`publira worker`がデータベースからインデックスを作り、すべてのテナントのカタログが入ったところで検索が切り替わります。それまでストアフロントは元のエンジンで答え続けるので、読者が空のインデックスを検索することはありません。

### プラットフォーム管理画面から

1. サイドバーの**外部サービス**にある**検索**を選びます。
2. **エンジン**で**OpenSearch**か**Elasticsearch**を選んで**URL**を入力し、エイリアスを決めたときは**インデックスのエイリアス(任意)**も入力します。
3. **認証**で**認証なし**を選ぶか、**ユーザー名とパスワード**を選んで両方を入力します。
4. **接続をテスト**を選び、成功したら**検索設定を保存**で保存します。

![OpenSearchを選んだ検索エンジンの設定。エンジン、URL、インデックスのエイリアス(任意)、認証、接続テスト、検索設定を保存ボタンがある。](./search-engine.png)

画面上部の**検索の状態**には、ストアフロントが今使っているエンジンと、インデックスを作っているあいだは切り替え先のエンジンが表示されます。画面は数秒ごとに状態を確かめ直すので、切り替わればすぐ表示に現れます。保存できるのはオペレーターとスーパー管理者で、監査担当は画面を閲覧できるだけです。

### publiractlから

```bash
publiractl search set \
  --engine opensearch \
  --url https://search.example.com:9200 \
  --username publira --password-file /run/secrets/search-password
publiractl search test
publiractl search show
```

`search set`は、保存済みの設定を、指定したフラグの値ですべて置き換えるので、毎回すべてを指定してください。`--username`を省略すると、保存済みのパスワードは削除されます。保存済みと同じ`--username`をパスワードなしで指定すると、保存済みのパスワードはそのまま残ります。`search show`は、検索が今使っているエンジンと、進行中のインデックスの作成や失敗した作成を表示します。

### かかる時間

ワーカーは30秒ごとに、作るべきインデックスがないか確かめます。インデックスを埋めるには、すべてのテナントの公開済みのシリーズ、著者、レーベルをエンジンが取り込み終えるまでの時間がかかります。そのあいだの変更も新しいインデックスに書き込まれるので、待っているあいだに失われるものはありません。

### インデックスの作成に失敗したとき

エンジンが止まった、保存済みの定義が使うプラグインがノードからなくなった、ユーザーにインデックスを作成する権限がない、といった理由でインデックスの作成に失敗しても、検索は元のエンジンのままです。エラーは**検索の状態**と`publiractl search show`に表示されます。ワーカーは30秒ごとに作成をやり直すので、エンジンを直せば、設定を保存し直さなくても作成は完了します。切り替えをやめるときは、検索が今使っているエンジンを保存し直してください。

![インデックスの作成に失敗したあとの検索の状態。PostgreSQLで検索していること、OpenSearchのインデックスを作成できなかったというメッセージ、最後に失敗した日時、エンジンのエラーが表示されている。最後に失敗した日時は試行のたびに変わるので、ここではグレーで表示している。](./search-build-failed.png)

### PostgreSQLに戻す

**PostgreSQL**を保存するか`publiractl search set --engine sql`を実行すると、検索はすぐにPostgreSQLに戻ります。データベースにはインデックスが要らないからです。エンジン上のインデックスはそのまま残るので、もう使わないなら自分で削除してください。

### 変更がすべてのプロセスに反映されるまで

`publira server`と`publira worker`は30秒ごとに設定を読み直すので、エンジンの切り替えは再起動しなくても1分以内にすべてのインスタンスに届きます。保存もテストも、そのたびに**監査ログ**に記録されます。

## テキスト解析

エンジンがタイトル、名前、あらすじを単語に分ける方法をテキスト解析といいます。テナントはインデックスを共有しているので、定義はすべてのテナントで1つです。各言語のインデックスは、その言語に独自の定義がない限り、この定義から作られます。

既定の定義はプラグインを使わず、どの言語にもひととおり対応します。ラテン文字のタイトルは単語で見つけ、1文字の打ち間違いを許します。漢字、かな、ハングルのタイトルは、その中の連続する2文字以上のどの部分からでも見つけます。大文字と小文字の違いや、英数字とかなの全角と半角の違いは無視します。言語についての知識はそれだけなので、たとえば漢字で書かれたタイトルを読みから見つけることはできません。それ以上が必要な言語には、その言語のプラグインを使った[独自の定義を設定](#言語ごとにプラグインを使う)できます。

定義はインデックスの`settings.analysis`オブジェクトで、64KiB以内のJSONで書きます。インデックスが参照する3つの名前として、アナライザーの`written_form`と`alternate_form`、ノーマライザーの`exact_match`を必ず定義します。それぞれの役割は[テキスト解析のリファレンス](https://github.com/publira/publira/blob/main/server/README.md#text-analysis)にあります。

- プラットフォーム管理画面では、**検索**の**テキスト解析**にある**共有**タブで、**定義(settings.analysis、JSON)**に定義を入力し、**テキスト解析を保存**で保存します。**既定に戻す**を選ぶと既定の定義に戻ります。PostgreSQLにはインデックスがないので、保存するテキスト解析もありません。
- `publiractl`では、`search set --analysis-file korean-analysis.json`でエンジンと一緒に定義を保存し、`--default-analysis`で既定の定義に戻します。どちらも指定しなければ、`search set`は保存済みの定義をそのまま残します。

ある言語をその言語のプラグインで検索するには、その言語に独自の定義を与えます。その言語のインデックスは独自の定義から、ほかの言語のインデックスは共有の定義から作られます。

- プラットフォーム管理画面の**テキスト解析**には、共有の定義のための**共有**タブと、言語ごとのタブがあります。**共有**タブには、共有の定義を使っている言語が表示されます。独自の定義がない言語のタブには、書き始めの土台として共有の定義が表示されます。そのタブで**テキスト解析を保存**を選ぶとエディターの内容がその言語独自の定義として保存され、**共有の定義を使う**を選ぶと独自の定義は破棄されて、その言語は再び共有の定義から作られます。
- `publiractl`では、`search set`で言語独自の定義を指定します。

```bash
publiractl search set --engine opensearch --url https://search.example.com --locale-analysis-file ja=japanese-analysis.json
```

`--locale-analysis-file`には、言語とファイルを`LOCALE=FILE`の形で指定します。`--shared-analysis-for ja`を指定すると、その言語は再び共有の定義から作られます。どちらも言語ごとに繰り返し指定できます。どちらにも指定しなかった言語は今の設定のままで、どちらも付けずに`search set`を実行すれば、すべての言語が今の設定のままです。指定できる言語は`ja`、`en`、`ko`、`zh-Hans`、`zh-Hant`です。独自の定義を持つ言語は、`publiractl search show`の**Own analysis**に表示されます。

![テキスト解析の画面。定義に含める3つの名前、共有の定義のタブと言語ごとのタブ、保存されている定義とそれを使っている言語、定義(settings.analysis、JSON)の入力欄、テキスト解析を保存ボタンがある。](./search-text-analysis.png)

定義を保存する前に、Publiraはその定義で空のインデックスを作るようエンジンに求めます。エンジンが受け付けなかった定義は保存されず、エンジンが返した理由と、言語独自の定義であればその言語が表示されます。保存した定義は、エンジンを切り替えたときと同じように、その定義で変わる言語の新しいインデックスに組み込まれ、作成が終わると検索はそのインデックスに切り替わります。ほかの言語のインデックスはそのままです。

### 言語ごとにプラグインを使う

どの言語も、独自の定義を与えるまでは共有の定義で検索されます。独自の定義を与えるかどうかは任意です。OpenSearchとElasticsearchは、どちらも多くの言語向けに解析プラグインを公開しています。日本語向けの`analysis-kuromoji`と`analysis-icu`は漢字で書かれたタイトルをかなで入力した読みと照らし合わせられ、ほかにも韓国語向けの`analysis-nori`、中国語向けの`analysis-smartcn`などがあります。こうしたプラグインを使った定義を与えると、その言語はプラグインの解析のとおりに検索されます。手順は次のとおりです。

1. ノードを停止した状態で、`bin/opensearch-plugin install`か`bin/elasticsearch-plugin install`をプラグインの名前を付けて実行し、すべてのノードにプラグインを入れます。リポジトリの[開発用のOpenSearchイメージ](https://github.com/publira/publira/blob/main/infra/docker/opensearch/Dockerfile)に、この手順をDockerfileで書いた例があります。入れたプラグインは、**接続をテスト**が表示する、すべてのノードにあるプラグインの一覧に現れます。
2. エンジンのプラグインのドキュメントに従い、プラグインのトークナイザーとフィルターを使って、上の3つの名前を定義した定義を書きます。
3. 書いた定義を、**テキスト解析**のその言語のタブか、`publiractl search set --locale-analysis-file`で保存します。

その言語のインデックスが新しい定義で作り直され、準備ができると、その言語の検索は新しいインデックスに切り替わります。その言語のタイトルがないシリーズは、代わりに表示されるタイトルでその言語のインデックスに入るので、そのタイトルにもその言語の解析が使われます。

## インデックスを再構築する

テナントが作品を公開したり、編集したり、既定言語を変えたりするたびに、ワーカーがインデックスを最新の状態に保ちます。エンジンやテキスト解析が変わったときや、リリースで読者が選べる言語や既定のテキスト解析が変わったときにも、ワーカーが新しいインデックスを作ります。そのため、手でインデックスを再構築する必要はめったにありません。ワーカーがインデックスを作っているあいだは、**検索の状態**と`publiractl search show`に作成中であることが表示され、ストアフロントは今あるインデックスで答え続けます。`publiractl search reindex`を使うのは、残る次の2つの場合です。

- リリースでインデックスが変わったとき。[リリースノート](../2-deployments/8-upgrading.md#リリースノートを読む)にカタログのインデックスが変わったとあれば、アップグレードが終わってから実行します。
- クラスターを置き換えたり、インデックスを削除したりして、インデックスが失われたとき。

```bash
publiractl search reindex
```

このコマンドは、言語ごとに今のインデックスとは別の新しいインデックスを作って、すべてのテナントのカタログを入れ、すべてのエイリアスを一度に新しいインデックスへ付け替えてから、古いインデックスを削除します。そのため、実行中もストアフロントの検索は止まりません。カタログは`publira_content_stats`ロールで読むので、このロールの接続先を`PUBLIRA_CONTENT_STATS_DB_URL`に設定してください。エンジンのパスワードを保存している場合は、暗号化キーも設定します。ワーカーがインデックスを作っているあいだは実行できず、作成中なら終了コード`1`で終了するので、作成が終わってから実行し直してください。PostgreSQLでは再構築するインデックスがないので、やはり`1`で終了します。

`publiractl search reindex --tenant comics.example.com`は、新しいインデックスを作らずに、検索が今使っているインデックスに1つのテナントのカタログを書き込み直します。特定のテナントの検索結果がおかしいときのためのもので、インデックスそのものへの変更は反映できません。
