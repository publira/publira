すべてのテナントのサイトの検索は、すべてのテナントで共有する1つのエンジンでシリーズ、著者、レーベルを探します。インストール環境は最初はデータベースそのものを使い、ほかに何も必要ありません。関連度順の検索結果が必要なインストール環境では、OpenSearchかElasticsearchを選べます。このページでは、エンジンを比較し、検索をあるエンジンから別のエンジンに移し、エンジンが保持するインデックスについて説明します。

このページの`publiractl`コマンドは、コマンド単体で示しています。[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明どおりに、`PUBLIRA_PLATFORM_DB_URL`に`publira_platform`の接続先を設定し、各プロセスと同じ`PUBLIRA_SECRET_ENCRYPTION_KEYS`と`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`を指定して実行してください。すべてのフラグは[`publiractl`リファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#search)にあります。

## エンジンを選ぶ

| エンジン | `--engine` | 検索の仕方 | 必要なもの |
| --- | --- | --- | --- |
| **PostgreSQL** | `sql` | 入力された文字列を含むタイトルや名前を、タイトル順または名前順で探します | なし。インストール環境がすでに持っているデータベースを使います |
| **OpenSearch** | `opensearch` | 結果を関連度順に並べ、ラテン文字で書かれた単語の1文字の打ち間違いを許容し、漢字、かな、ハングルで書かれたタイトルをその一部から見つけます。[独自のテキスト解析](#言語に独自のプラグインを使う)を設定した言語は、その解析のとおりに検索されます。たとえば、漢字で書かれた日本語のタイトルを、かなで入力した読みから見つけられます | OpenSearchクラスター |
| **Elasticsearch** | `elasticsearch` | OpenSearchと同じ検索です | Elasticsearchクラスター |

どのエンジンが結果を見つけても、ストアフロントに表示される各結果の内容はデータベースから読み込まれます。そのため、エンジンの更新が追いついていないせいでシリーズに古いタイトル、価格、表紙が表示されることはありません。検索の絞り込みと並べ替えは、どのエンジンでも同じように行えます。

どのエンジンも、シリーズを読者の言語で表示されるタイトルとあらすじで探します。英語で閲覧している読者は、シリーズを英語のタイトルで見つけられますが、日本語のタイトルにしかない単語では見つけられません。英語のタイトルがないシリーズは、その代わりに表示されるタイトル、つまりサイトの既定言語のタイトルで見つかります。著者とレーベルはどの言語でも1つの名前を持ち、読者の言語にかかわらずその名前で見つかります。

読者が検索するよりも一覧をたどることが多いカタログや、読者がタイトルを正確に入力するカタログなら、PostgreSQLで十分です。読者が読みでタイトルを探したり、綴りを間違えたりして、何も見つけられずにいるようなら、エンジンに移行してください。

## OpenSearchまたはElasticsearchを準備する

Publiraはエンジンを運用しません。自分で運用するクラスターかマネージドのクラスターを使い、次のものを準備してください。

- **プラグイン（必要な場合）**：既定のテキスト解析はOpenSearchとElasticsearchに標準で含まれる機能だけで構成されているので、公式イメージのエンジンはそのままで動作します。プラグインが必要になるのは、プラグインを使った[独自のテキスト解析を設定する](#言語に独自のプラグインを使う)言語がある場合だけです。
- **URL**：エンジンが応答する`http://`または`https://`のURLです。`publira server`、`publira worker`、`publiractl`のすべてから到達できる必要があります。
- **ユーザー**：エンジンが求める場合に必要です。PubliraはHTTPベーシック認証でログインし、それを`https://`のURLにだけ送ります。APIキーにも独自の認証局にも対応していないので、セキュリティを有効にしたエンジンには、サーバーがすでに信頼している証明書が必要です。ユーザーには、名前が後述のインデックスのエイリアスで始まるインデックスの作成、書き込み、削除と、エイリアスの移動の権限が必要です。
- **インデックスのエイリアス**：Publiraのインデックスの名前の元になる名前で、別の名前を指定しなければ`publira-catalog`です。Publiraは読者が選べる言語ごとに1つのインデックスを持ち、それぞれのインデックスを、このエイリアスの末尾に言語を付けた名前（`publira-catalog-en`、`publira-catalog-ja`、`publira-catalog-zh-hans`など）のエイリアスで参照します。インデックスとそのエイリアスはPubliraが自分で作成します。1つのクラスターを共有するインストール環境には、それぞれ別のエイリアスを指定してください。2つのインストール環境が1つのエイリアスを使うと、互いのカタログを上書きしてしまいます。

## エンジンをテストする

テストでは、エンジンにその種類と、すべてのノードにあるプラグインを問い合わせ、製品名、バージョン、プラグインを報告します。エンジンが応答しない場合、認証情報を拒否した場合、選んだものとは別の製品だった場合に失敗します。プラグインによって結果が決まることはありません。既定のテキスト解析にはプラグインが不要で、独自の定義は保存するときにエンジンに照らして確認されるためです。プラグインの一覧を取得するには、ほかでは必要のないクラスター権限がユーザーに必要なので、その権限のないユーザーではプラグインが一覧表示されないままテストが成功します。

- プラットフォーム管理画面では、**検索**の**接続をテスト**が、保存前のフォームの値をテストします。テストは`publira server`から実行されます。
- `publiractl search test`は保存済みのエンジンを、`publiractl`を実行している場所からテストし、テストが失敗すると`1`で終了します。PostgreSQLではテストするものがないので、`1`で終了します。

## 別のエンジンに移る

エンジンを保存しても、検索がすぐにそのエンジンに移るわけではありません。新しいエンジンのインデックスは空なので、まず`publira worker`がデータベースからインデックスを構築し、インデックスにすべてのテナントのカタログが入った時点で検索が移ります。それまでストアフロントは移行前のエンジンで応答し続けるので、読者が空のインデックスを検索することはありません。

### プラットフォーム管理画面から

1. サイドバーの**外部サービス**の下にある**検索**を選びます。
2. **エンジン**で**OpenSearch**か**Elasticsearch**を選び、その**URL**と、指定する場合は「**インデックスのエイリアス（任意）**」を入力します。
3. **認証**で**認証なし**を選ぶか、**ユーザー名とパスワード**を選んで両方を入力します。
4. **接続をテスト**を選び、成功したら**検索設定を保存**で保存します。

![OpenSearchを選んだ検索エンジン。エンジン、URL、インデックスのエイリアス（任意）、認証、接続テスト、検索設定を保存。](./search-engine.png)

画面上部の**検索の状態**には、ストアフロントが応答に使っているエンジンと、インデックスを構築している間は移行先のエンジンが表示されます。画面は数秒ごとに状態を確認し直すので、移行が起きるとそれが表示されます。保存できるのはオペレーターまたはスーパー管理者で、監査担当は画面を閲覧することしかできません。

### publiractlから

```bash
publiractl search set \
  --engine opensearch \
  --url https://search.example.com:9200 \
  --username publira --password-file /run/secrets/search-password
publiractl search test
publiractl search show
```

`search set`は保存済みの設定をすべて、指定したフラグで置き換えるので、毎回すべてのフラグを指定してください。`--username`を省略すると、保存済みのパスワードは削除されます。同じ`--username`を指定してパスワードを指定しなければ、保存済みのパスワードが保持されます。`search show`は、検索が応答に使っているエンジンと、進行中または失敗した構築を表示します。

### かかる時間

ワーカーは30秒ごとに構築すべきインデックスを探し、インデックスを埋めるには、エンジンがすべてのテナントの公開済みのシリーズ、著者、レーベルをすべて取り込むのに必要なだけの時間がかかります。その間に行われた変更も新しいインデックスに書き込まれるので、待っている間に何かが失われることはありません。

### 構築が失敗したとき

構築が失敗すると（エンジンが停止した、保存済みの定義が必要とするプラグインがノードからなくなった、ユーザーにインデックスを作成する権限がない、など）、検索は移行前のままになり、エラーが**検索の状態**と`publiractl search show`に表示されます。ワーカーは30秒ごとに再試行するので、エンジンを直せば、設定を保存し直さなくても構築が完了します。移行をやめる場合は、検索が現在応答に使っているエンジンを保存してください。

![構築が失敗したあとの検索の状態。PostgreSQLで応答していること、OpenSearchのインデックスを構築できなかったというメッセージ、最後に失敗した日時、エンジンのエラー。最後に失敗した日時は試行のたびに変わるため、ここではグレーで表示されている。](./search-build-failed.png)

### PostgreSQLに戻す

**PostgreSQL**を保存するか、`publiractl search set --engine sql`を実行すると、検索はすぐに戻ります。データベースにはインデックスが不要なためです。エンジン上のインデックスはそのまま残るので、再び使わない場合は自分で削除してください。

### 変更がすべてのプロセスに届くとき

`publira server`と`publira worker`は30秒ごとに設定を読み直すので、移行は再起動なしで1分以内にすべてのインスタンスに届きます。保存とテストはそれぞれ**監査ログ**に記録されます。

## テキスト解析

エンジンがタイトル、名前、あらすじを単語に分ける方法がテキスト解析です。テナントはインデックスを共有するので、定義はすべてのテナントで1つであり、言語ごとのインデックスは、その言語に独自の定義がない限り、この定義から構築されます。既定の定義はプラグインを必要とせず、どの言語にもそこそこ適しています。ラテン文字のタイトルは1文字の打ち間違いを許容しつつ単語で見つけ、漢字、かな、ハングルのタイトルはその中の連続する2文字以上の任意の部分で見つけ、大文字と小文字、英字とかなの全角と半角を区別しません。言語についてはそれ以上のことを知らないので、たとえば漢字で書かれたタイトルを読みから見つけることはできません。それ以上が必要な言語には、その言語のプラグインを使った[独自の定義を設定](#言語に独自のプラグインを使う)できます。

定義はインデックスの`settings.analysis`オブジェクトで、最大64 KiBのJSONです。インデックスが参照する3つの名前、つまりアナライザーの`written_form`と`alternate_form`、ノーマライザーの`exact_match`を定義する必要があります。それぞれの役割は[テキスト解析リファレンス](https://github.com/publira/publira/blob/main/server/README.md#text-analysis)にあります。

- プラットフォーム管理画面では、**検索**の**テキスト解析**の**共有**タブで、「**定義（settings.analysis、JSON）**」に定義を入力し、**テキスト解析を保存**で保存します。**既定に戻す**で既定の定義に戻ります。PostgreSQLにはインデックスがないので、保存するテキスト解析もありません。
- `publiractl`では、`search set --analysis-file korean-analysis.json`でエンジンと一緒に定義を保存し、`--default-analysis`で既定に戻します。どちらも指定しなければ、`search set`は保存済みの定義を保持します。

言語をその言語のプラグインで検索するには、その言語に独自の定義を設定します。その言語のインデックスはその定義から構築され、ほかの言語のインデックスは共有の定義から構築されます。

- プラットフォーム管理画面の**テキスト解析**には、共有の定義のタブ（**共有**。どの言語がそれを使っているかが表示されます）と、言語ごとのタブがあります。独自の定義がない言語のタブには、出発点として共有の定義が表示されます。そのタブで**テキスト解析を保存**を選ぶと、エディターの内容がその言語独自の定義として保存され、**共有の定義を使う**を選ぶとそれが破棄され、その言語は再び共有の定義から構築されます。
- `publiractl`では、`search set`で言語独自の定義を指定します。

```bash
publiractl search set --engine opensearch --url https://search.example.com --locale-analysis-file ja=japanese-analysis.json
```

`--locale-analysis-file`は言語とファイルを`LOCALE=FILE`の形で受け取り、`--shared-analysis-for ja`はその言語を再び共有の定義から構築します。どちらも言語ごとに繰り返し指定できます。どちらにも指定されなかった言語は今の状態を保ち、どちらも指定せずに`search set`を実行した場合はすべての言語が今の状態を保ちます。言語は`ja`、`en`、`ko`、`zh-Hans`、`zh-Hant`です。`publiractl search show`は、独自の定義を持つ言語を**Own analysis**の下に一覧表示します。

![テキスト解析。定義が定義すべき3つの名前、共有の定義のタブと言語ごとのタブ、どの定義が保存されていてどの言語がそれを使っているか、定義（settings.analysis、JSON）、テキスト解析を保存。](./search-text-analysis.png)

定義を保存する前に、その定義で空のインデックスを作成するようエンジンに依頼し、エンジンが拒否した定義は保存されません。その際、エンジンが示した理由と、言語独自の定義の場合はそれを指定した言語が表示されます。保存した定義は、新しいエンジンの場合と同じように、それによって変わる言語の新しいインデックスに組み込まれ、構築が終わると検索はそのインデックスに移ります。ほかの言語のインデックスはそのまま残ります。

### 言語に独自のプラグインを使う

各言語は、独自の定義を設定するまでは共有の定義で検索され、独自の定義の設定は任意です。OpenSearchとElasticsearchはどちらも多くの言語向けに解析プラグインを公開しています。たとえば、日本語向けの`analysis-kuromoji`と`analysis-icu`（漢字で書かれたタイトルを、かなで入力した読みに一致させられます）、韓国語向けの`analysis-nori`、中国語向けの`analysis-smartcn`などです。そうしたプラグインを使った定義は、その言語をプラグインの解析どおりに検索します。

1. すべてのノードを停止した状態で、`bin/opensearch-plugin install`または`bin/elasticsearch-plugin install`とプラグインの名前を使って、プラグインをインストールします。リポジトリの[開発用のOpenSearchイメージ](https://github.com/publira/publira/blob/main/infra/docker/opensearch/Dockerfile)に、この手順をDockerfileとして示しています。以後、**接続をテスト**ではすべてのノードにあるプラグインの中にそれが表示されます。
2. エンジンのプラグインのドキュメントに従って、プラグインのトークナイザーとフィルターを使い、上記の3つの名前を定義する定義を書きます。
3. それを**テキスト解析**のその言語のタブで保存するか、`publiractl search set --locale-analysis-file`で保存します。

その言語のインデックスがその定義で再構築され、準備ができると、その言語での検索は新しいインデックスに移ります。その言語のタイトルがないシリーズは、代わりに表示されるタイトルでその言語のインデックスに入るので、そのタイトルにもその言語の解析が適用されます。

## インデックスを再構築する

ワーカーは、テナントが公開、編集、既定言語の変更を行うたびにインデックスを最新に保ち、エンジンやテキスト解析が変わったとき、またはリリースによって読者が選べる言語や既定のテキスト解析が変わったときには新しいインデックスを構築します。そのため、インデックスを手動で再構築する必要はめったにありません。構築中は、**検索の状態**と`publiractl search show`に構築が進行中であることが表示され、ストアフロントは既存のインデックスで応答し続けます。`publiractl search reindex`は、残る次の2つの場合のためのものです。

- **リリースでインデックスが変わった場合**：[リリースノート](../2-deployments/8-upgrading.md#リリースノートを読む)にカタログのインデックスが変わったと書かれていたら、アップグレードが終わってから実行します。
- **インデックスが失われた場合**：クラスターを置き換えたり、インデックスを削除したりした場合です。

```bash
publiractl search reindex
```

このコマンドは、言語ごとに現在のインデックスと並べて新しいインデックスを構築し、すべてのテナントのカタログで埋め、すべてのエイリアスを一斉に新しいインデックスに移し、古いインデックスを削除します。そのため、実行中もストアフロントは検索を続けられます。カタログは`publira_content_stats`ロールとして読み込むので、そのロール用の`PUBLIRA_CONTENT_STATS_DB_URL`を指定し、エンジンのパスワードが保存されている場合は暗号鍵もあわせて指定してください。ワーカーがインデックスを構築している間は実行できず、構築が進行中だと`1`で終了します。構築が終わってから再び実行してください。PostgreSQLでは再構築するインデックスがないので、`1`で終了します。

`publiractl search reindex --tenant comics.example.com`は、新しいインデックスを構築せずに、検索が応答に使っているインデックスに1つのテナントのカタログを書き込み直します。これは結果がおかしく見える1つのテナントのためのもので、インデックスそのものへの変更を適用することはできません。
