インストールが保存する画像は、表紙、エピソードのページ、著者の写真、各テナントのロゴのどれも、すべてのテナントが共有する1つのS3互換バケットに置かれます。このバケットは`publiractl setup`で保存済みです。このページでは、バケットの各設定の意味とテストの方法、あとから変更する方法、保存した画像が読者に届くしくみを説明します。

このページの`publiractl`コマンドは、コマンドの部分だけを示しています。[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明に従い、`PUBLIRA_PLATFORM_DB_URL`に`publira_platform`の接続先を設定して実行してください。`PUBLIRA_SECRET_ENCRYPTION_KEYS`と`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`には、各プロセスと同じ値を設定します。フラグの一覧は[`publiractl`のリファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#storage)にあります。

## バケット

Publiraはバケットを作成しません。先にプロバイダーで空のバケットを作成し、Publiraが使う認証情報に、バケット内のオブジェクトをアップロード、読み取り、一覧取得、削除する権限を与えてください。読者がバケットから直接画像を取得することはないので、バケットを公開する必要はありません。

設定では、使うバケットとその接続先を指定します。

| 設定 | `publiractl storage set` | プラットフォーム管理画面 |
| --- | --- | --- |
| バケットの名前 | `--bucket` | **バケット** |
| バケットのリージョン | `--region` | **リージョン** |
| Amazon S3以外のストレージのアドレス | `--endpoint` | **エンドポイント** |
| バケットをホスト名ではなくURLのパスで指定するかどうか | `--force-path-style` | **パス形式でアクセスする** |
| 保存したオブジェクトを読み取れるURL | `--public-base-url` | **公開ベースURL(任意)** |

![オブジェクトストレージのフォームのうち、バケットからパス形式でアクセスするまでの部分。バケット、リージョン、公開ベースURL(任意)があり、S3互換プロバイダー向けの設定の中にエンドポイントとパス形式でアクセスするがある。](./object-storage-bucket.png)

Amazon S3のバケットなら、バケットとリージョンだけを指定し、ほかは空のままにします。

Cloudflare R2、MinIO、RustFS、各社のオブジェクトストレージといった、ほかのS3互換ストレージを使うときは、そのS3 APIのアドレスをエンドポイントに指定します。プロバイダーがパス形式を求めるときは、パス形式でのアクセスを有効にします。セルフホストのストレージは、たいていパス形式を求めます。リージョンのないストレージでも、リージョンには値が必要です。そのストレージのドキュメントが推奨する値を入力し、推奨がなければ`us-east-1`を入力してください。

公開ベースURLは空のままにしてください。[画像が読者に届くまで](#画像が読者に届くまで)で説明するとおり、何を入力しても、画像は必ず`publira server`を通して配信されます。

## 認証情報

Publiraは、バケットへのリクエストにすべて署名します。署名には、保存したアクセスキーを使う方法と、各プロセスが自分で見つけた認証情報を使う方法の2つがあります。

プラットフォーム管理画面では、**認証情報**で**アクセスキーを使う**か**各サーバー自身の認証情報を使う**かを選びます。`publiractl storage set`では、`--access-key-id`を指定するとキーを保存します。シークレットは、`--secret-access-key-file`を指定すればファイルから、`--secret-access-key-stdin`を指定すれば標準入力から読み込み、どちらもなければ入力を伏せたプロンプトで尋ねます。プラットフォームがシークレットを環境変数でしか渡せない場合は、`--secret-access-key-env`で環境変数から読み込みます。`--access-key-id`を省略すると、各プロセス自身の認証情報で署名するようになり、保存済みのキーは削除されます。

![認証情報の欄。各サーバー自身の認証情報を使うと、アクセスキーを使うの2つの選択肢が、それぞれの説明とともに表示されている。](./object-storage-credentials.png)

### 保存したアクセスキー

プロバイダーが発行したアクセスキーIDとシークレットアクセスキーを、設定と一緒に保存します。シークレットはインストールの暗号化キーで暗号化して保存されるので、バケットに接続するプロセスはどれも、同じ暗号化キーを設定して動かす必要があります。保存したシークレットが再び表示されることはありません。Amazon S3以外のストレージではふつうこの方法を使い、プロセスが自前の認証情報を持たないインストールでは、この方法しか使えません。

### 各プロセス自身の認証情報

キーは保存せず、各プロセスがAWS SDK単体と同じ方法で認証情報を見つけて署名します。使われるのは、環境変数の`AWS_ACCESS_KEY_ID`と`AWS_SECRET_ACCESS_KEY`、Web IDトークン、プロセスが動いているマシンのインスタンスロールのいずれかです。AWS上なら、長期間有効なシークレットを1つもデータベースに置かずに済みます。その代わり、`publira server`、`publira worker`、手元で実行する`publiractl`のすべてに、その認証情報が必要です。サーバーは画像をアップロードして読み取り、ワーカーは使われなくなった画像を削除し、`publiractl storage test`も署名するからです。

## 接続をテストする

テストでは、小さなオブジェクトをアップロードし、読み戻し、一覧で確かめてから削除します。これでPubliraがバケットに対して行う操作がすべて試され、結果は4つの手順ごとに表示されます。

- プラットフォーム管理画面では、**ストレージ**の**接続をテスト**が、保存する前のフォームの値をテストします。テストは`publira server`から実行されます。
- `publiractl storage test`は、保存済みの設定を、`publiractl`を実行したマシンからテストします。失敗した手順があると、終了コード`1`で終了します。

失敗したときは、失敗した手順とその理由が表示されます。理由には、ストレージが認証情報を拒否した、ある操作の権限がキーにない、その名前とリージョンとエンドポイントではバケットが見つからない、エンドポイントに接続できない、といったものがあります。管理画面のテストとコマンドは別々のマシンで動くので、一方からだけストレージに届くようなファイアウォールがあると、テストは片方で成功し、もう片方で失敗します。ストレージに届く必要があるのは`publira server`と`publira worker`です。

![失敗した接続テスト。バケットが見つからないためアップロードに失敗し、読み取り、一覧取得、削除は実行されていない。](./object-storage-connection-test.png)

## 設定を変更する

### プラットフォーム管理画面から

サイドバーの**外部サービス**にある**ストレージ**を選びます。画面には保存済みの設定が表示され、保存済みのシークレットは**保存済み(非表示)**と表示されます。値を変更したら**接続をテスト**を選び、**ストレージ設定を保存**で保存します。別のアクセスキーに替えるときは、**アクセスキーを置き換える**を選んで、アクセスキーIDとシークレットを両方入力します。保存済みのシークレットは、一緒に保存したアクセスキーIDとしか組み合わせられないからです。

![アクセスキーを保存した状態の認証情報。アクセスキーを使うが選ばれ、アクセスキーID、保存済み(非表示)と表示されたシークレットとアクセスキーを置き換えるボタン、接続テスト、ストレージ設定を保存ボタンがある。](./object-storage-saved-access-key.png)

保存できるのはオペレーターとスーパー管理者です。監査担当は画面を閲覧できますが、保存はできません。

### publiractlから

```bash
publiractl storage set \
  --bucket publira-images \
  --region ap-northeast-1 \
  --access-key-id AKIA... \
  --secret-access-key-file /run/secrets/aws-secret-access-key
publiractl storage test
publiractl storage show
```

`storage set`は、保存済みの設定を、指定したフラグの値ですべて置き換えます。指定しなかったフラグの設定は消えるので、毎回すべてを指定してください。保存済みと同じ`--access-key-id`をシークレットなしで指定すると、保存済みのシークレットはそのまま残ります。

### 変更が反映されるまで

どのプロセスも30秒ごとに設定を読み直すので、保存した設定は再起動しなくても1分以内にすべてのプロセスに届きます。保存もテストも、そのたびに**監査ログ**に記録されます。

### 別のバケットに移す

新しいバケットを保存しても、画像は何もコピーされません。それまでにアップロードされた画像は古いバケットに残り、インストールはそれを新しいバケットで探して見つけられなくなります。保存する前に、オブジェクトをキーを変えずに新しいバケットへコピーしてください。保存したら、最初のコピーのあいだにアップロードされたものを拾うために、もう一度コピーします。AWS CLIでは次のようにします。ほかのプロバイダーでは、それに当たるツールを使ってください。

```bash
aws s3 sync s3://publira-images s3://publira-images-new
publiractl storage set --bucket publira-images-new --region ap-northeast-1 ...
aws s3 sync s3://publira-images s3://publira-images-new
```

保存したあと、インストールが古いバケットに触れることはありません。古いバケットは、新しいバケットからの配信がしばらく続くまで残しておき、そのあとで自分で削除してください。

### アクセスキーをローテーションする

プロバイダーで新しいキーを発行し、`storage set`か**アクセスキーを置き換える**で保存してテストします。古いキーを無効にするのは、そのあとです。プロセスが新しいキーに切り替わるまでに最大1分かかるので、それより早く古いキーを無効にすると、アップロードや画像の読み取りが失敗する時間ができてしまいます。

## 画像が読者に届くまで

読者のブラウザーとアプリは、テナントのホスト名の`/images`から画像を取得します。[ルーティング](../2-deployments/4-edge/index.md#ルーティング)で求めているとおり、このリクエストはリバースプロキシが`publira server`に転送します。サーバーはリクエストごとに次の処理をします。

1. 読者がその画像を見てよいか確かめます。エピソードのページを見られるのは、そのエピソードが無料になっている読者か、エピソードを解放した読者だけです。未公開のエピソードのページを見られるのは、管理画面にいるテナントのスタッフだけです。
2. バケットから元の画像を読み取り、WebPとAVIFのうちブラウザーが受け付けるほうに変換して、ページが求めるサイズに縮小します。
3. 変換した画像を変換キャッシュに入れます。同じ画像を同じサイズで求める次のリクエストでは、バケットを読むことも変換し直すこともありません。
4. エピソードのページは、暗号化してから読者に送ります。ブラウザーが受け取るのは、保存してほかの場所で開けるような画像ファイルではありません。表紙やロゴなど、ほかの画像はそのまま送ります。

そのため、バケットを公開する必要も、前段にCDNを置く必要も、縮小したコピーを前もって作っておく必要もありません。バケットに置くのは、画像1つにつき元の画像1つだけです。

### 変換キャッシュ

変換キャッシュは、`publira server`に`PUBLIRA_REDIS_URL`で指定したValkeyかRedisのサーバーに置かれ、サーバーのすべてのインスタンスで共有されます。指定しなければ各インスタンスのメモリーに置かれます。インスタンスが1つならそれでかまいませんが、インスタンスを増やすと、増やした分だけすべての画像を変換し直すことになります。

変換した画像は1時間保持されます。`publira server`の`PUBLIRA_IMAGE_CACHE_TTL`に`6h`のような期間か秒数を指定すると、この時間を変えられます。長くするとバケットの読み取りと変換が減る代わりに、Valkeyのメモリーを多く使い、短くするとその逆になります。画像のレスポンスには`X-Publira-Image-Cache: hit`か`miss`が付くので、キャッシュが効いているかどうかがわかります。

画像に関するほかの環境変数と、変換に必要なlibvipsライブラリを組み込んだサーバーのビルド方法は、[`publira server`のリファレンス](https://github.com/publira/publira/blob/main/server/cmd/publira/README.md#image-delivery)にあります。
