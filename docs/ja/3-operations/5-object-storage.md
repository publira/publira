インストール環境が保管するすべての画像（表紙、エピソードのページ、著者の写真、各テナントのロゴ）は、すべてのテナントで共有する1つのS3互換バケットに保存されます。そのバケットは`publiractl setup`が保存しました。このページでは、その各設定、設定のテスト方法、あとからの変更方法、そして保存された画像が読者に届く仕組みを説明します。

このページの`publiractl`コマンドは、コマンド単体で示しています。[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明どおりに、`PUBLIRA_PLATFORM_DB_URL`に`publira_platform`の接続先を設定し、各プロセスと同じ`PUBLIRA_SECRET_ENCRYPTION_KEYS`と`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`を指定して実行してください。すべてのフラグは[`publiractl`リファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#storage)にあります。

## バケット

Publiraはバケットを作成しません。先にプロバイダーで空のバケットを作成し、Publiraが使う認証情報に、そのバケット内のオブジェクトをアップロード、読み取り、一覧取得、削除する権限を与えてください。バケットを公開する必要はありません。読者がバケットから直接取得することはないためです。

設定では、バケットとそこへの接続方法を指定します。

| 設定 | `publiractl storage set` | プラットフォーム管理画面 |
| --- | --- | --- |
| バケットの名前 | `--bucket` | **バケット** |
| リージョン | `--region` | **リージョン** |
| Amazon S3以外のストアのアドレス | `--endpoint` | **エンドポイント** |
| バケットをホスト名ではなくURLのパスで指定する | `--force-path-style` | **パス形式でアクセスする** |
| 保存したオブジェクトを読み取れるURL | `--public-base-url` | **公開ベースURL（任意）** |

![バケットからパス形式でアクセスするまでのオブジェクトストレージのフォーム。バケット、リージョン、公開ベースURL（任意）、そしてS3互換プロバイダー向けの設定の下にあるエンドポイントとパス形式でアクセスする。](./object-storage-bucket.png)

Amazon S3のバケットの場合は、バケットとリージョンを指定し、残りは空のままにします。

ほかのS3互換ストア（Cloudflare R2、MinIO、RustFS、各プロバイダーのオブジェクトストレージ）の場合は、そのS3 APIのアドレスをエンドポイントに指定し、プロバイダーが求める場合はパス形式でのアクセスを有効にします。セルフホストのストアの多くはこれを求めます。リージョンのないストアでもリージョンの値は必要です。そのドキュメントが推奨する値を入力し、推奨がなければ`us-east-1`を入力してください。

公開ベースURLは空のままにしてください。[画像が読者に届く仕組み](#画像が読者に届く仕組み)で説明するとおり、何を入力していても、画像は常に`publira server`を通して配信されます。

## 認証情報

Publiraは、バケットへのすべてのリクエストに次の2つのいずれかの方法で署名します。

**設定と一緒に保存するアクセスキー**：プロバイダーが発行するアクセスキーIDとシークレットアクセスキーです。シークレットはインストール環境の暗号鍵で暗号化して保存されるので、バケットにアクセスするすべてのプロセスはその鍵を指定して実行する必要があります。保存したシークレットが再び表示されることはありません。Amazon S3以外のストアでは通常こちらを選びます。また、プロセスが独自の認証情報を持たないインストール環境では、こちらしか選べません。

**各プロセスが自分で見つける認証情報**：キーは保存しません。各プロセスはAWS SDKが単独で行うのと同じ方法で署名します。環境の`AWS_ACCESS_KEY_ID`と`AWS_SECRET_ACCESS_KEY`、Web IDトークン、または実行しているマシンのインスタンスロールです。AWSでは長期間有効なシークレットをデータベースに一切置かずに済みますが、その代わり`publira server`、`publira worker`、そして実行する`publiractl`のすべてにその認証情報が必要になります。サーバーは画像をアップロードして読み取り、ワーカーはどこからも使われなくなった画像を削除し、`publiractl storage test`も署名を行うためです。

プラットフォーム管理画面では、**認証情報**でこの2つを**アクセスキーを使う**と**各サーバー自身の認証情報を使う**として選べます。`publiractl storage set`では、`--access-key-id`を指定するとキーが保存されます。シークレットは`--secret-access-key-file`でファイルから、`--secret-access-key-stdin`で標準入力から、マスクされたプロンプトから、またはプラットフォームがシークレットを環境変数としてしか設定できない場合は`--secret-access-key-env`で環境変数から読み込みます。`--access-key-id`を省略すると、各プロセス自身の認証情報で署名し、保存済みのキーは削除されます。

![認証情報。各サーバー自身の認証情報を使うとアクセスキーを使うが、それぞれの意味とともに表示されている。](./object-storage-credentials.png)

## 接続をテストする

テストでは小さなオブジェクトをアップロードし、読み取り、一覧に表示されることを確かめ、削除します。これはPubliraがバケットに対して行う操作のすべてであり、4つの手順それぞれの結果が報告されます。

- プラットフォーム管理画面では、**ストレージ**の**接続をテスト**が、保存前のフォームの値をテストします。テストは`publira server`から実行されます。
- `publiractl storage test`は保存済みの設定を、`publiractl`を実行している場所からテストし、失敗した手順があると`1`で終了します。

失敗した場合は、その手順と理由が表示されます。ストアが認証情報を拒否した、キーにある操作の権限がない、その名前、リージョン、エンドポイントでバケットが見つからなかった、エンドポイントに到達できなかった、などです。管理画面のテストとコマンドは別々のマシンで実行されるので、一方からはストアに到達でき、もう一方からは到達できないファイアウォールがあると、テストが一方では成功し、もう一方では失敗します。ストアに到達できる必要があるのは`publira server`と`publira worker`です。

![失敗した接続テスト。バケットが見つからないためアップロードが失敗し、読み取り、一覧取得、削除は実行されなかった。](./object-storage-connection-test.png)

## 設定を変更する

### プラットフォーム管理画面から

サイドバーの**外部サービス**の下にある**ストレージ**を選びます。画面には保存済みの設定が表示され、保存済みのシークレットは「**保存済み（非表示）**」と表示されます。値を変更し、**接続をテスト**を選んでから、**ストレージ設定を保存**で保存します。別のアクセスキーを使うには、**アクセスキーを置き換える**を選び、アクセスキーIDとシークレットを一緒に入力します。保存済みのシークレットは、一緒に保存したIDとしか組み合わせられません。

![アクセスキーが保存されている認証情報。アクセスキーを使う、アクセスキーID、保存済み（非表示）と表示されたシークレットとアクセスキーを置き換える、接続テスト、ストレージ設定を保存。](./object-storage-saved-access-key.png)

保存できるのはオペレーターまたはスーパー管理者です。監査担当は画面を閲覧できますが、保存はできません。

### publiractlから

```bash
publiractl storage set \
  --bucket publira-images \
  --region ap-northeast-1 \
  --access-key-id AKIA... \
  --secret-access-key-file /run/secrets/aws-secret-access-key
publiractl storage test
publiractl storage show
```

`storage set`は保存済みの設定をすべて、指定したフラグで置き換えるので、毎回すべてのフラグを指定してください。省略したフラグの設定は消去されます。同じ`--access-key-id`を指定してシークレットを指定しなければ、保存済みのシークレットが保持されます。

### 変更が反映されるとき

すべてのプロセスは30秒ごとに設定を読み直すので、保存した内容は再起動なしで1分以内にすべてのプロセスに反映されます。保存とテストはそれぞれ**監査ログ**に記録されます。

### 別のバケットに移る

新しいバケットを保存しても、何もコピーされません。それまでにアップロードされた画像は古いバケットに残り、インストール環境は画像がない新しいバケットを探すことになります。保存する前にオブジェクトをキーを保ったままコピーし、それから保存し、最初のコピーの間にアップロードされたものを拾うためにもう一度コピーしてください。AWS CLI、またはプロバイダーの同等のツールでは次のようにします。

```bash
aws s3 sync s3://publira-images s3://publira-images-new
publiractl storage set --bucket publira-images-new --region ap-northeast-1 ...
aws s3 sync s3://publira-images s3://publira-images-new
```

保存後、インストール環境が古いバケットにアクセスすることはありません。インストール環境が新しいバケットからしばらく問題なく配信できるまで古いバケットは残しておき、その後、自分で削除してください。

### アクセスキーをローテーションする

プロバイダーで新しいキーを発行し、`storage set`か**アクセスキーを置き換える**で保存し、テストしてから、初めて古いキーを無効にします。プロセスは1分以内に新しいキーに切り替わるので、それより早く古いキーを無効にすると、アップロードや画像の読み取りが失敗する期間が生じます。

## 画像が読者に届く仕組み

読者のブラウザーとアプリは、テナント自身のホスト名の`/images`から画像を取得します。[ルーティング](../2-deployments/4-edge/index.md#ルーティング)が求めるとおり、エッジはこれを`publira server`に転送します。サーバーはリクエストごとに次のことを行います。

1. 読者がその画像を見てよいかを確認します。エピソードのページは、そのエピソードが無料になっている読者か、エピソードを解放した読者にだけ表示されます。未公開のエピソードのページは、管理画面にいるテナントのスタッフにだけ表示されます。
2. バケットから元画像を読み取り、ブラウザーが受け付ける形式に応じてWebPかAVIFに変換し、ページが求めるサイズにリサイズします。
3. 変換した結果を変換キャッシュに保持し、同じ画像を同じサイズで求める次のリクエストでは、バケットの読み取りも変換も行わずに済むようにします。
4. エピソードのページは、読者に送る前に暗号化します。これにより、ブラウザーが受け取るのは、保存してほかの場所で開ける画像ファイルではなくなります。表紙、ロゴ、そのほかの画像はそのまま送られます。

このため、バケットには公開アクセスも、前段のCDNも、事前にリサイズしたコピーも必要ありません。バケットが保持するのは画像ごとに1つの元画像だけです。

### 変換キャッシュ

変換キャッシュは、`publira server`に`PUBLIRA_REDIS_URL`として指定されたValkeyまたはRedisのサーバーに保持され、サーバーのすべてのインスタンスで共有されます。指定がない場合は各インスタンスのメモリーに保持されます。これは単一のインスタンスでは問題ありませんが、インスタンスを追加するたびに、そのインスタンスがすべての画像を改めて変換することになります。

変換した画像は、`publira server`の`PUBLIRA_IMAGE_CACHE_TTL`で別の値を指定しない限り、1時間保持されます。値は`6h`のような期間か秒数で指定します。長くするとバケットの読み取りと変換の回数が減る代わりにValkeyのメモリーを使い、短くするとその逆になります。画像のレスポンスにはそれぞれ`X-Publira-Image-Cache: hit`または`miss`が付くので、キャッシュが役目を果たしているかを確認できます。

そのほかの画像関連の変数と、変換に必要なlibvipsライブラリを含めたサーバーのビルド方法は、[`publira server`リファレンス](https://github.com/publira/publira/blob/main/server/cmd/publira/README.md#image-delivery)にあります。
