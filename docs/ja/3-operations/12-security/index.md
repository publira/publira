Publiraには、すべてのテナントの決済プロバイダとメールサーバーの認証情報、すべての読者の個人情報、それらを暗号化する鍵が保存されています。このページでは、これらを守るオペレーターに向けて、Publiraが何によってデータを分けているかと、各シークレットをどこに置いてよいかを説明します。シークレットの入れ替え方、2段階認証と監査ログで得られるもの、前段に置くWAFとレート制限の設定は、[このセクションのページ](#このセクションの内容)で説明します。

## データを分ける仕組み

### データベースのロール

`publiractl db`コマンドが使う[管理用ログイン](../../2-deployments/2-installing.md#サービスを用意する)でPostgreSQLに接続するプロセスはありません。Publiraの各部分は`publiractl db roles`が作成する6つのロールのどれかで接続し、各ロールが扱えるのはその部分に必要なものに限られます。詳しくは[データベースのロール](../../2-deployments/2-installing.md#データベースのロール)を参照してください。

読者やテナントのスタッフに応答するロールは、行レベルセキュリティにより、リクエストで指定されたテナントの行しか扱えません。これらの処理に不具合があっても、ほかのテナントの行は読み取れないということです。オペレーターのパスワードハッシュとプラットフォームのメールの認証情報には、`publira_platform`と、プラットフォームのメールを送るワーカーのロールしかアクセスできません。テナント管理画面のロールが読み取れるプラットフォームのメール設定は、送信元アドレスだけです。

この分離は、各プロセスが自分のロールの接続URLだけを持っている間しか成り立ちません。管理用ログインのパスワードは`publiractl db`コマンドにだけ渡してください。プロセスの接続URLに、管理用ログインや、そのプロセスが使わないロールを設定してはいけません。

### 管理画面のAPI

`publira server`は、テナント管理画面とプラットフォーム管理画面のAPIを、公開APIと同じく`/rpc`配下で提供しています。ポートも、リバースプロキシが転送する1つのポートを共有しています。そのため、管理画面のAPIに外から届くかどうかはリバースプロキシの転送先しだいです。[ルーティング](../../2-deployments/4-edge/index.md#ルーティング)のとおりに設定したリバースプロキシは、これらをどこにも転送しません。`web-admin`と`web-platform`はプライベートネットワーク経由で管理画面のAPIを呼び出し、リバースプロキシはどのホストでも`404`を返します。

その内側にも守りがあります。管理画面のAPIへのリクエストは、オペレーターのセッションかWebサービストークンがなければ、実行される前に拒否されます。セッションができる前に実行されるログイン、パスワードの再設定、メールアドレスの確認の3つは、クライアントごとに回数を制限するか、サーバー自身が保護しています。プラットフォーム管理画面で最初のオペレーターを作成するにはWebサービストークンが必要で、このトークンを送るのはプラットフォーム管理画面のサーバーだけです。

つまり、`publira server`に届いた者がすべてのテナントの作品やプラットフォームの読者の一覧を手にできないのは、Webサービストークンがあるからです。このトークンは、下の表に挙げたプロセスにだけ持たせてください。

リバースプロキシで制限していても、テナントのドメインからのリクエストを受けるプロセスは、[構成の概要](../../2-deployments/1-overview.md#publiraで動かすプロセス)で説明しているとおり`publira server --role storefront`で動かす価値があります。両者は別々の防御層です。リバースプロキシは管理画面のAPIをインターネットから隠し、`--role storefront`は管理画面のデータベースログインとWebサービストークンを、読者がアクセスするプロセスに持たせません。そのプロセスに不具合があっても、リバースプロキシが誤って管理画面のパスを転送しても、これらには届きません。

### 各シークレットの置き場所

シークレットは、それを読むプロセスにだけ設定してください。必要としないプロセスに設定すれば、漏れうる場所が増えるだけです。

| シークレット | 設定する場所 | 設定してはいけない場所 | 持っている者にできること |
| --- | --- | --- | --- |
| シークレットの暗号化キー | `publira server`、`publira worker`、`publiractl` | Webアプリ | データベースのコピーがあれば、保存されているすべての認証情報を復号できる |
| アクセストークンの署名キー(`PUBLIRA_AUTH_JWT_SECRET`) | `publira server` | それ以外のすべて | どの読者、スタッフ、オペレーターのセッションにも署名できる |
| 各Webアプリのセッションキー(`PUBLIRA_AUTH_SECRET`) | そのWebアプリ | `publira server`、`publira worker` | そのアプリのセッションCookieを読み取ったり偽造したりできる。セッションCookieにはユーザーのアクセストークンが入っている |
| キャッシュ再検証トークン | `publira server`、`publira worker`、すべてのWebアプリ | `publiractl` | キャッシュされたどのページでも、何度でも破棄できる |
| Webサービストークン | `publira server`、`web-admin`、`web-platform` | `web-storefront`、`publira worker` | 非公開のシリーズを含むすべてのテナントの作品と、プラットフォームのテナント、オペレーター、読者を読み取れる |
| 管理用ログインのパスワード | `publiractl db`コマンド | 常駐するすべてのプロセス | データベースのすべてを操作できる |
| 各ロールのパスワード | そのロールで接続するプロセス | それ以外のプロセス | そのロールが扱えるものにアクセスできる |

Webアプリ同士で1つのセッションキーを共有することもできますが、Composeファイルと同じく、アプリごとに別のキーを設定してください。キーを1つ入れ替えたときにログアウトするのが、そのアプリのユーザーだけで済みます。

### publiractlへのシークレットの渡し方

`publiractl`はシークレットを引数では受け取りません。KubernetesやDockerの`/run/secrets/`のように、シークレットをファイルとしてマウントできる環境では、シークレットごとの`--<name>-file`フラグでファイルとして渡してください。ファイルなら、`publiractl`を実行するユーザーだけが読めるようにでき、tmpfs上に置くこともできます。環境変数の値は、そのプロセスから起動したすべてのプロセスに引き継がれます。`/proc/<pid>/environ`、`docker inspect`やオーケストレーターのタスクの詳細、環境変数を記録するクラッシュレポートやデバッグダンプからも読み取れます。

シークレットごとの`--<name>-env`フラグは、[Amazon ECS](../../2-deployments/6-ecs-fargate/index.md)のように、シークレットを環境変数でしか渡せない環境に限って使ってください。

### 環境ごとに別のシークレットを使う

シークレットは、本番環境、ステージング環境、各開発者のマシンと、Publiraを動かす環境ごとにすべて新しく生成してください。アクセストークンの署名キーを共有する2つの環境は、両方に同じIDで存在するアカウントについて、互いのセッションを受け入れてしまいます。本番環境のバックアップから復元したステージング環境では、すべてのアカウントがこれにあたります。

本番環境から復元したコピーが保存済みの認証情報を復号できるのは、本番環境の暗号化キーがあるときだけです。逆に暗号化キーがあれば、そのコピーは本番環境のSMTPアカウント、決済プロバイダのキーなど、テナントが保存したすべての認証情報を手にします。こうしたコピーは、本番環境のシークレットを置いてよい場所でだけ動かしてください。アクセストークンの署名キー、セッションキー、各トークン、ロールのパスワードは、コピー専用のものを設定してください。

## 脆弱性の報告

Publira自体の脆弱性は、公開のIssueではなく、[セキュリティポリシー](https://github.com/publira/publira/security/policy)に従って非公開で報告してください。
