Publiraは、すべてのテナントの決済プロバイダとメールサーバーの認証情報、すべての読者の個人情報、そしてそれらを暗号化する鍵を保持しています。このページは、それらを守るオペレーターのためのページです。Publiraがデータを分離するために何に頼っているか、各シークレットをどこに置いてよいかを説明します。各シークレットの入れ替え方や、2段階認証と監査ログで何ができるかは、[このセクションのページ](#このセクションの内容)で説明します。

## データを分離する仕組み

### データベースのロール

`publiractl db`コマンドが使う[管理用ログイン](../../2-deployments/2-installing.md#サービスを用意する)でPostgreSQLに接続するプロセスはありません。Publiraの各部分は、`publiractl db roles`が作成する6つのロールのいずれかで接続し、各ロールが扱えるのはその部分に必要なものだけです。詳しくは[データベースのロール](../../2-deployments/2-installing.md#データベースのロール)を参照してください。読者とテナントのスタッフへの応答に使うロールは、行レベルセキュリティによって、リクエストが指定したテナントの行しか扱えません。そのため、これらの処理に欠陥があっても、ほかのテナントの行は読み取れません。オペレーターのパスワードハッシュとプラットフォームのメールの認証情報には、`publira_platform`と、プラットフォームのメールを送るワーカーのロール以外はアクセスできません。テナント管理画面のロールが読み取れるのはプラットフォームのメールの送信元アドレスだけで、それ以外のプラットフォームのメール設定は読み取れません。

この分離が成り立つのは、各プロセスが自分のロールの接続URLだけを持ち、ほかの接続URLを持たない間だけです。管理用ログインのパスワードは`publiractl db`コマンドにだけ渡してください。プロセスの接続URLに、管理用ログインや、そのプロセスが使わないロールを設定してはいけません。

### 管理画面のAPI

`publira server`は、テナント管理画面とプラットフォーム管理画面のAPIを、公開APIと同じポートの`/rpc`配下で提供しています。このポートは、リバースプロキシの転送先になっているポートです。管理画面のAPIに外から到達できるのはリバースプロキシが転送する場合だけで、[リバースプロキシの設定のルーティングの項](../../2-deployments/4-edge/index.md#ルーティング)のとおりに設定していれば、どこにも転送されません。`web-admin`と`web-platform`はプライベートネットワークを通じて管理画面のAPIを呼び出し、リバースプロキシはどのホストでもこれらのリクエストに`404`を返します。

さらにその内側でも、管理画面のAPIへのリクエストは、オペレーターのセッションかWebサービストークンを伴わない限り、実行前に拒否されます。セッションができる前に実行される少数のリクエスト、つまりログイン、パスワードの再設定、メールアドレスの確認は、クライアントごとに回数が制限されるか、サーバー自身によって保護されています。プラットフォーム管理画面の最初のオペレーターを作成するにはWebサービストークンが必要で、このトークンを送るのはプラットフォーム管理画面のサーバーだけです。つまり、`publira server`に到達した者が、すべてのテナントの作品やプラットフォームの読者の一覧を手に入れるのを防いでいるのはWebサービストークンです。このトークンは、下の表に挙げたプロセスにだけ持たせてください。

リバースプロキシでこのように制限していても、[構成の概要](../../2-deployments/1-overview.md#publiraで動かすプロセス)で説明しているとおり、テナントのドメインからのリクエストを受けるプロセスを`publira server --role storefront`で動かす意味はあります。この2つは別々の防御層です。リバースプロキシは管理画面のAPIをインターネットから切り離し、`--role storefront`は管理画面のデータベースログインとWebサービストークンを、読者がアクセスするプロセスから切り離します。そのため、そのプロセスに欠陥があっても、リバースプロキシが誤って管理画面のパスを転送してしまっても、これらには届きません。

### 各シークレットの置き場所

各シークレットは、それを読むプロセスにだけ設定してください。値を必要としないプロセスに設定すると、漏えいしうる場所が1つ増えるだけです。

| シークレット | 設定する場所 | 設定してはいけない場所 | 持っている者にできること |
| --- | --- | --- | --- |
| シークレットの暗号化キー | `publira server`、`publira worker`、`publiractl` | Webアプリ | データベースのコピーがあれば、Publiraが保存しているすべての認証情報を復号できる |
| アクセストークンの署名キー(`PUBLIRA_AUTH_JWT_SECRET`) | `publira server` | それ以外のすべて | どの読者、スタッフ、オペレーターのセッションにも署名できる |
| 各Webアプリのセッションキー(`PUBLIRA_AUTH_SECRET`) | そのWebアプリ | `publira server`、`publira worker` | そのアプリのセッションCookieを読み取り、偽造できる。セッションCookieにはユーザーのアクセストークンが入っている |
| キャッシュ再検証トークン | `publira server`、`publira worker`、すべてのWebアプリ | `publiractl` | どのキャッシュ済みページでも、何度でも破棄できる |
| Webサービストークン | `publira server`、`web-admin`、`web-platform` | `web-storefront`、`publira worker` | 非公開のシリーズを含むすべてのテナントの作品と、プラットフォームのテナント、オペレーター、読者を読み取れる |
| 管理用ログインのパスワード | `publiractl db`コマンド | 常駐するすべてのプロセス | データベースのすべてを操作できる |
| 各ロールのパスワード | そのロールで接続するプロセス | それ以外のプロセス | そのロールが扱えるものにアクセスできる |

Webアプリは1つのセッションキーを共有することもできますが、Composeファイルと同じく、アプリごとに別のキーを設定してください。そうすれば、1つのキーを入れ替えてもログアウトするのはそのアプリのユーザーだけです。

### publiractlへのシークレットの渡し方

`publiractl`は、シークレットを引数では受け取りません。KubernetesやDockerが`/run/secrets/`の下にマウントするように、シークレットをファイルとしてマウントできる環境では、シークレットごとの`--<name>-file`フラグでファイルとして渡してください。ファイルなら、`publiractl`を実行するユーザーだけが読めるようにでき、tmpfs上に置くこともできます。環境変数の値は、その値を持つプロセスから起動したすべてのプロセスに引き継がれます。また、`/proc/<pid>/environ`、`docker inspect`やオーケストレーターのタスクの詳細表示、環境変数を記録するクラッシュレポートやデバッグダンプからも読み取れてしまいます。

シークレットごとの`--<name>-env`フラグは、[Amazon ECS(Fargate)](../../2-deployments/6-ecs-fargate/index.md)のように、シークレットを環境変数でしか渡せない環境でだけ使ってください。

### 環境ごとに別のシークレットを使う

シークレットは、Publiraを動かす環境ごとにすべて新しく生成してください。本番環境、ステージング環境、各開発者のマシンのそれぞれです。アクセストークンの署名キーを共有する2つの環境は、両方に同じIDで存在するアカウントについて、互いのセッションを受け入れてしまいます。本番環境のバックアップから復元したステージング環境のデータベースでは、すべてのアカウントがこれにあたります。

本番環境から復元したコピーで保存済みの認証情報を復号できるのは、本番環境の暗号化キーがある場合だけです。そして暗号化キーがあれば、そのコピーは本番環境のSMTPアカウント、決済プロバイダのキー、そのほかテナントが保存したすべての認証情報を手にします。こうしたコピーは、本番環境のシークレットを置いてよい場所でだけ動かしてください。また、アクセストークンの署名キー、セッションキー、各トークン、ロールのパスワードは、コピー専用のものを設定してください。

## 脆弱性の報告

Publira自体の脆弱性は、公開のIssueではなく、[セキュリティポリシー](https://github.com/publira/publira/security/policy)に従って非公開で報告してください。
