インストール環境は、すべてのテナントの決済プロバイダとメールサーバーの認証情報、すべての読者の個人データ、そしてそれらを封じる鍵を保持しています。このページは、それらを安全に保つオペレーターに向けたものです。インストール環境がそれらを分離するために何に頼っているか、そして各シークレットをどこに置いてよいかを説明します。各シークレットの入れ替え方と、2段階認証や監査ログによって得られるものは、[このセクションの内容](#このセクションの内容)にあるページで説明しています。

## データを分離しているもの

### データベースのロール

`publiractl db`コマンドが使う[管理用ログイン](../../2-deployments/2-installing.md#サービスを用意する)としてPostgreSQLに接続するプロセスはありません。インストール環境の各部分は、`publiractl db roles`が作成する6つのロールのいずれかとして接続し、各ロールは、[データベースのロール](../../2-deployments/2-installing.md#データベースのロール)で説明しているとおり、その部分が必要とするものにしか届きません。読者とテナントのスタッフに応答するロールは、行レベルセキュリティによって、リクエストが示すテナントに縛られているので、それらの経路に欠陥があってもほかのテナントの行は読めません。また、オペレーターのパスワードハッシュとプラットフォームのメールの認証情報は、`publira_platform`と、プラットフォームのメールを送るワーカーのロール以外のどのロールからも届きません。テナント管理画面のロールは、プラットフォームのメールの送信元アドレスを読みますが、プラットフォームのメール設定のそれ以外のものは何も読みません。

これが成り立つのは、各プロセスが自分のロールの接続URLだけを持ち、それ以外を持たない間だけです。管理用ログインのパスワードは`publiractl db`コマンドだけに与え、プロセスの接続URLを、そのログインや、そのプロセスが使わないロールに決して設定しないでください。

### 管理画面のAPI

`publira server`は、テナント管理画面とプラットフォーム管理画面のAPIを、公開APIと並べて`/rpc`配下で、エッジが転送する1つのポートで提供します。これらに到達できるのはエッジが転送する場所だけで、[ルーティング](../../2-deployments/4-edge/index.md#ルーティング)のとおりに設定したエッジは、これらをどこにも転送しません。`web-admin`と`web-platform`はプライベートネットワーク経由でこれらを呼び出し、エッジはどのホストでもこれらに`404`で応答します。その背後でも、各リクエストは、オペレーターのセッションかWebサービストークンを伴わない限り、実行前に拒否されます。セッションができる前に実行される少数のリクエスト（ログイン、パスワードの再設定、メールアドレスの確認）は、クライアントごとに制限されるか、サーバー自身によって守られています。そして、プラットフォーム管理画面の最初のオペレーターの作成にはWebサービストークンが必要で、それを送るのはプラットフォーム管理画面のサーバーだけです。したがって、Webサービストークンは、`publira server`に到達した誰かと、すべてのテナントの作品と、プラットフォームの読者の一覧との間に立つものです。下の表が示すプロセスだけに持たせてください。

[概要](../../2-deployments/1-overview.md#インストール環境が動かすもの)で説明しているとおり、テナントのドメインが到達するプロセスを`publira server --role storefront`として動かすことは、エッジのルールがあっても引き続き価値があります。この2つは別々の層です。エッジは管理画面のAPIをインターネットから遠ざけ、`--role storefront`は管理画面のデータベースログインとWebサービストークンを読者が到達するプロセスから遠ざけるので、そのプロセスの欠陥も、結局は管理画面のパスを転送してしまったエッジも、それらには届きません。

### 各シークレットを置いてよい場所

各シークレットは、それを読むプロセスだけに与えてください。値を必要としないプロセスは、それが漏れうる場所を1つ増やすだけです。

| シークレット | 設定する場所 | 決して設定しない場所 | 保持者ができること |
| --- | --- | --- | --- |
| シークレット暗号化キー | `publira server`、`publira worker`、`publiractl` | Webアプリ | データベースのコピーがあれば、インストール環境が保存するすべての認証情報を開く |
| アクセストークンの署名鍵、`PUBLIRA_AUTH_JWT_SECRET` | `publira server` | それ以外のすべて | どの読者、スタッフ、オペレーターのセッションにも署名する |
| 各Webアプリのセッションキー、`PUBLIRA_AUTH_SECRET` | そのWebアプリ | `publira server`、`publira worker` | そのアプリのセッションCookie（ユーザーのアクセストークンを運ぶ）を読み、偽造する |
| キャッシュ再検証トークン | `publira server`、`publira worker`、すべてのWebアプリ | `publiractl` | 任意のキャッシュ済みページを、好きなだけ何度でも破棄する |
| Webサービストークン | `publira server`、`web-admin`、`web-platform` | `web-storefront`、`publira worker` | 非公開のシリーズを含む、任意のテナントの作品と、プラットフォームのテナント、オペレーター、読者を読む |
| 管理用ログインのパスワード | `publiractl db`コマンド | すべての常駐プロセス | データベース内のすべて |
| 各ロールのパスワード | そのロールとして接続するプロセス | それ以外 | そのロールが届くもの |

Webアプリは1つのセッションキーを共有することもできますが、Composeファイルのように、それぞれに別のキーを与えてください。そうすれば、1つを入れ替えても、ログアウトするのはそのアプリのユーザーだけです。

### publiractlへのシークレットの渡し方

`publiractl`は、シークレットを引数として受け取ることはありません。プラットフォームがシークレットをファイルとしてマウントできる場合（KubernetesやDockerが`/run/secrets/`の下にマウントするように）は、そのシークレットの`--<name>-file`フラグでファイルとして渡してください。ファイルは、`publiractl`を実行する1人のユーザーだけが読めるようにでき、tmpfs上に置いておけます。環境変数の値は、それを持つプロセスから起動されたすべてのプロセスに引き継がれ、`/proc/<pid>/environ`、`docker inspect`やオーケストレーターによるタスクの記述、環境を記録するクラッシュレポートやデバッグダンプから読み取られるおそれがあります。

シークレットの`--<name>-env`フラグは、[Amazon ECS](../../2-deployments/6-ecs-fargate/index.md)のように、シークレットを環境変数としてしか設定できないプラットフォームでだけ使ってください。

### インストール環境ごとに1組のシークレット

インストール環境ごとに、すべてのシークレットを新しく1組生成してください。本番環境、ステージング環境、各開発者のマシンのそれぞれです。アクセストークンの署名鍵を共有する2つのインストール環境は、両方に存在するIDのアカウントについて、互いのセッションを受け入れます。本番環境のバックアップから復元したステージング環境のデータベースでは、これがすべてのアカウントに当てはまります。

本番環境から復元したコピーが、保存されている認証情報を読めるのは本番環境の暗号化キーがある場合だけで、それがあれば、そのコピーは本番環境のSMTPアカウント、決済プロバイダの鍵、そしてテナントが保存したその他すべての認証情報を手にします。そのようなコピーは、本番環境自身のシークレットを置いてよい場所でだけ動かし、独自のアクセストークンの署名鍵、セッションキー、トークン、ロールのパスワードを与えてください。

## 脆弱性の報告

Publira自体の脆弱性は、[セキュリティポリシー](https://github.com/publira/publira/security/policy)で説明しているとおり非公開で報告してください。公開のIssueでは決して報告しないでください。
