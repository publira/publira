このページでは、[各シークレットの置き場所](./index.md#各シークレットの置き場所)に挙げたシークレットを入れ替える手順を説明します。どの手順も、インシデントの最中より平常時のほうが落ち着いて進められるので、必要になる前に目を通しておいてください。

シークレットを最初に生成する手順は[インストール](../../2-deployments/2-installing.md#シークレットを生成する)で、保管については[バックアップと復元](../../2-deployments/9-backup-and-restore.md#シークレットの暗号化キー)で説明しています。

## シークレットの暗号化キーのローテーション

Publiraが保存する認証情報はすべて暗号化キーで暗号化されており、値ごとに暗号化に使ったキーのIDが記録されています。`PUBLIRA_SECRET_ENCRYPTION_KEYS`はプロセスが値の復号に使えるキーの一覧で、`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`は新しい値の暗号化に使うキーを指定します。ローテーションでは、キーを追加して新しい値の暗号化に使うよう切り替えたあと、保存済みの値をそのキーで暗号化し直します。一覧にないキーで暗号化された値は、まったく復号できません。

### 1. 新しいキーを追加する

キーを生成し、`k2`のように一覧にまだないIDを付けます。古いキーと並べて追加し、プライマリーキーはそのままにします。

```text
PUBLIRA_SECRET_ENCRYPTION_KEYS=k1:<old key>,k2:<new key>
PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID=k1
```

この設定で`publira server`と`publira worker`を再起動し、以降の`publiractl`コマンドもすべてこの設定で実行します。次の手順からは値がこのキーで暗号化されるので、新しいキーはすぐにシークレットの保管場所とバックアップに保存してください。

### 2. プライマリーキーにする

すべてのプロセスが両方のキーを持って動くようになったら、プライマリーキーを`k2`に変えて、もう一度再起動します。それ以降に保存される値はすべて`k2`で暗号化され、`k1`で暗号化された値も引き続き復号できます。

再起動を2回に分けるのは、`k2`をまだ持たないプロセスが、ほかのプロセスが`k2`で暗号化した値を復号できないからです。`publira server`や`publira worker`を複数のインスタンスで動かしていたり、1つずつ順に再起動したりする場合に、キーの追加と同時にプライマリーキーを切り替えると、メールの送信に失敗したりログインが拒否されたりする時間ができます。

[Docker Compose](../../2-deployments/3-docker-compose.md)の構成では、どちらの手順も、`.env`の2つの変数を編集して`docker compose up -d`を実行するだけです。再起動するのは`server`とそれに伴うワーカーで、ほかのサービスは動き続けます。

### 3. 保存済みの値を暗号化し直す

プロセスと同じ2つの変数を設定し、管理用ログインの接続で`publiractl db reseal`を実行します。

```bash
publiractl db reseal
```

このコマンドは、データベースにある暗号化された値をすべて一覧のキーで復号し、プライマリー以外のキーで暗号化されていたものをプライマリーキーで暗号化し直します。対象は次のとおりです。

- プラットフォームとすべてのテナントの認証情報
- すべてのスタッフとオペレーターの2段階認証のシークレット
- Appleでサインインの連携ごとに保存しているトークン
- Web Pushの秘密鍵
- アウトボックスのエントリーがワーカーに渡す値

値そのものは変わらないので、誰もログアウトせず、何も入力し直す必要はありません。実行中もPubliraは動き続けます。実行中に保存が行われると、保存とコマンドのどちらかがもう一方の完了を待つので、どちらも失われません。

保存済みの値に記録されているキーIDごとに、1行ずつ出力されます。

```text
KEY ID        RESEALED  ON PRIMARY  UNREADABLE
k1            42        0           0
k2 (primary)  0         3           0
```

`RESEALED`はそのキーで暗号化されていて今回プライマリーキーで暗号化し直した値の数、`ON PRIMARY`はもともとプライマリーキーで暗号化されていた値の数、`UNREADABLE`は一覧のどのキーでも復号できない値の数です。何も書き込まずに同じ表を確認するには、`publiractl db reseal --dry-run`を実行します。

[Docker Compose](../../2-deployments/3-docker-compose.md)の構成では、`publiractl`サービスに管理用の接続と`.env`のキーがすでに設定されています。

```bash
docker compose run --rm publiractl db reseal
```

### 4. 古いキーは使われなくなってから削除する

`k1`を一覧から削除してよいのは、`db reseal`が`0`で終了し、`UNREADABLE`の列に値が1つも残っていないときだけです。この状態でもう一度実行すると、出力はプライマリーキーの1行だけになり、そこに数えられた値はすべて`k1`なしで復号できます。

一覧のどのキーでも復号できない値があると、`db reseal`はその値には手を付けずにほかの値をすべて暗号化し直し、`1`で終了します。復号できなかった値はカラム、行、記録されているキーIDとともにログに出力され、表ではそのキーIDの行に数えられます。こうした値は、一覧から外したキーか、同じIDを付けた別のキーで暗号化されています。そのキーを一覧に戻して、コマンドをもう一度実行してください。誰もキーを持っていない値は、キーを失ったときと同じく、保存した画面で入力し直すしかありません。

キーがなくなった値は復号できません。たとえばテナント管理者の認証アプリのシークレットがまだ`k1`で暗号化されているのに`k1`を削除すると、その管理者のログインは2段階認証の段階でエラーページになります。サーバーのログには`secretcrypto: unknown key id: k1`が出力され、テナントの監査ログには、理由が`secret_undecryptable`の失敗した**ログイン時の2段階認証**が記録されます。なくなったキーで暗号化されたパスワードを使うメールも送信されません。キーを一覧に戻して再起動すれば、すべて元に戻ります。

キーが漏えいした場合は、暗号化し直すだけでは足りません。古いキーと、ローテーション前に取ったデータベースのバックアップがあれば、そのバックアップ内の値はすべて復号できてしまいます。SMTPのパスワード、バケットのアクセスキー、決済プロバイダのキーなど、認証情報そのものを発行元で新しくして、保存し直してください。プラットフォーム管理画面では、SMTPの新しいパスワードは**メール**の**パスワード**の横にある**変更する**から、新しいアクセスキーは**ストレージ**の**アクセスキーを置き換える**から入力します。詳しくは[メール](../6-email.md#設定を変更する)と[オブジェクトストレージ](../5-object-storage.md#アクセスキーをローテーションする)を参照してください。

## データベースのロールのパスワードのローテーション

ロールが一度に持てるパスワードは1つだけなので、PostgreSQLでパスワードを変更したら、そのロールで接続するプロセスをすべてすぐに再起動します。

| ロール | 接続するプロセス |
| --- | --- |
| `publira_public`、`publira_admin` | `publira server` |
| `publira_platform` | `publira server`と、プラットフォームの設定を変更する`publiractl`コマンド |
| `publira_outbox`、`publira_ticker` | `publira worker` |
| `publira_content_stats` | `publira worker`と`publiractl job` |

1. `openssl rand -hex 32`で新しいパスワードを生成します。16進数にするのは、接続URLにパスワードをエスケープせずに入れるためです。
2. 管理用ログインの接続で、そのロールのフラグだけを付けて`publiractl db roles`を実行します。ほかのロールのパスワードは変わりません。

   ```bash
   publiractl db roles --admin-password-file /run/secrets/publira-admin-db-password
   ```

   ロールごとに1行が出力され、指定したロールには`set its password`、ほかのロールには`kept its password`と表示されます。

3. 上の表に挙げたプロセスの接続URLを新しいパスワードに変更し、再起動します。

プロセスがすでに開いている接続はログインしたままなので、パスワードを変えた瞬間に何かが失敗することはありません。ただし、そのあとに開く接続は拒否されるので、2つの手順の間を空けないでください。古いパスワードのまま再起動したプロセスは起動せず、ログに`password authentication failed for user "publira_admin"`を繰り返し出力します。動いているプロセスでは`GET /readyz`がロールごとのチェックを返すので、どのロールのパスワードが合っていないかがわかります。プロセスが持っているパスワードで`db roles`をもう一度実行すれば元に戻ります。

すべてのロールを一度にローテーションするには、`db roles`に6つのフラグをすべて付けて実行し、`publira server`と`publira worker`を再起動します。

Docker Composeの構成では、パスワードは`.env`の`PUBLIRA_*_DB_PASSWORD`変数にあり、Composeファイルがそこからすべての接続URLを組み立てます。変数を変更したら、次を実行します。

```bash
docker compose run --rm publiractl db roles --admin-password-file /run/secrets/admin-db-password
docker compose up -d
```

`docker compose up -d`は、接続URLが変わったプロセスだけを再起動します。

### 管理用ログインのパスワード

管理用ログインは`publiractl`の管理対象外です。`psql`で`ALTER ROLE postgres PASSWORD '<new password>'`を実行するか、データベースのプロバイダーの機能でPostgreSQL側のパスワードを変更し、`db`コマンドの実行に使う`PUBLIRA_DB_URL`も書き換えてください。管理用ログインを使う常駐プロセスはないので、再起動するものはありません。

Docker Composeの構成では、PostgreSQLが`PUBLIRA_POSTGRES_PASSWORD`を読むのはボリュームを作成するときだけなので、`.env`を変更するだけでは何も変わりません。`docker compose exec postgres psql -U postgres -d publira`で`ALTER ROLE`を実行してから、`.env`に同じ値を設定してください。次に`docker compose up -d`を実行したときは、変数が変わった`postgres`コンテナが再起動するので、すべてのプロセスが数秒間止まります。

## 署名キーとトークンのローテーション

これらの値はプロセスの起動時に読み込まれるので、値を持つすべてのプロセスに新しい値を設定し、まとめて再起動すればローテーションは完了です。どれもデータベースには保存されず、入れ替えたあとに古い値を取っておく必要もありません。

| 値 | 変更する場所 | 変更による影響 |
| --- | --- | --- |
| `PUBLIRA_AUTH_JWT_SECRET` | `publira server` | 全員がログアウトします。すべてのテナントのサイトとモバイルアプリの読者、すべてのテナント管理画面のスタッフ、プラットフォーム管理画面のオペレーターが対象です |
| 1つのWebアプリの`PUBLIRA_AUTH_SECRET` | そのWebアプリ | そのアプリのユーザーだけがログアウトします |
| キャッシュ再検証トークン | `publira server`、`publira worker`、すべてのWebアプリ | 誰もログアウトしません |
| Webサービストークン | `publira server`、`web-admin`、`web-platform` | 誰もログアウトしません |

Docker Composeの構成では、`.env`の`PUBLIRA_AUTH_JWT_SECRET`、`PUBLIRA_WEB_STOREFRONT_AUTH_SECRET`、`PUBLIRA_WEB_ADMIN_AUTH_SECRET`、`PUBLIRA_WEB_PLATFORM_AUTH_SECRET`、`PUBLIRA_REVALIDATE_TOKEN`、`PUBLIRA_WEB_SERVICE_TOKEN`がこれらの値です。どれか1つを変更して`docker compose up -d`を実行すると、その変数を読むプロセスだけが再起動します。

### アクセストークンの署名キー

セッションはすべてこのキーで署名したアクセストークンなので、キーを新しくするとすべてのセッションが一斉に終了します。読者やスタッフがページを開くと、「セッションの有効期限が切れました。もう一度ログインしてください。」というメッセージとともにログイン画面に移ります。テナントのモバイルアプリのセッションも同じ種類のトークンなので、やはり終了します。2段階認証のログインの途中だったスタッフは、パスワードの入力からやり直します。

エピソードの画像へのリンクにも、同じキーで署名した有効期間の短いトークンが付いています。テナントのサイトは無料エピソードのページをリンクごと最大1時間キャッシュするので、そのページが作り直されるまで、無料エピソードの画像が読み込めないことがあります。

このキーか、いずれかのセッションキーが漏えいしたおそれがあるときは、必ずこのキーをローテーションしてください。セッションCookieに入っているアクセストークンは1日有効で、それより早く無効にするには署名キーを変えるしかありません。

### Webアプリのセッションキー

各Webアプリは、自分の`PUBLIRA_AUTH_SECRET`でセッションCookieを暗号化します。キーを新しくするとそのアプリが暗号化したCookieはすべて読めなくなり、ユーザーはメッセージなしでログイン画面に移ります。ほかのアプリのセッションはそのままです。`web-storefront`のキーを替えると、読者はサイトからはログアウトしますが、モバイルアプリではログインしたままです。進行中だったAppleやGoogleでのログインは取り消されます。`web-admin`のキーを替えると、進行中だった2段階認証のログインも取り消されます。

値は32バイト以上必要で、使われるのは先頭の32バイトだけです。古い値の末尾だけを書き換えるのではなく、`openssl rand -base64 32`でまったく新しい値を生成してください。

### キャッシュ再検証トークン

`publira server`と`publira worker`はWebアプリのキャッシュ済みページを破棄するとき、リクエストにこのトークンを付けます。各Webアプリは、自分のトークンと一致しないリクエストを拒否します。双方のトークンが食い違っている間は破棄のリクエストがすべて`401`で拒否され、ワーカーは試行のたびに`revalidate endpoint returned status=401`を含む`outbox event retry scheduled`をログに出力します。ワーカーは1回の破棄をおよそ9分間再試行するので、その間にすべてのプロセスを新しいトークンで再起動すれば何も失われません。再試行を使い切った破棄の対象ページは古いままになります。詳しくは[定期ジョブとメンテナンスジョブ](../10-scheduled-jobs.md#断念されたエントリーの確認)を参照してください。

### Webサービストークン

`web-admin`と`web-platform`は、スタッフ全員に共通する情報を読み込むときにこのトークンを送ります。`publira server`のトークンと食い違っている間はこの読み込みが拒否され、どちらの管理画面もダッシュボードに「セッションが無効です。再ログインしてください。」と表示します。ログインし直しても解決しないので、3つのプロセスを同じトークンで再起動してください。
