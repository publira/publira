ここでの手順は、[各シークレットを置いてよい場所](./index.md#各シークレットを置いてよい場所)が示す各シークレットを入れ替えるものです。必要になる前に読んでおいてください。どの手順も、インシデントの最中より、落ち着いた日に行うほうが簡単です。

シークレットを最初に生成する手順は[インストール](../../2-deployments/2-installing.md#シークレットを生成する)に、それらを保管する手順は[バックアップと復元](../../2-deployments/9-backup-and-restore.md#シークレットの暗号化キー)にあります。

## シークレット暗号化キーの入れ替え

インストール環境が保存するすべての認証情報は暗号化キーで封じられ、封じられた各値は、それを封じたキーを示します。`PUBLIRA_SECRET_ENCRYPTION_KEYS`は、プロセスが値を開くのに使えるすべてのキーの一覧で、`PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID`は、新しい値を封じるのに使うキーを示します。入れ替えとは、キーを追加し、それで封じるようにし、保存されている値をそのキーに移すことです。キーがもう一覧にない値は、まったく開けません。

### 1. 新しいキーを追加する

キーを生成し、`k2`のように、一覧にまだないIDを付けます。古いキーの横に追加し、プライマリーキーはそのままにしておきます。

```text
PUBLIRA_SECRET_ENCRYPTION_KEYS=k1:<old key>,k2:<new key>
PUBLIRA_SECRET_ENCRYPTION_PRIMARY_KEY_ID=k1
```

これを付けて`publira server`と`publira worker`を再起動し、以降のすべての`publiractl`コマンドでもこれを使ってください。新しいキーはすぐにシークレットストアとバックアップに保管してください。次の手順からは、値がそのキーで封じられます。

### 2. プライマリーキーにする

すべてのプロセスが両方のキーを持って動くようになったら、プライマリーキーを`k2`に変更し、もう一度再起動します。それ以降に保存されるすべての値は`k2`で封じられ、`k1`で封じられたすべての値も引き続き開けます。

2回の再起動を分けているのは意図的です。まだ`k2`を持っていないプロセスは、ほかのプロセスがすでにそのキーで封じた値を開けません。そのため、`publira server`や`publira worker`が複数のインスタンスで動いている間や、1つずつ順に再起動する間に、同じ手順でプライマリーキーを切り替えると、メールが失敗したりログインが拒否されたりする時間帯が生じます。

[Docker Compose](../../2-deployments/3-docker-compose.md)のインストール環境では、各手順は`.env`の2つの変数の編集と、それに続く`docker compose up -d`です。これは`server`を、それとともにワーカーを再起動し、残りは動かしたままにします。

### 3. 保存されている値を封じ直す

プロセスが今持っているのと同じ2つの変数を付けて、管理用ログインの接続で`publiractl db reseal`を実行します。

```bash
publiractl db reseal
```

これは、データベース内の封じられたすべての値を一覧のキーで開き、プライマリー以外のキーを示す値をそれぞれプライマリーキーで封じ直します。対象は、プラットフォームとすべてのテナントの認証情報、すべてのスタッフとオペレーターの2段階認証のシークレット、Appleでサインインの各連携が保持するトークン、Web Pushの秘密鍵、そしてアウトボックスのエントリーがワーカーに運ぶ値です。値自体は変わらないので、誰もログアウトせず、誰も何かを入力し直す必要はありません。実行中もインストール環境はサービスを提供し続けます。その間に届いた保存は、コマンドを待つか、コマンドがその保存を待つので、どちらも失われません。

コマンドは、保存されている値が示すキーIDごとに1行を出力します。

```text
KEY ID        RESEALED  ON PRIMARY  UNREADABLE
k1            42        0           0
k2 (primary)  0         3           0
```

`RESEALED`は、そのキーが封じていて、今はプライマリーキーが封じている値の数、`ON PRIMARY`は、もともとプライマリーキーが封じていた値の数、`UNREADABLE`は、一覧のどのキーでも開けない値の数です。何も書き込まずに同じ表を確認するには、`publiractl db reseal --dry-run`を実行してください。

[Docker Compose](../../2-deployments/3-docker-compose.md)のインストール環境では、`publiractl`サービスがすでに管理用の接続と`.env`のキーを持っています。

```bash
docker compose run --rm publiractl db reseal
```

### 4. 古いキーは、何も使わなくなってから削除する

`k1`を一覧から削除するのは、`db reseal`が`0`で終了し、`UNREADABLE`の列に値が1つも残っていないときだけにしてください。その後にもう一度実行すると、プライマリーキーの1行だけが出力され、そこで数えられるすべての値は`k1`なしで開けます。

一覧のどのキーでも開けない値があると、`db reseal`はその値をそのままにし、それ以外のすべての値を封じて、`1`で終了します。そのログには、そのような各値が、そのカラム、その行、それが示すキーIDとともに示され、表ではそのキーIDの下に数えられます。その値は、もう一覧にないキーで、または同じIDの別のキー素材で封じられたものです。そのキーを一覧に戻して、もう一度コマンドを実行してください。もう誰もキーを持っていない値は、キーを失った場合と同じく、保存した場所で入力し直す必要があります。

キーがなくなった値は開けません。テナント管理者の認証アプリのシークレットがまだそのキーで封じられているのに`k1`を削除すると、その管理者のログインは2段階認証の手順でエラーページになって失敗し、サーバーは`secretcrypto: unknown key id: k1`をログに書き、テナントの監査ログには、理由`secret_undecryptable`とともに失敗した**ログイン時の2段階認証**が記録されます。失われたキーで封じられたパスワードを必要とするメールも送られません。そのキーを一覧に戻して再起動すれば、これらはすべて元に戻ります。

キーが漏えいしたときは、封じ直すだけでは不十分です。古いキーと、入れ替えより前に取ったデータベースのバックアップを持っている者は、そのバックアップ内のすべての値を開けます。そのため、認証情報そのものを、それを発行した場所で入れ替え（新しいSMTPパスワード、バケットの新しいアクセスキー、決済プロバイダの新しい鍵など）、新しいものを保存してください。プラットフォーム管理画面では、[メール](../6-email.md#変更する)と[オブジェクトストレージ](../5-object-storage.md#アクセスキーをローテーションする)で説明しているとおり、新しいSMTPパスワードは**メール**の**パスワード**の横にある**変更する**で、新しいアクセスキーは**ストレージ**の**アクセスキーを置き換える**で入力します。

## データベースのロールのパスワードの入れ替え

ロールが持てるパスワードは一度に1つなので、入れ替えは、PostgreSQLでの変更と、そのロールとして接続するすべてのプロセスの速やかな再起動です。

| ロール | 接続するもの |
| --- | --- |
| `publira_public`、`publira_admin` | `publira server` |
| `publira_platform` | `publira server`、およびプラットフォームの設定を変更する`publiractl`コマンド |
| `publira_outbox`、`publira_ticker` | `publira worker` |
| `publira_content_stats` | `publira worker`、および`publiractl job` |

1. `openssl rand -hex 32`で新しいパスワードを生成します。接続URLはパスワードをエスケープせずに含むので、16進数にしています。
2. 管理用ログインの接続で、そのロールのフラグだけを付けて`publiractl db roles`を実行します。ほかのすべてのロールはパスワードを保ちます。

   ```bash
   publiractl db roles --admin-password-file /run/secrets/publira-admin-db-password
   ```

   コマンドはロールごとに1行を出力し、指定したロールには`set its password`、それ以外には`kept its password`と出ます。

3. 上の表のすべてのプロセスの接続URLを新しいパスワードに変更し、再起動します。

プロセスがすでに開いている接続はログインしたままなので、パスワードを変更した瞬間に何かが失敗することはありません。その後にプロセスが開く接続は拒否されるので、2つの手順の間を空けないでください。古いパスワードで再起動したプロセスはまったく起動せず、そのログには`password authentication failed for user "publira_admin"`が繰り返し出ます。再び動き出すと、その`GET /readyz`はロールごとに1つのチェックを示すので、不一致があればそこに名前が出ます。プロセスが持っているパスワードで`db roles`をもう一度実行すれば、元に戻ります。

すべてのロールを一度に入れ替えるには、`db roles`に6つのフラグをすべて与え、`publira server`と`publira worker`を再起動してください。

Docker Composeのインストール環境では、パスワードは`.env`の`PUBLIRA_*_DB_PASSWORD`変数で、Composeファイルはそれらからすべての接続URLを組み立てます。変数を変更してから、次を実行します。

```bash
docker compose run --rm publiractl db roles --admin-password-file /run/secrets/admin-db-password
docker compose up -d
```

`docker compose up -d`は、接続URLが変わったプロセスだけを再起動します。

### 管理用ログインのパスワード

`publiractl`は管理用ログインを管理しません。そのパスワードは、`psql`での`ALTER ROLE postgres PASSWORD '<new password>'`か、データベースプロバイダーを通じてPostgreSQLで変更し、そのあと`db`コマンドの実行に使う`PUBLIRA_DB_URL`を変更してください。常駐プロセスはこれを使わないので、何も再起動しません。

Docker Composeのインストール環境では、PostgreSQLは`PUBLIRA_POSTGRES_PASSWORD`をボリュームの作成時にしか読まないので、`.env`を変更するだけでは何も変わりません。`docker compose exec postgres psql -U postgres -d publira`で`ALTER ROLE`を実行してから、`.env`に同じ値を設定してください。次の`docker compose up -d`は、変数が変わったので`postgres`コンテナを再起動し、そのためにすべてのプロセスが数秒間中断されます。

## 署名鍵とトークンの入れ替え

これらの値は、プロセスの起動時に読まれます。入れ替えは、その値を持つすべてのプロセスに新しい値を与え、まとめて再起動するだけです。どれもデータベースには保存されず、入れ替えたあとに古い値を保管しておく必要もありません。

| 値 | 変更する場所 | 変更の影響 |
| --- | --- | --- |
| `PUBLIRA_AUTH_JWT_SECRET` | `publira server` | 全員がログアウトします。すべてのテナントのサイトとモバイルアプリの読者、すべてのテナント管理画面のスタッフ、プラットフォーム管理画面のオペレーターです |
| 1つのWebアプリの`PUBLIRA_AUTH_SECRET` | そのWebアプリ | そのアプリのユーザーだけがログアウトします |
| キャッシュ再検証トークン | `publira server`、`publira worker`、すべてのWebアプリ | 誰もログアウトしません |
| Webサービストークン | `publira server`、`web-admin`、`web-platform` | 誰もログアウトしません |

Docker Composeのインストール環境では、変数は`.env`の`PUBLIRA_AUTH_JWT_SECRET`、`PUBLIRA_WEB_STOREFRONT_AUTH_SECRET`、`PUBLIRA_WEB_ADMIN_AUTH_SECRET`、`PUBLIRA_WEB_PLATFORM_AUTH_SECRET`、`PUBLIRA_REVALIDATE_TOKEN`、`PUBLIRA_WEB_SERVICE_TOKEN`です。1つを変更すると、`docker compose up -d`は、それを読むプロセスをちょうど再起動します。

### アクセストークンの署名鍵

すべてのセッションはこの鍵で署名されたアクセストークンなので、新しい鍵にすると、すべてのセッションが一度に終わります。ページを開いた読者やスタッフは、「セッションの有効期限が切れました。もう一度ログインしてください。」というメッセージとともにログイン画面に送られます。テナントのモバイルアプリのセッションも同じ種類のトークンなので、これも終わります。2段階認証によるログインの途中だったスタッフは、パスワードからやり直します。

エピソードの画像へのリンクには、同じ鍵で署名された短期間有効なトークンが付いています。テナントのサイトは、無料エピソードのページをリンクを含めて最大1時間キャッシュするので、そのページが再構築されるまで、無料エピソードの画像を読み込めないことがあります。

この鍵は、漏えいしたおそれがあるとき、そしてセッションキーが漏えいしたおそれがあるときは必ず入れ替えてください。セッションCookieは1日有効なアクセストークンを運んでおり、それをより早く終わらせられるのは新しい署名鍵だけです。

### Webアプリのセッションキー

各Webアプリは、自身の`PUBLIRA_AUTH_SECRET`でセッションCookieを封じます。新しいキーにすると、そのアプリが封じたすべてのCookieが読めなくなるので、そのアプリのユーザーはメッセージなしでログイン画面に移りますが、ほかのアプリはセッションを保ちます。`web-storefront`のキーを入れ替えると、読者はサイトからはログアウトしますが、モバイルアプリからはログアウトせず、進行中だったAppleでサインインやGoogleでログインは取り消されます。`web-admin`のキーを入れ替えると、進行中だった2段階認証によるログインも取り消されます。

値は少なくとも32バイト必要で、使われるのは先頭の32バイトだけです。そのため、古い値の末尾を書き換えるのではなく、`openssl rand -base64 32`でまったく新しい値を生成してください。

### キャッシュ再検証トークン

`publira server`と`publira worker`は、Webアプリのキャッシュ済みページを破棄するすべてのリクエストにこのトークンを付けて送り、各Webアプリは、自分のトークンと一致しないリクエストを拒否します。双方が一致しない間は、すべての破棄が`401`で拒否され、ワーカーは各試行を`revalidate endpoint returned status=401`を伴う`outbox event retry scheduled`としてログに書きます。ワーカーは各破棄をおよそ9分間試行し続けるので、その間にすべてのプロセスを新しいトークンで再起動すれば何も失われません。試行回数を使い切った破棄は、[定期ジョブとメンテナンスジョブ](../10-scheduled-jobs.md#断念されたものを確認する)で説明しているとおり、対象のページをそのままにします。

### Webサービストークン

`web-admin`と`web-platform`は、すべてのスタッフに共通して見えるものを読むためにこのトークンを送ります。`publira server`が別のトークンを持っている間は、それらの読み取りが拒否され、どちらの管理画面もダッシュボードに「セッションが無効です。再ログインしてください。」と表示します。ログインし直しても解決しません。3つすべてを同じトークンで再起動してください。
