インストール環境は、どのテナントのものでもないいくつかの設定で動いています。新しいテナントが最初に使う言語、タイムゾーン、通貨、1人の読者や1つのアドレスがプラットフォームに過剰な負荷をかけないようにする上限、そして期限のある記録を保持する期間です。このページでは、それぞれのグループが何を防ぐのか、どう変更するのか、そしてテナントの管理者が自分のテナントについてどの部分を変更できるのかを説明します。

ポリシーと保持期間の値にはそれぞれ組み込みの既定値があり、何も保存していないインストール環境はその既定値で動きます。既定タイムゾーンと既定通貨も同様です。既定タイムゾーンは保存されるまで`UTC`で、既定通貨は`publiractl setup`に指定したもの、指定しなかった場合は`USD`、このリリースより前から動いているインストール環境では`JPY`です。既定言語には組み込みの既定値がありません。`publiractl setup`が既定言語を保存し、プラットフォーム管理画面のセットアップ画面がそれを最初のオペレーターが選んだ言語で置き換えました。各値の範囲と組み込みの既定値は、`publiractl`リファレンスの[`policy`](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#policy)と[保持期間](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#retention-periods)にあり、このページでは繰り返しません。

## 設定の場所

どのグループも、プラットフォーム管理画面からでも、[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明どおりに実行する`publiractl`からでも設定できます。

| グループ | プラットフォーム管理画面 | `publiractl` |
| --- | --- | --- |
| 既定の言語、タイムゾーン、通貨 | **プラットフォーム**の下の**一般** | `platform set`、`platform show` |
| 2段階認証、テナントによるコインの発行の可否、ログイン、パスワード、購入、チケット、メールの上限、使い捨てメールドメインのリスト | **ポリシー**の下の**セキュリティ** | `policy set`、`policy show` |
| コメント、報告、評価、問い合わせ、ビューアー、通知設定の上限 | **ポリシー**の下の**コミュニティ** | `policy set`、`policy show` |
| 期限のある記録を保持する期間 | **ポリシー**の下の**保持期間** | `retention set`、`retention show` |

![プラットフォーム管理画面のサイドバー。プラットフォームの下の一般、外部サービスの下のメール、ストレージ、検索、Web Push、ポリシーの下のセキュリティ、コミュニティ、保持期間。](./platform-policies-sidebar.png)

どちらも同じコードを通して書き込みます。`set`コマンドはフラグで指定した値だけを変更してほかの値を保持し、プラットフォーム管理画面のページはそのページのすべての値を一度に保存します。何も変わらない保存は記録されません。それ以外の保存は、**監査ログ**に**プラットフォーム設定を更新**、**プラットフォームのポリシーを更新**、**保持期間の既定値を更新**として記録されます。**セキュリティ**、**コミュニティ**、**保持期間**のページは、自分が見ていない保存を上書きしません。ページを開いたあとに誰かがそのページを保存していた場合、プラットフォーム管理画面は「別のオペレーターが設定を変更したため保存されませんでした。再読み込みしてもう一度お試しください。」と表示して保存を拒否します。**セキュリティ**と**コミュニティ**は1つのポリシーとして保存されるので、どちらを保存する場合も、もう一方が古い内容であれば拒否されます。**一般設定**の3つのフォームはこの確認を行いません。それぞれ、保存されている内容にかかわらず自分の値を保存し、ほかの値は保存されているまま残します。`publiractl`は書き込む直前に保存済みの値を読み込み、その間に別の保存が入ると`1`で終了します。そのあと同じコマンドを再び実行すると、その保存の上にフラグの内容が適用されます。

これらのページを保存できるのはオペレーターまたはスーパー管理者です。監査担当にも同じフォームが表示されますが、保存は拒否されます。

ポリシーが保存されるまで、プラットフォーム管理画面のダッシュボードの**設定の状況**カードには「サインイン、不正利用対策、データ保持期間には組み込みの既定値が適用されています。」と表示されます。これは正常に動いているインストール環境であり、未完成の状態ではありません。値を変更するのは、組み込みの値がプラットフォームに合わない場合だけにしてください。

## プラットフォームの既定値

**一般設定**には3つの値があり、それぞれに保存ボタンがあります。

![一般設定。既定言語と既定言語を保存、既定タイムゾーンと既定タイムゾーンを保存、そしてその通貨で販売しているテナントに購入があるため読み取り専用になっている既定通貨と既定通貨を保存。](./platform-policies-general.png)

**既定言語**は、言語を選んでいないオペレーターにプラットフォーム管理画面をログイン画面も含めて表示する言語であり、パスワードの再設定など、プラットフォーム管理画面がオペレーターに送るメールの言語です。どのテナントの言語も決めません。[テナント](./2-tenants.md#テナントを作成する前に)で説明するとおり、各テナントには作成時にそれぞれの既定言語が与えられます。この値は最初のオペレーターがセットアップ画面で選んだものです。

**既定タイムゾーン**は、タイムゾーンを指定せずに作成された新しいテナントが最初に使うタイムゾーンであり、プラットフォーム管理画面が日時を表示し、日付を数えるタイムゾーンです。テナントは作成時のタイムゾーンを保持するので、既定を変更しても影響を受けるのはそのあとに作成されたテナントだけです。テナントのタイムゾーンは、そのテナントの管理者がテナント管理画面から変更します。この値は最初のオペレーターがセットアップ画面で選んだもので、セットアップ画面ではそのオペレーターのブラウザーのタイムゾーンが提示されました。

**既定通貨**は、管理者が**決済設定**を保存していないすべてのテナントが販売に使う通貨です。つまり、そのテナントの価格はこの通貨で入力・表示されます。決済設定を保存したテナントはそこで保存した通貨を使い続け、既定はもうそのテナントには及びません。一覧では、通貨を名前か、`EUR`のようなISO 4217コードで探します。この通貨で販売しているテナントで一度でも販売が行われると、既定通貨は変更できなくなります。その場合、欄は読み取り専用になってその理由を表示し、`publiractl`も変更を拒否します。これは、そうしたテナントのそれぞれが独自の通貨で決済設定を保存するまで続きます。`publiractl setup`とプラットフォーム管理画面のセットアップ画面は、インストール環境のセットアップ時に既定通貨を尋ねるので、そのときに選んでおいてください。

コマンドラインでは次のようにします。

```bash
publiractl platform set --default-locale en --default-timezone America/New_York --default-currency USD
```

## セキュリティ

**セキュリティポリシー**には、すべてのテナントに同じように適用され、どのテナントも変更できない値があります。それぞれが、アカウント、メールを送る操作、またはお金に関わる操作を守ります。

### テナント管理者の2段階認証

**テナント管理者に多要素認証を必須にする**（`--mfa-required-for-tenant-admin`）を有効にすると、テナント管理者はパスワードだけではテナント管理画面にログインできなくなります。認証アプリを設定していない管理者が締め出されることはありません。パスワードの入力後、管理画面に**2段階認証を設定する**が表示され、認証アプリを登録した時点でログインが完了します。画面にはテナントがそれを求めていると表示されますが、実際にはプラットフォームの要件であり、テナントがオフにすることはできません。

![セキュリティのテナント管理者に多要素認証を必須にするチェックボックス。](./platform-policies-mfa-required.png)

これはすべてのテナントに一斉に適用され、**テナント管理者**のロールにだけ適用されます。編集担当と監査担当が求められることはありません。各管理者の次回のログインから有効になり、すでに開いているセッションには適用されません。管理者はアカウント設定から自分の認証アプリをオフにすることもでき、その場合は次回のログイン時に再び設定を求められます。

プラットフォーム管理画面のオペレーター自身はこの設定の対象外です。オペレーターには次の設定があります。

### プラットフォームのオペレーターの2段階認証

**Platform Consoleのすべてのオペレーターに2段階認証を必須にする**（`--mfa-required-for-platform-operator`）を有効にすると、オペレーターはパスワードだけではプラットフォーム管理画面にログインできなくなります。認証アプリを設定していないオペレーターが締め出されることはありません。パスワードの入力後、管理画面に**2段階認証を設定する**が表示され、認証アプリを登録してリカバリーコードを表示された時点でログインが完了します。

![セキュリティのPlatform Consoleのすべてのオペレーターに2段階認証を必須にするチェックボックス。](./platform-policies-operator-mfa-required.png)

どのオペレーターもすべてのテナントのデータを読めるので、これは**監査担当**を含むすべてのロールに適用されます。各オペレーターの次回のログインから有効になり、すでに開いているセッションには適用されません。オペレーターは**アカウント設定**から自分の認証アプリをオフにすることもでき、その場合は次回のログイン時に再び設定を求められます。誰かが有効にするまではオフです。`publira server`に`PUBLIRA_SECRET_ENCRYPTION_KEYS`がないインストール環境では、これを有効にすることは拒否されます。そこではどのオペレーターも認証アプリを設定できず、誰もログインしてこれを再びオフにできなくなるためです。

### テナントが発行するコイン

**テナントにコインの発行を許可する**（`--tenant-coins-allowed`）を有効にすると、テナントがコインを発行できるようになります。コインは、テナントの読者が前もって購入し、そのテナントのエピソードに使う残高です。新しいインストール環境でも、この設定がなかったリリースからアップグレードしたインストール環境でも、誰かが有効にするまではオフです。

![セキュリティのテナントにコインの発行を許可するチェックボックスと、その下の説明。](./platform-policies-tenant-coins.png)

コインは前払いの価値を保存する手段なので、あなたと各テナントの所在地によっては、前払式支払手段、電子マネー、資金移動、ギフトカードに関する法律の対象になることがあります。法域によっては、コインを販売するテナントではなく、インストール環境を運営するプラットフォームが、そうした法律の対象となる当事者とみなされます。テナントにコインの発行を許可しても自分が発行者にならないことを確認するか、発行者として必要なことを済ませるまでは、オフのままにしてください。

有効にしても、読者に見えるものは何も変わりません。[コイン](../4-console/9-coins.md)で説明するとおり、テナントは引き続き、管理画面の**決済** › **コイン**で自分のテナントのコインを有効にする必要があります。チェックボックスを外すか`--tenant-coins-allowed=false`で無効にすると、各テナント自身の設定にかかわらず、すべてのテナントが一斉に停止されます。どのテナントもコインを販売せず、どの読者もコインを使わなくなりますが、各読者の残高は保たれます。再び有効にすると、各テナントには保存していた設定が戻ります。

### レート制限

各上限は1分あたりまたは1時間あたりの回数で、それとは別に1日あたりの回数があり、1日あたりの回数が短いほうの回数より少なくなることはありません。上限を超えたリクエストは、その時間枠が過ぎるまで拒否されます。時間枠は読者の最初のリクエストから始まるのではなく、時計に合わせて固定されているので、回数は毎分または毎時の区切りで、1日あたりの回数はUTCの午前0時に、数え直しになります。

| セキュリティのページの項目 | 守るもの |
| --- | --- |
| 「**パスワード確認数（1分）**」と**パスワード確認数（1日）** | 読者が、パスワードの変更、メールアドレスの変更、アカウントの削除のために現在のパスワードを入力すること。それぞれアカウントごとに数え、正しいパスワードを入力すると回数がリセットされるので、1回打ち間違えた読者ではなく、手にしたセッションのパスワードを推測しようとする人の動きを遅らせます |
| 「**アドレスごとのメール要求数（1時間）**」と**アドレスごとのメール要求数（1日）** | メールを送るフォームから1つのアドレスに送られるメール。読者の会員登録とメールアドレスの確認、3つのアプリすべてでのパスワードの再設定とメールアドレスの変更、スタッフの招待、プラットフォーム管理画面からの管理者の招待とオペレーターの追加、問い合わせへの返信です。アドレスはそのテナント内、またはプラットフォーム管理画面内で数え、`+tag`の付いたアドレスはそれを除いたアドレスとして数えます |
| 「**送信元ごとのメール要求数（1時間）**」と**送信元ごとのメール要求数（1日）** | 同じメールを、それを要求したクライアントのアドレスごとに、すべてのアドレスとすべてのテナントをまたいで数えたもの。これにより、1つのクライアントが見知らぬ人の長いリストにメールを送ることを防ぎます |
| 「**読者ごとのアプリ内課金の確定数（1分）**」と**読者ごとのアプリ内課金の確定数（1日）** | 1人の読者が、AppleやGoogleで検証するためにサーバーに渡すストアのトランザクション |
| 「**読者ごとの待てば無料チケットの利用数（1分）**」と**読者ごとの待てば無料チケットの利用数（1日）** | 1人の読者による、待てば無料チケットを使うリクエスト。使われたチケットはもともとシリーズの回復時間で制限されているので、この上限は拒否される試行の回数を抑えます |

![セキュリティのレート制限。パスワード確認、アドレスごとと送信元ごとのメール要求、アプリ内課金の確定、待てば無料チケットの利用が、それぞれ1分または1時間と1日の単位で表示されている。](./platform-policies-rate-limits.png)

このほかに、同じ種類の上限が8つありますが、まだセキュリティのページに欄がありません。改訂版への同意を求められた読者が、テナントの利用規約とプライバシーポリシーに送る同意（`publiractl policy set --legal-page-agreement-per-minute`と`--legal-page-agreement-per-day`で設定しない限り1分あたり10回、1日あたり50回）、1人の読者が自分のアカウントにAppleまたはGoogleのアカウントを連携するリクエスト（`--identity-link-per-minute`と`--identity-link-per-day`で設定しない限り1分あたり5回、1日あたり20回）、1人の読者が自分のアイコンをアップロード、選択、削除する回数（`--icon-change-per-minute`と`--icon-change-per-day`で設定しない限り1分あたり5回、1日あたり20回）、1人の読者がパスキーの登録やパスキーでのリクエストの確認を開始する回数、またはパスキーの名前を変更したり削除したりする回数（`--passkey-per-minute`と`--passkey-per-day`で設定しない限り1分あたり10回、1日あたり50回）、1人の読者が開始するシリーズの残りの購入手続き（`--series-remainder-checkout-per-minute`と`--series-remainder-checkout-per-day`で設定しない限り1分あたり10回、1日あたり50回）、1人の読者が開始するサブスクリプションの購入手続き（`--subscription-checkout-per-minute`と`--subscription-checkout-per-day`で設定しない限り1分あたり10回、1日あたり50回）、1人の読者がコインで支払うエピソード（`--coin-payment-per-minute`と`--coin-payment-per-day`で設定しない限り1分あたり20回、1日あたり500回）、そして1人の読者が開始するエピソード、巻、コインパックの購入手続きをまとめて数えたもの（`--purchase-checkout-per-minute`と`--purchase-checkout-per-day`で設定しない限り1分あたり10回、1日あたり100回）です。セキュリティのページを保存しても、これらの設定値はそのまま保持されます。

招待は1件ごとに1回のリクエストとして数えます。**テナント作成**の**初期管理者メール**のアドレスもそれぞれ数え、それらはすべてテナントが作成される前に数えられます。1つでも上限を超えると、テナントは作成されず、メールも送られません。`publiractl`はフォームを通して送らないので、これらの上限のどれにも数えられません。

クライアントのアドレスは、[Publiraが信頼するプロキシ](../2-deployments/4-edge/index.md#publiraが信頼するプロキシ)で説明するとおり、`publira server`が`Forwarded`または`X-Forwarded-For`から、信頼するプロキシを飛ばして見つけたアドレスです。オフィスや携帯電話会社のゲートウェイのように1つのアドレスを共有している読者は、そのアドレスの送信元ごとの回数とクライアントごとの回数を共有します。

### ログインの試行

このほかに2つの上限が、テナントのサイト、テナント管理画面、プラットフォーム管理画面へのパスワードでのログインそのものを守ります。これらは**セキュリティ**のページでレート制限の次にあり、同じ方法で数えられます。

| セキュリティのページの項目 | フラグ | 守るもの |
| --- | --- | --- |
| 「**アドレスごとのログイン試行数（1分）**」と**アドレスごとのログイン試行数（1日）** | `--login-attempts-per-account-per-minute`と`--login-attempts-per-account-per-day` | 1つのアドレスに対して試されたパスワード。アドレスはそのテナント内（テナントのサイトとテナント管理画面で1つの回数を共有します）、またはプラットフォーム管理画面内で数えます。正しいパスワードでログインすると回数がリセットされるので、打ち間違えた人ではなく、1つのアカウントのパスワードを推測しようとする人の動きを遅らせます |
| 「**送信元ごとのログイン失敗数（1時間）**」と**送信元ごとのログイン失敗数（1日）** | `--login-attempts-per-source-per-hour`と`--login-attempts-per-source-per-day` | 1つのクライアントのアドレスからの、すべてのアドレス、すべてのテナント、プラットフォーム管理画面をまたいだログインの失敗。これにより、1つのクライアントが長いアドレスのリストに対してパスワードを試すことを防ぎます。正しいパスワードでのログインは数えません |

![セキュリティのログイン試行の上限。アドレスごとのログイン試行数（1分と1日）と、送信元ごとのログイン失敗数（1時間と1日）。](./platform-policies-sign-in-attempts.png)

どちらかの上限を超えた試行は、パスワードを確認する前に拒否されます。拒否のされ方はそのアドレスのアカウントがあるかどうかにかかわらず同じなので、推測しようとする人には、どのアドレスが登録されているかについて何も伝わりません。その際、ログイン画面には、メールアドレスまたはパスワードが正しくないという表示ではなく、「短時間に操作が集中しています。少し時間をおいて再試行してください。」と表示されます。パスワードが正しかった可能性も十分にあるためです。2段階認証はパスワードのあとの別の確認であり、これらの上限はそのコードを数えません。

アカウントごとの上限があるために、アドレスを知っている人なら誰でも、間違ったパスワードでその回数を使い切ることで、時間枠が過ぎるまでアドレスの持ち主がパスワードでログインできないようにすることもできます。AppleやGoogleでのログインと、パスワードの再設定はその影響を受けません。1日あたりの値は、誰かのスクリプトのせいで丸1日パスワードでログインできなくなることがない程度に、十分大きくしておいてください。

### 回数を保持する場所

上限は`publira server`が、その`PUBLIRA_REDIS_URL`で指定されたValkeyまたはRedisのサーバーで数えます。このサーバーは[インストール](../2-deployments/2-installing.md#サービスを用意する)で用意したものです。`publira server`のすべてのインスタンスがその回数を共有するので、実行するインスタンスの数にかかわらず、上限はインストール環境全体で守られます。

この変数がないと、各インスタンスは自分のメモリーで数え、ログにはその旨が何も出ません。その場合、リクエストが3つのインスタンスに分散した読者には上限の3倍が許され、再起動するとすべての回数が0から始まります。インスタンスがRedisに到達できない間も同じことが起きます。起動時に接続できなかったサーバーはエラーをログに出して単独で数え、あとで接続を失ったサーバーは警告をログに出し、接続が戻るまで単独で数え、戻ったときに再びログに出します。`publira server`のインスタンスを複数実行する場合は、そのすべてに`PUBLIRA_REDIS_URL`を設定してください。

保存した変更は、再起動なしで10秒以内に、実行中のすべてのインスタンスに届きます。

### 使い捨てメールドメインのリスト

**使い捨てメールドメインリストのURL**（`--disposable-email-domains-url`）は、`publira server`が使い捨てメール用のドメインのリストを読み込む場所です。Publiraにはリストが同梱されていないので、URLを指定するまでリストはありません。

![セキュリティの使い捨てメールドメインリストのURLと、その下の説明。](./platform-policies-disposable-email-domains.png)

リストは1行に1つのドメインを書いたプレーンテキストのファイルで、空行と`#`で始まる行は無視されます。これは[disposable-email-domains](https://github.com/disposable-email-domains/disposable-email-domains)プロジェクトのブロックリストの形式です。リストにあるドメインは、そのサブドメインも対象にします。各インスタンスは、リストが最初に必要になったときと、その1時間後に再びリストを読み込みます。読み込みに失敗した場合や、ファイルにドメインではない行がある場合、インスタンスは最後に読み込んだリストを使い続け、警告をログに出します。以前のリストがない場合は何も拒否せず、1時間後に再び試します。新しいURLは、保存したあとの次の照会のときに読み込まれます。

リストを保存しただけでは何も拒否されません。使い捨てのアドレスを拒否したいテナントは、管理画面の**設定**の**受け付けないメールアドレス**で**使い捨てメールのドメインを受け付けない**をオンにします。それ以降、読者はリストにあるドメインのアドレスで会員登録したり、そのようなアドレスに変更したりできなくなります。AppleやGoogleでのログインは影響を受けません。プラットフォームにリストがない場合、そのスイッチには効果がないことが表示されます。

## コミュニティ

**コミュニティの上限**は、テナントのコミュニティで読者が行うことに対する上限です。ここでの各値は、すべてのテナントの出発点であり、テナントが選べる最も緩い値でもあります。テナントは自分のテナントについて上限を厳しくすることはできますが、緩くすることはできません。

![コミュニティの上限。コメントの投稿、コメントの報告、アカウントごととクライアントごとの問い合わせ、エピソードの評価、閲覧者設定の更新、通知設定の更新が、それぞれ1分または1時間と1日の単位で表示され、重複コメントの判定時間（分）とコミュニティ上限を保存がある。](./platform-policies-community.png)

| コミュニティのページの項目 | 制限するもの |
| --- | --- |
| 「**コメント投稿数（1分）**」と**コメント投稿数（1日）** | 1人の読者が投稿するコメント |
| 「**コメント報告数（1分）**」と**コメント報告数（1日）** | 1人の読者が報告するコメント |
| 「**アカウントごとの問い合わせ数（1時間）**」と**アカウントごとの問い合わせ数（1日）** | ログインしている1人の読者がテナントの問い合わせフォームから送るメッセージ |
| 「**クライアントごとの問い合わせ数（1時間）**」と**クライアントごとの問い合わせ数（1日）** | ログインしているかどうかにかかわらず、1つのクライアントのアドレスから問い合わせフォームを通して送られるメッセージ。すべてのテナントをまたいで数えます |

これらはセキュリティの上限と同じ場所で数えられるので、[回数を保持する場所](#回数を保持する場所)の内容がこれらにも当てはまります。

## 保持期間

**保持期間の既定値**は、独自の期間を設定していないすべてのテナントについて、4種類の記録を保持する期間を決めます。各期間は日数の整数です。期間を過ぎたものは`publira worker`が自身のスケジュールで削除します。そのために何かを設定する必要はなく、`publiractl job`で同じ削除を手動で実行することもできます。

![保持期間の既定値。日数で指定する取り下げられたコメント、コンテンツイベント、日次ランキングのスナップショット、週次ランキングのスナップショットと、保持期間の既定値を保存。](./platform-policies-retention.png)

| 記録 | 内容 | 削除するジョブ | 頻度 |
| --- | --- | --- | --- |
| **取り下げられたコメント** | 投稿者が削除したコメント。そのコメントについての報告や異議申し立てが未解決の間もスタッフが読めるように保持されます。コメントに対して出された報告もコメントと一緒に削除されます | `purge-withdrawn-comments` | 1時間ごと |
| **コンテンツイベント** | 閲覧、読了、購入、お気に入り、評価、コメントの1件ずつの発生記録 | `purge-content-events` | 24時間ごと |
| **日次ランキングのスナップショット** | 各日のランキング | `purge-ranking-snapshots` | 24時間ごと |
| **週次ランキングのスナップショット** | 各週のランキング | `purge-ranking-snapshots` | 24時間ごと |

各削除ジョブは開始時に期間を読み込むので、保存した変更は次回の実行から適用されます。また、各ジョブは、現在の間隔の中でまだ実行されていなければ`publira worker`の起動時にも実行され、停止期間のあとの最初の実行では、その間に期限が切れたものをすべて削除します。

一部の記録は、設計上、期間を過ぎても残ります。

- スタッフ、または報告のしきい値によって非表示にされたコメントは、古さにかかわらず削除されません。モデレーションの判断の記録だからです。削除されるのは、投稿者が取り下げたコメントだけです。
- テナントが持つ各種類の最新のランキングは常に保持されるので、ランキングが空になることはありません。

期間の選び方は次のとおりです。

- **コンテンツイベント**は、記録されたあと2つのものの元になります。1日が終わると作られるその日の統計と、テナントが自身のタイムゾーンで終えた直近28日間から作られるおすすめです。統計はイベントより長く残るので、期間を短くしてもテナントのレポートが縮むことはありません。各ログイン済みの読者がどの日にアクティブだったかの記録も同様に長く残ります。管理画面はこの記録を使って、ある週に会員登録した読者をその後12週間追跡するので、それより短い期間でもその週の集計はできます。30日（28日に、おすすめを作る日の1日と、時計の変更で長くなる日のための1日を加えたもの）未満の期間にすると、おすすめが少ない日数から作られることになり、また統計が作られる前にその日のイベントが削除されるおそれがあるので、プラットフォームの既定でもテナント独自の期間でも拒否されます。Publiraがこれを拒否するようになる前に保存された短い期間は、30日として扱われます。
- **ランキングのスナップショット**は、時間を追った比較のために保持されます。読者に表示されるのは常に最新のものだけです。期間を短くしても、その比較でさかのぼれる範囲が短くなるだけです。
- **取り下げられたコメント**の期間は、テナントがコメントについての報告や異議申し立てを解決するのにかかる時間をカバーするようにしてください。テナント管理画面には、取り下げられた各コメントがいつ削除される予定かがスタッフ向けに表示されます。

コマンドラインでは次のようにします。

```bash
publiractl retention set --content-event-days 120
```

## テナントが変更できること

テナントの管理者は、これらの一部を、テナント管理画面の**設定** → **制限と保持**から自分のテナントについて変更できます。管理者向けの説明は[設定](../4-console/3-setup/1-settings.md#制限と保持)にあります。編集担当と監査担当にはそのページが表示されますが、保存はできません。

| グループ | テナントができること |
| --- | --- |
| **一般**：既定の言語とタイムゾーン | ここでは何もできません。各テナントは作成された時点から独自の言語とタイムゾーンを持ち、管理画面の**設定**から変更します |
| **一般**：既定通貨 | **決済設定**で独自の通貨を選べます。選ぶと、既定はもうそのテナントには及びません |
| **セキュリティ**：すべての値 | 何もできません。テナントが行う関連する選択は、使い捨てメールのドメインを拒否するかどうかだけで、拒否に使うリストはプラットフォームのものです |
| **コミュニティ**：すべての値 | どの値も厳しくできます。上限を下げるか、重複コメントの判定時間を長くします。プラットフォームの値より緩い値は拒否されます |
| **保持期間**：すべての期間 | どの期間もプラットフォームの既定より長くも短くも設定できます。範囲は1日から36500日で、**コンテンツイベント**は30日からです |

そのページでは、各グループの**プラットフォームの既定値を使う**が最初はチェックされていて、その横にプラットフォームの値が表示されます。チェックを外すと管理者はテナント独自の値を入力でき、**コミュニティの上限を保存**または**保持期間を保存**で保存します。再びチェックを入れて保存すると、そのグループはプラットフォームの値に戻ります。プラットフォームの既定値を使っているテナントは、その後の既定値の変更にすべて従います。

テナント独自の値はプラットフォームの値が変わっても残りますが、例外が1つあります。テナントのコミュニティの上限は、リクエストのたびにプラットフォームの値と比較され、厳しいほうが適用されます。そのため、プラットフォームの上限をテナント独自の値より低くすると、そのテナントの上限も厳しくなります。プラットフォームの上限を再び上げても、より厳しい値を選んだテナントの上限が緩むことはありません。保持期間にはこのような比較はなく、テナント独自の期間がそのまま使われます。

テナントによる変更は、そのテナントの管理画面の監査ログに**コミュニティの上限更新**と**保持期間更新**として記録されます。
