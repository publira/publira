インストールが受け持つ出版社は、1社ごとに1つのテナントになります。テナントは独自のドメインで公開サイトを公開し、別のホスト名で管理画面を開きます。最初のテナントは`publiractl setup`で作成済みです。このページでは、2つ目以降のテナントを追加する方法と、作成後にテナントの何を変更できるかを説明します。

このページの`publiractl`コマンドは、コマンドの部分だけを示しています。[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明に従い、`PUBLIRA_PLATFORM_DB_URL`に`publira_platform`の接続先を設定して実行してください。フラグの一覧は[`publiractl`のリファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#tenant)にあります。

## テナントを作成する前に

テナントは、作成したその瞬間からそのホスト名で公開されます。次のことを先に決めておいてください。

- ドメインは、公開サイトを公開するホスト名です。たとえば`comics.example.com`のような名前です。
- 管理画面のホスト名は、スタッフがログインするホスト名です。別の名前を指定しなければ、ドメインの前に`admin.`を付けた`admin.comics.example.com`のような名前になります。
- 画像ホストは、サイトの画像を`images.comics.example.com`のような専用のホスト名で配信するときにだけ決めます。詳しくは[画像ホスト](#画像ホスト)で説明します。決めなければ、画像はドメインで配信されます。
- 既定言語は、サイトと管理画面が最初に使う言語です。自動では決まりません。テナントの管理者が、あとからテナント管理画面で変更できます。
- サイトで提供する言語は、読者が選べる言語です。既定言語もこの中に含まれます。何も指定しなければ、サイトは既定言語だけで提供されます。これも、あとからテナントの管理者が変更できます。
- 最初の管理者と、その管理者が管理画面に入る方法を決めます。方法には、招待メールを送る方法と、パスワード付きのアカウントを作成する方法があります。2つの違いは[テナントのスタッフ](./3-tenant-staff.md)で比べています。

ホスト名は1つずつ小文字で書き、`https://`やパス、末尾の`/`は付けません。1つのホスト名を使えるのは1つのテナントだけで、ドメイン、管理画面のホスト名、画像ホストのうちどれか1つの役割にしか使えません。リバースプロキシはホスト名ごとに1つの転送先にしか送らないので、同じ名前を2か所で使うと、片方には届かなくなるからです。そのため、Publiraは次のホスト名を受け付けません。

- ほかのテナントがドメイン、管理画面のホスト名、画像ホストのいずれかとしてすでに使っているホスト名(管理画面に既定で割り当てられる`admin.<domain>`も含みます)
- テナント自身のドメインと同じ管理画面のホスト名
- テナント自身のドメインや管理画面のホスト名と同じ画像ホスト

テナントに割り当てられるはずの`admin.<domain>`がすでに使われているときは、そのテナントに専用の管理画面ドメインを指定してください。

ホスト名が決まったら、そのホスト名でインストールに届くようにします。[テナントを追加するとき](../2-deployments/4-edge/index.md#テナントを追加するとき)の手順に従い、DNS、証明書、リバースプロキシのルーティングの順に設定してください。この作業はテナントの作成の前でもあとでもかまいませんが、終わるまでスタッフは管理画面を開けません。

### 管理画面を別のドメインに置く

管理画面のホスト名は、テナントのドメインの下になくてもかまいません。たとえば`example.com`のサイトの管理画面を、`admin.example.net`に置くこともできます。指定には、後述の**管理画面ドメイン**か`--admin-domain`を使います。管理画面のために2つ目のドメインを取得できるなら、そのほうが安全です。

公的な認証局が発行する証明書は、すべてCertificate Transparencyログに公開されます。crt.shなどのサービスを使えば、誰でもドメイン名でこのログを検索できます。サイトのドメインの下にある管理画面のホスト名は、名前が何であっても、証明書が発行された時点からサイトと並んでこの検索結果に現れます。ワイルドカード証明書を使えばホスト名はログに載りませんが、`admin.<domain>`は誰もが真っ先に試す名前です。一方、登録可能ドメインがサイトと異なるホスト名に管理画面を置き、サイトのホスト名を1つも含まない証明書を使えば、このような形でサイトと結び付けられることはありません。管理画面はどのみちスタッフにログインを求めるので、こうして人目から隠せるのはログインページです。既定は引き続き`admin.<domain>`で、そのままでも問題なく使えます。

管理画面のホスト名は、スタッフがパスキーを登録する前に決めておいてください。[2段階認証](./12-security/2-two-step-verification.md#テナントのスタッフ)で説明しているとおり、パスキーは管理画面のホスト名に結び付くので、あとから管理画面を別のホスト名に移すと、登録済みのパスキーは使えなくなります。

さらに、リバースプロキシで、管理画面のホスト名へのアクセスをスタッフのIPアドレスからだけに絞ることもできます。[リバースプロキシの設定例](../2-deployments/4-edge/1-sample-configurations.md)には、この設定は含まれていません。この制限で守るのは管理画面のページです。管理画面のAPIには、こうした制限は要りません。管理画面はプライベートネットワーク経由でAPIを呼び出しますし、[リバースプロキシを通すのは公開APIだけ](../2-deployments/4-edge/index.md#リバースプロキシを通すのは公開apiだけ)のとおりに設定したリバースプロキシは、どのホスト名でもこのAPIを転送しないからです。

### 画像ホスト

テナントのサイトの画像は、ページと同じリバースプロキシを通り、テナントのドメインで配信されます。画像ホストを設定すると、画像は`images.comics.example.com`のような専用のホスト名で配信されます。そうすれば、[画像と公開APIを別々に提供する](../2-deployments/7-scaling-out.md#画像と公開apiを別々に提供する)で説明しているとおり、ページや公開APIとは別の、画像専用のロードバランサーやCDNを通してPubliraに届けられます。そうする必要がなければ、画像ホストは要りません。

画像ホストを設定したテナントでは、公開APIがサイトの画像のアドレスをそのホスト名で返します。Publiraがそのホスト名で返すのはテナントのサイトの画像だけで、ページ、API、管理画面は返しません。テナントのサイトとモバイルアプリは画像ホストから画像を読み込み、テナント管理画面はこれまでどおり管理画面のホスト名から画像を読み込みます。

画像ホストも、テナントのほかのホスト名と同じようにインストールに届くようにします。DNSに登録して証明書を用意し、そのホスト名の`/images`を`publira server`に転送してください。詳しくは[テナントの画像ホスト](../2-deployments/4-edge/index.md#テナントの画像ホスト)で説明しています。リバースプロキシの設定例は、ホスト名を`PUBLIRA_EDGE_IMAGE_HOSTS`に加えれば転送するようになります。設定した時点からサイトは画像をそこから読み込むので、準備を済ませてから設定してください。

あとから画像ホストを設定したり、変更したり、解除したりするのは、[テナントを別のホスト名に移す](#テナントを別のホスト名に移す)で説明するほかのホスト名の移動と同じです。`publira worker`が変更をWebアプリに伝えるまでは、変更前にサイトが用意したページが以前のホスト名の画像を指しているので、それまでは以前のホスト名でも画像を配信し続けてください。

## テナントを作成する

### プラットフォーム管理画面から

サイドバーの**テナント**にある**テナント作成**を選び、次の項目を入力します。

- **テナント名**には、出版社の名前を入力します。招待メールをはじめ、テナントのメールはこの名前で出版社を呼びます。
- **ドメイン**には、先に決めたドメインを入力します。
- **管理画面ドメイン**には、管理画面のホスト名が`admin.<domain>`ではないときにだけ、そのホスト名を入力します。空欄なら、入力欄の下に表示されるとおり、管理画面は`admin.<domain>`で開きます。
- **画像ホスト**には、テナントのサイトの画像をドメイン以外で配信するときにだけ、そのホスト名を入力します。空欄なら、入力欄の下に表示されるとおり、画像はドメインで配信されます。
- **既定言語**を選びます。
- **提供する言語**では、テナントのサイトで提供する言語にチェックを入れます。既定言語には常にチェックが入っていて外せません。ほかの言語は、最初はチェックが外れています。
- **初期管理者メール(任意、複数可)**には、テナントの管理者として招待するメールアドレスを、カンマか改行で区切って入力します。テナントを作成するとすぐ、各アドレスに招待メールが送られます。

![テナント作成フォーム。テナント名、ドメイン設定の注意書きが付いたドメイン、入力欄の下に説明がある管理画面ドメインと画像ホスト、既定言語、既定言語にチェックが入った提供する言語、初期管理者メール、作成ボタンが並んでいる。](./tenants-create-tenant.png)

**作成**を選ぶとテナントが作成され、そのテナントのページが開きます。タイムゾーンはプラットフォームの既定値になり、テナントの管理者がテナント管理画面から変更できます。

### publiractlから

```bash
publiractl tenant create \
  --name "Example Comics" \
  --domain comics.example.com \
  --default-locale en \
  --supported-locale en \
  --supported-locale ja \
  --initial-admin-email owner@comics.example.com
```

`--supported-locale`には、テナントのサイトで提供する言語を指定します。何度でも指定でき、既定言語もその中に含める必要があります。省略すると、サイトは既定言語だけで提供されます。`--admin-domain`は管理画面専用のホスト名を、`--image-domain`はサイトの画像専用のホスト名を指定します。`--timezone`には、プラットフォームの既定値以外のIANAタイムゾーンを指定します。`--initial-admin-email`も何度でも指定でき、各アドレスはプラットフォーム管理画面から作成したときと同じように招待されます。

### 作成したあと

招待メールは`publira worker`が送ります。送るには、ワーカーが動いていて、プラットフォームのSMTP設定が保存されている必要があります。メールを送らないインストールでは、[テナントのスタッフ](./3-tenant-staff.md#メールを使わずにアカウントを作成する)で説明するとおり、代わりに`publiractl tenant admin create`でテナントの最初の管理者を作成します。

管理者がログインしたら、サイト、ブランディング、決済、ほかのスタッフなど、テナントの残りの設定は管理画面から行います。

## テナントを変更する

テナント名、ドメイン、管理画面のホスト名、画像ホストは、作成後も変更できます。言語とタイムゾーンはテナントの管理者が決めるもので、テナント管理画面から変更します。テナントは削除できません。

### プラットフォーム管理画面から

**テナント一覧**でテナントを開きます。**基本情報**では**テナント名**を、**ドメイン設定**では**ドメイン**、**管理画面ドメイン**、**画像ホスト**を変更できます。**管理画面ドメイン**を空にすると管理画面は`admin.<domain>`に戻り、**画像ホスト**を空にするとサイトの画像は再びドメインで配信されます。

![テナントのページ。基本情報にはテナント名、作成日時、状態、保存ボタンがある。ドメイン設定には注意書き、ドメイン、入力欄の下に説明がある管理画面ドメインと画像ホスト、保存ボタンがある。](./tenants-profile-domain.png)

### publiractlから

```bash
publiractl tenant update --tenant comics.example.com --name "Example Comics Ltd."
```

`--tenant`には、テナントのドメインか公開IDを指定します。`--name`、`--domain`、`--admin-domain`、`--image-domain`は、それぞれ指定した値だけを置き換え、ほかの値はそのまま残します。`--admin-domain ""`を指定すると管理画面は`admin.<domain>`に戻り、`--image-domain ""`を指定するとサイトの画像は再びドメインで配信されます。テナントの今の設定は、`publiractl tenant show --tenant comics.example.com`で確認できます。

### テナントを別のホスト名に移す

`publira worker`が変更をWebアプリに伝えると、サイトはすぐに古いドメインで応答しなくなり、ページのリンクも新しいドメインを指すようになります。ただし、[アウトボックス](./10-scheduled-jobs.md#アウトボックスメールプッシュ通知キャッシュの再検証)で説明しているとおり、`PUBLIRA_REVALIDATE_TOKEN`のないワーカーは変更を伝えられないので、古いドメインはその後も最大5分間応答し続けます。新しいドメインはすぐに応答します。ただし、変更前に誰かが新しいドメインを開いていた場合は例外です。サイトは、どのテナントのものでもなかったホスト名を最大5分間覚えているからです。管理画面は、一度調べたホスト名をどれも最大5分間覚えています。そのため、新しい管理画面のホスト名が応答するまでには最大5分かかり、それまでは古いホスト名が応答し続けます。

作業は[テナントを追加するとき](../2-deployments/4-edge/index.md#テナントを追加するとき)と同じ順序で進めます。変更の前に新しいホスト名をDNS、証明書、ルーティングに加え、変更が反映されたら古いホスト名を取り除きます。専用の管理画面ドメインを持たないテナントは管理画面が`admin.<domain>`にあるので、ドメインを移すと管理画面も一緒に移ります。この場合は、新しいホスト名を2つとも用意しておく必要があります。

ドメインを移すと、ドメインの上に成り立っているものもすべて移ります。

- 読者とスタッフのログインはホスト名ごとなので、新しいホスト名でログインし直すことになります。
- スタッフのパスキーは管理画面のホスト名に結び付いています。新しい管理画面ドメインを指定したときや、管理画面が`admin.<domain>`にあるテナントのドメインを変えたときのように、管理画面のホスト名が変わると、[2段階認証](./12-security/2-two-step-verification.md#テナントのスタッフ)で説明しているとおりパスキーは使えなくなります。
- テナントのモバイルアプリは1つのホスト名に向けてビルドされ、そのホスト名のリンクしか開きません。[アプリマニフェスト](../5-mobile-app/1-app-manifest.md)に新しいホスト名を指定して、ビルドと申請をやり直してください。
- テナント管理画面に表示される決済用の**Webhook URL**と、AppleやGoogleでのログイン用に表示されるコールバックURLは、ドメイン上のURLです。新しいURLを各プロバイダーに登録し直してください。
- 変更前に送ったメールのリンクは、古いホスト名を指したままです。

## テナントを停止する

プラットフォーム管理画面のテナントのページで**停止する**を選ぶか、`publiractl tenant suspend --tenant comics.example.com`を実行すると、テナントは**停止中**になります。**再開する**を選ぶか`publiractl tenant resume`を実行すると、再び稼働中に戻ります。プラットフォーム管理画面のボタンは確認なしに、押した時点で反映されます。どちらの方法でも変更は**監査ログ**に記録され、ダッシュボードではそのテナントが**停止中テナント**に数えられます。

![稼働中のテナントのページの上部。一覧へ戻る、監査ログを確認、停止するの各ボタンが並んでいる。](./tenants-suspend.png)

![停止中のテナントのページ。停止するの代わりに再開するが表示され、基本情報の状態が停止中になっている。](./tenants-suspended.png)

![ダッシュボードのテナント数。総テナント数、稼働中テナント、停止中テナント、保留ユーザーが並んでいる。](./tenants-dashboard-counts.png)

停止すると、テナントのサービスの提供が止まります。変わるのはそれだけです。

- サイト、アプリ、管理画面が使えなくなります。APIはこのテナントへのリクエストを、ログインも含めてすべて拒否し、画像も配信しなくなります。ただし、読者のブラウザーやPubliraの前段のキャッシュにすでにある画像は、最大1時間は表示されます。Publiraが画像の保持を認めている期間が1時間だからです。
- 読者に伝わるのは、サイトが利用できないことだけです。サイトのどのページを開いても、そのことを伝えるページがステータス`503`で返ります。このステータスは、サイトがなくなったのではなく、しばらく利用できないだけだと検索エンジンに伝えます。アプリでは、どの画面の代わりにも同じ内容が**再試行**ボタンとともに表示されます。テナントが再開されたあとで読者がこのボタンをタップするか、アプリに戻ってくると、アプリは再び使えるようになります。
- スタッフには、サイトが停止中のため管理画面を利用できないことが、ログインページを含めた管理画面のすべてのページに表示されます。内部の詳細は何も表示しません。
- Webアプリは、一度調べたホスト名を最大5分間覚えています。そのため停止から5分間は、すでに用意してあったページが表示されることがあり、それ以外のページでは上の案内の代わりにWebアプリのエラーページが表示されます。
- 決済プロバイダーと受信メールのプロバイダーから届く通知も拒否されます。拒否された通知は各プロバイダーが独自のスケジュールで再送します。テナントを再開した時点でまだ再送されている通知は再開後に処理されますが、プロバイダーがすでに再送をあきらめた通知は処理されません。
- 読者とスタッフはログアウトされません。停止中はセッションが受け付けられませんが、再開すると再び使えるようになります。
- 読者とスタッフへのメールとプッシュ通知は送られず、あとで送るために取っておかれることもありません。リンク先が利用できず、再開するころには内容が古くなっているからです。例外は、プラットフォーム管理画面や`publiractl`から送るテナントの管理者への招待で、これは停止中でも送られます。招待のリンクはテナントを再開すると使えるようになり、それまでに期限が切れていれば**再送**で新しいリンクを発行できます。
- 予約公開、無料公開期間、印税の締め処理など、テナントの予定された処理は続きます。そのため、再開したテナントは、本来のスケジュールどおりの状態になっています。
- テナントの情報、メンバー、招待は、[テナントのスタッフ](./3-tenant-staff.md)で説明するとおり、停止中でもプラットフォーム管理画面と`publiractl`から変更できます。

停止しても再開しても、テナントについて削除されるものや変わるものはありません。再開すれば、ほかに何もしなくてもすぐにサービスの提供が再開されます。
