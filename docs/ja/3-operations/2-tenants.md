インストール環境がサービスを提供する出版社はそれぞれテナントであり、独自のドメインで公開される公開サイトと、別のホスト名で提供される管理画面を持ちます。最初のテナントは`publiractl setup`が作成しました。このページでは次のテナントを追加する方法と、テナントについてあとから変更できることを説明します。

このページの`publiractl`コマンドは、コマンド単体で示しています。[プラットフォーム管理画面とpubliractl](./1-platform-console.md#どちらを使うか)の説明どおりに、`PUBLIRA_PLATFORM_DB_URL`に`publira_platform`の接続先を設定して実行してください。フラグの一覧は[`publiractl`リファレンス](https://github.com/publira/publira/blob/main/server/cmd/publiractl/README.md#tenant)にあります。

## テナントを作成する前に

テナントは作成された瞬間からそのホスト名でサービスが提供されるため、次のことを先に決めておきます。

- **ドメイン**：公開サイトを提供するホストです。たとえば`comics.example.com`です。
- **管理画面のホスト**：スタッフがログインするホストです。専用のホストを指定しない限り、ドメインの前に`admin.`を付けたもの、たとえば`admin.comics.example.com`になります。
- **画像ホスト**：サイトの画像を専用のホスト名、たとえば`images.comics.example.com`で配信する場合にだけ必要です。詳しくは[画像ホスト](#画像ホスト)で説明します。画像ホストがない場合、画像はドメインで配信されます。
- **既定言語**：サイトと管理画面が最初に表示される言語です。自動では選ばれません。テナントの管理者があとからテナント管理画面で変更できます。
- **サイトが読者に提供する言語**：既定言語もそのひとつです。指定しなければ、サイトは既定言語だけを提供します。これもテナントの管理者があとから変更できます。
- **最初の管理者**と、その人がアクセスする方法：メールで招待を送るか、パスワード付きのアカウントを作成するかです。2つの方法の比較は[テナントのスタッフ](./3-tenant-staff.md)にあります。

ホスト名はそれぞれ単独で、小文字で書きます。`https://`もパスも末尾の`/`も付けません。1つのホスト名は1つのテナントの、ドメイン、管理画面のホスト、画像ホストのいずれか1つとしてだけ使えます。プロキシはホスト名ごとに転送先を1つだけ決めるので、同じ名前を2か所で使うと一方に到達できなくなるためです。Publiraは、ほかのテナントがこの3つのいずれかとしてすでに使っているドメイン、管理画面のホスト、画像ホストを受け付けません。これには既定で管理画面に割り当てられる`admin.<domain>`も含まれます。また、テナント自身のドメインと同じ管理画面のホストや、テナント自身のドメインまたは管理画面のホストと同じ画像ホストも受け付けません。テナントに割り当てられるはずの`admin.<domain>`がすでに使われている場合は、そのテナントに専用の管理画面ドメインを指定してください。

次に、[テナントの追加](../2-deployments/4-edge/index.md#テナントを追加する)に示す順序で、テナントのホスト名がインストール環境に届くようにします。DNS、証明書、エッジのルーティングの順です。この作業はテナントの作成の前でもあとでもかまいませんが、終わるまでスタッフは管理画面を開けません。

### 独自のドメインに置く管理画面のホスト

管理画面のホストはテナントのドメインの下にある必要はありません。`example.com`のサイトの管理画面を`admin.example.net`に置くこともでき、その場合は後述の**管理画面ドメイン**または`--admin-domain`で指定します。管理画面用に2つ目のドメインを登録できるなら、そのほうが安全です。公的な認証局が発行する証明書はすべてCertificate Transparencyログに公開され、crt.shなどのサービスを使えば誰でもドメインで検索できます。そのため、サイトのドメインの下にある管理画面のホストは、名前が何であれ、証明書が発行された瞬間からサイトと並んで一覧に載ります。ワイルドカード証明書を使えば名前はログに載りませんが、`admin.<domain>`は誰もが最初に試す名前です。別の登録可能ドメインにあり、サイトのホストを1つも含まない証明書を使う管理画面のホストは、このような形でサイトと結び付けられることはありません。それでも管理画面はスタッフにログインを求めるので、これによって人目から隠れるのはログインページです。既定は引き続き`admin.<domain>`で、そのままでも動作します。

これはスタッフがパスキーを登録する前に決めてください。パスキーは管理画面のホストに結び付くため、あとから管理画面を別のホストに移すと、登録済みのパスキーは使えなくなります。詳しくは[2段階認証](./12-security/2-two-step-verification.md#テナントのスタッフ)を参照してください。

さらに、エッジで管理画面のホストをスタッフのIPアドレスからのアクセスだけに制限することもできます。[サンプル設定](../2-deployments/4-edge/1-sample-configurations.md)はこれを行いません。これで守られるのは管理画面のページです。管理画面のAPIにはこのようなルールは不要です。管理画面はAPIをプライベートネットワーク経由で呼び出し、[公開APIだけがエッジを通る](../2-deployments/4-edge/index.md#エッジを通るのは公開apiだけ)の説明どおりに設定したエッジは、どのホストでもAPIを転送しないためです。

### 画像ホスト

テナントのサイトの画像は、ページと同じエッジを通して、テナントのドメインで配信されます。画像ホストを使うと、画像は代わりに専用のホスト名、たとえば`images.comics.example.com`で配信されます。これにより、[画像と公開APIを分けて配信する](../2-deployments/7-scaling-out.md#画像と公開apiを分けて提供する)で説明するように、画像だけをページや公開APIとは別の専用のロードバランサーやCDNを通してPubliraに届けられます。そうした必要のないテナントには画像ホストも不要です。

テナントに画像ホストがあると、公開APIはサイトの画像のアドレスをそのホストで返し、Publiraはそのホストではテナントのサイトの画像だけに応答します。ページ、API、管理画面はそこでは提供されません。テナントのサイトとモバイルアプリは画像をそこから読み込みます。テナント管理画面は引き続き管理画面のホストで画像を読み込みます。

画像ホストも、テナントのほかのホスト名と同じようにインストール環境に届くようにする必要があります。DNSに登録し、証明書を用意し、そのホストの`/images`を`publira server`にルーティングします。詳しくは[テナントの画像ホスト](../2-deployments/4-edge/index.md#テナントの画像ホスト)を参照してください。サンプル設定は、ホストが`PUBLIRA_EDGE_IMAGE_HOSTS`に含まれればルーティングします。設定した時点からサイトは画像をそこから読み込むので、設定する前に準備を済ませておいてください。

あとから画像ホストを設定、変更、解除する作業は、[テナントを別のホスト名に移す](#テナントを別のホスト名に移す)で説明する、ほかのホスト名の移動と同じです。変更前にサイトが用意したページは、`publira worker`が変更をWebアプリに伝えるまで以前のホストの画像にリンクしているので、それまでは以前のホストでの配信を続けてください。

## テナントを作成する

### プラットフォーム管理画面から

サイドバーの**テナント**の下にある**テナント作成**を選び、次の項目を入力します。

- **テナント名**：出版社の名前です。招待メールやそのほかのテナントのメールで、この名前が使われます。
- **ドメイン**：決めておいたドメインです。
- **管理画面ドメイン**：管理画面のホストです。`admin.<domain>`でない場合にだけ入力します。空欄にすると、項目の下の説明のとおり、管理画面は`admin.<domain>`で提供されます。
- **画像ホスト**：テナントのサイトの画像を配信するホストです。画像をドメインで配信しない場合にだけ入力します。空欄にすると、項目の下の説明のとおり、画像はドメインで配信されます。
- **既定言語**。
- **提供する言語**：言語ごとのチェックボックスで、テナントのサイトが提供する言語にチェックを入れます。既定言語のチェックボックスは常にチェックされていて外せず、ほかは最初はチェックされていません。
- **初期管理者メール（任意・複数可）**：テナントの管理者として招待するアドレスを、カンマか改行で区切って入力します。テナントが作成されるとすぐに、それぞれのアドレスに招待メールが送られます。

![テナント作成フォーム。テナント名、ドメイン設定時の注意が添えられたドメイン、項目の下に説明がある管理画面ドメインと画像ホスト、既定言語、既定言語のチェックボックスがチェックされた提供する言語、初期管理者メール、作成ボタン。](./tenants-create-tenant.png)

**作成**を選ぶとテナントが作成され、そのページが開きます。タイムゾーンはプラットフォームの既定のものになり、テナントの管理者がテナント管理画面から変更できます。

### publiractlから

```bash
publiractl tenant create \
  --name "Example Comics" \
  --domain comics.example.com \
  --default-locale en \
  --supported-locale en \
  --supported-locale ja \
  --initial-admin-email owner@comics.example.com
```

`--supported-locale`はテナントのサイトが提供する言語を指定し、繰り返し指定できます。既定言語はそのいずれかである必要があります。省略すると、サイトは既定言語だけを提供します。`--admin-domain`は管理画面に専用のホストを、`--image-domain`はサイトの画像に専用のホストを、`--timezone`はプラットフォームの既定以外のIANAタイムゾーンを指定します。`--initial-admin-email`は繰り返し指定でき、それぞれのアドレスはプラットフォーム管理画面から指定したときと同じように招待されます。

### 作成したあと

招待メールは`publira worker`が送るので、ワーカーが動いていて、プラットフォームのSMTP設定が保存されている必要があります。メールを送らないインストール環境では、代わりに`publiractl tenant admin create`でテナントの最初の管理者を作成します。詳しくは[テナントのスタッフ](./3-tenant-staff.md#メールを使わずにアカウントを作成する)を参照してください。

管理者がログインしたら、テナントの残りの設定、つまりサイト、ブランディング、決済、ほかのスタッフは、そのテナントの管理画面から行います。

## テナントを変更する

テナントの名前、ドメイン、管理画面のホスト、画像ホストは、作成後に変更できます。言語とタイムゾーンはテナントの管理者が管理するもので、テナント管理画面から変更します。テナントは削除できません。

### プラットフォーム管理画面から

**テナント一覧**からテナントを開きます。**基本情報**では**テナント名**を、**ドメイン設定**では**ドメイン**、**管理画面ドメイン**、**画像ホスト**を変更します。**管理画面ドメイン**を空にすると管理画面は`admin.<domain>`に戻り、**画像ホスト**を空にするとサイトの画像は再びドメインで配信されます。

![テナントのページ。テナント名、作成日時、状態、保存ボタンがある基本情報と、注意書き、項目の下に説明があるドメイン、管理画面ドメイン、画像ホスト、保存ボタンがあるドメイン設定。](./tenants-profile-domain.png)

### publiractlから

```bash
publiractl tenant update --tenant comics.example.com --name "Example Comics Ltd."
```

`--tenant`はテナントをドメインか公開IDで指定します。`--name`、`--domain`、`--admin-domain`、`--image-domain`はそれぞれその値だけを置き換え、ほかの値はそのまま残します。`--admin-domain ""`は管理画面を`admin.<domain>`に戻し、`--image-domain ""`はサイトの画像を再びドメインで配信します。`publiractl tenant show --tenant comics.example.com`はテナントの現在の状態を表示します。

### テナントを別のホスト名に移す

`publira worker`が変更をWebアプリに伝えるとすぐに、サイトは古いドメインで応答しなくなり、ページは新しいドメインにリンクするようになります。[アウトボックス](./10-scheduled-jobs.md#アウトボックスメールプッシュ通知キャッシュの再検証)で説明するとおり、`PUBLIRA_REVALIDATE_TOKEN`のないワーカーはこれを伝えられず、その場合、古いドメインは最大5分間応答し続けます。新しいドメインはすぐに応答します。ただし、変更前に誰かがそのドメインを開いていた場合は例外です。サイトはどのテナントにも属していなかったホスト名を最大5分間記憶するためです。管理画面は一度調べたホスト名をすべて最大5分間保持するので、新しい管理画面のホストが応答するまでにはその時間がかかり、古いホストはそれまで応答し続けます。

[テナントの追加](../2-deployments/4-edge/index.md#テナントを追加する)の順序に従ってください。変更の前に新しい名前をDNS、証明書、ルーティングに追加し、変更が反映されてから古い名前を取り除きます。専用の管理画面ドメインを持たないテナントの管理画面は`admin.<domain>`にあるので、ドメインを移すと管理画面も移り、新しい名前の両方を準備しておく必要があります。

ドメインを移すと、その上に成り立っているものもすべて移ります。

- 読者とスタッフのログインは1つのホスト名に対して行われるので、新しいホスト名で再びログインすることになります。
- スタッフのパスキーは管理画面のホストに属するので、管理画面のホストが変わる移動、つまり新しい管理画面ドメインを指定する場合や、管理画面が`admin.<domain>`にあるテナントのドメインを変える場合には、パスキーが使えなくなります。詳しくは[2段階認証](./12-security/2-two-step-verification.md#テナントのスタッフ)を参照してください。
- テナントのモバイルアプリは1つのホスト向けにビルドされ、そのホストのリンクしか開きません。[アプリマニフェスト](../5-mobile-app/1-app-manifest.md)に新しいホストを指定して、ビルドと申請をやり直してください。
- テナント管理画面に表示される決済用の**Webhook URL**と、AppleやGoogleでのログイン用に表示されるリターンURLは、ドメイン上にあります。新しいURLをそれぞれのプロバイダーに登録してください。
- 変更前に送られたメールは古いホストにリンクしています。

## テナントを停止する

プラットフォーム管理画面のテナントのページで**停止する**を選ぶか、`publiractl tenant suspend --tenant comics.example.com`を実行すると、テナントは**停止中**になります。**再開する**、または`publiractl tenant resume`で、テナントは再び稼働中になります。プラットフォーム管理画面のボタンは、確認なしで押した瞬間に反映されます。どちらの方法でも変更は**監査ログ**に記録され、ダッシュボードはそのテナントを**停止中テナント**に数えます。

![稼働中のテナントのページの上部。一覧へ戻る、監査ログを確認、停止するボタン。](./tenants-suspend.png)

![停止中のテナントのページ。停止するボタンの代わりに再開するボタンがあり、基本情報の状態が停止中になっている。](./tenants-suspended.png)

![ダッシュボードのテナント数。総テナント数、稼働中テナント、停止中テナント、保留ユーザー。](./tenants-dashboard-counts.png)

停止するとテナントへのサービスの提供が止まりますが、それ以外は何も変わりません。

- サイト、アプリ、管理画面が使えなくなります。APIはテナントへのすべてのリクエストを、ログインも含めて拒否し、画像も配信されなくなります。読者のブラウザーやPubliraの前段にあるキャッシュがすでに保持している画像は、最大1時間表示され続けます。これはPubliraが画像の保持を許している時間です。
- 読者には、サイトが利用できないことだけが表示されます。サイトのすべてのページが、その旨を伝えるページをステータス`503`で返します。このステータスは、サイトがなくなったのではなく一時的に利用できないことを検索エンジンに伝えます。アプリはすべての画面の代わりに同じ内容を**再試行**とともに表示し、テナントが再開されたあと、読者がそれをタップするかアプリに戻ってくると、再び開きます。
- スタッフには、サイトが停止されているため管理画面を利用できないことが、ログインページを含む管理画面のすべてのページで表示されます。内部の詳細は何も表示されません。
- Webアプリは一度調べたホスト名を最大5分間保持します。停止後のその間は、すでに用意されていたページが表示されることがあり、それ以外のページでは上記のページの代わりにアプリのエラーページが表示されます。
- テナントの決済プロバイダと受信メールプロバイダーが送る通知も拒否されます。各プロバイダーは拒否された通知をそれぞれのスケジュールで再送するので、テナントが再開された時点でまだ再送中の通知はそのときに処理され、すでに再送をあきらめた通知は処理されません。
- 読者とスタッフはログインしたままです。テナントが停止している間はセッションが受け付けられず、再開されると再び使えるようになります。
- 読者とスタッフへのメールとプッシュ通知は送られず、あとで送るために保持されることもありません。リンク先が利用できないうえに、テナントが再開されるころには内容が古くなっているためです。例外は、プラットフォーム管理画面や`publiractl`から送るテナント管理者への招待で、これは送信されます。そのリンクはテナントが再開されると使えるようになり、それまでに期限が切れていた場合は**再送**で新しいリンクを発行できます。
- 予約公開、無料公開期間、印税の締め、そのほかの予定された処理は続行されるので、再開されたテナントは、本来のスケジュールどおりの状態になっています。
- テナントの詳細、メンバー、招待は、引き続きプラットフォーム管理画面と`publiractl`から変更できます。詳しくは[テナントのスタッフ](./3-tenant-staff.md)を参照してください。

停止や再開によってテナントについて何かが削除されたり変更されたりすることはなく、再開するとすぐに、ほかに何もしなくてもサービスの提供が再開されます。
