テナントは、読者とスタッフにメールを送ります。メールアドレスの確認、パスワードの再設定、購入の領収書、招待、お問い合わせへの回答などです。テナント管理者がテナント独自のメールサーバーを設定するまでは、これらのメールはすべてプラットフォームのメールサーバーから、オペレーターが決めたプラットフォームのアドレスで送られます。**外部連携** › **メール情報**で設定すると、出版社独自のSMTPサーバーから、出版社のドメインのアドレスで送れるようになります。

この画面はテナント管理者にしか表示されません。使い始めるのに、オペレーターの許可は必要ありません。

## 独自のサーバーから送られるメール

テナント独自のサーバーを有効にすると、テナントが送るメールはすべてそのサーバーから送られます。

- 読者宛てのメール。会員登録の確認、パスワードの再設定とパスワード変更の通知、メールアドレス変更の確認とアドレス変更の通知、アカウントがあるアドレスで誰かが会員登録しようとしたことの通知です。
- サイトでエピソードを購入した読者への領収書。シリーズとエピソードの名前、支払った金額、購入日時が書かれ、閲覧期間のあるエピソードではいつまで読めるかも書かれます。読者の購入履歴へのリンクも付きます。
- 通知設定でメールを受け取るようにしている読者への通知。フォローしているものの新しいエピソード、自分のコメントの公開、お知らせを知らせます。お知らせが誰に届くかは[読者に表示される場所](./4-announcements.md#読者に表示される場所)で説明しています。
- 読者のお問い合わせへの回答。
- スタッフ宛てのメール。新しいテナント管理者への招待、管理画面のパスワードの再設定とメールアドレスの変更、新しいお問い合わせの通知です。お問い合わせの通知はテナント管理者に届きます。

## 始める前に

出版社のメールを管理している担当者から、次の情報を受け取っておいてください。

- SMTPサーバーのホスト名とポート番号。接続の最初からTLSを使うのか(通常はポート465)、STARTTLSを使うのか(通常はポート587)も確認します。
- SMTPサーバーのユーザー名とパスワード。認証情報なしでメールを中継するサーバーなら必要ありません。
- 送信元にするアドレス。サーバーがこのアドレスで送信できるようになっている必要があります。ドメインのSPFレコードとDKIMレコードにこのサーバーを含めてください。含めないと、読者のメールサービスでテナントのメールが迷惑メールに振り分けられやすくなります。

## 設定の手順

1. **外部連携** › **メール情報**を開き、**送信メール**のセクションにある**テナントSMTP上書きを有効にする**で、**上書きを有効化**にチェックを入れます。その下に入力項目が表示されます。
2. 次の項目を入力します。
   - **ホスト**と**ポート**を入力します。
   - **ユーザー名**と**パスワード**は、サーバーへのログインが必要な場合に入力します。プラットフォームのアドレスを信頼するリレーのように、認証情報を使わないリレーでは**ユーザー名**を空欄にします。この場合、メールはログインせずに送られ、パスワードは保存されません。ユーザー名を入れずにパスワードだけを入力すると、保存できません。
   - **暗号化方式**は、**TLS**、**STARTTLS**、**なし**から選びます。**TLS**と**STARTTLS**は、どちらもTLS 1.2以降が必要です。**STARTTLS**では、サーバーがSTARTTLSに対応していないと、暗号化せずに送ることはせず、送信に失敗します。**なし**は、プライベートネットワーク経由で接続するサーバーの場合だけ選んでください。
   - **送信者メールアドレス**には、`noreply@comics.example.com`のような送信元のアドレスを入力します。
   - 「**送信者名(任意)**」には、読者のメールソフトでアドレスの横に表示される名前を入力します。通常はサイト名です。空欄にすると、テナントのメールでも接続テストでもテナント名が使われます。
   - 「**返信先メールアドレス(任意)**」には、サポート用のアドレスなど、読者からの返信を受け取るアドレスを入力します。空欄にすると、返信は送信者メールアドレスに届きます。お問い合わせへの回答では、この設定ではなく、回答ごとの返信先アドレスが使われます。
3. **接続テスト**を選び、**テストを実行**を選びます。テストでは、フォームに入力した値を保存せずに使ってメールを送ります。送信先は自分のアドレスです。**自分に送信する**のチェックを外すと、別のアドレスに送れます。テストに失敗した場合は、判別できる限り、どの段階で失敗したかが表示されます。段階は、接続、TLSかSTARTTLS、ログイン、サーバーによる宛先の拒否、サーバーの応答の遅れのどれかです。
4. **保存**を選びます。テナントが次に送るメールから、新しいサーバーが使われます。

![SMTP接続テストのダイアログ。「自分に送信する」、「閉じる」、「テストを実行」がある。](./email-test-connection.png)

保存したパスワードは二度と表示されません。項目にはパスワードが保存済みであることが表示され、**変更する**を選ぶと別のパスワードに替えられます。**変更する**を選んで欄を空のまま保存すると、パスワードは削除されます。認証情報を使わないリレーに切り替えるときは、この方法でパスワードを削除します。パスワードのないユーザー名も保存できないので、**ユーザー名**も空にしてください。

## 送信できなくなったとき

テナント独自のサーバーを有効にした後は、送信に失敗しても、プラットフォームのサーバーに切り替えて送られることはありません。サーバーがメールを拒否したり、サーバーに接続できなかったりした場合、プラットフォームは間隔を少しずつ広げながらしばらく再試行します。それでも送れなければ、そのメールの送信をあきらめます。送信の失敗は、管理画面のどこにも表示されません。確認メールやパスワード再設定のメールが届かないと読者から連絡があったら、保存済みの設定で**接続テスト**をもう一度実行してください。

プラットフォームのメールサーバーに戻すには、**上書きを有効化**のチェックを外して**保存**を選びます。ほかの設定は残るので、再び有効にするときにそのまま使えます。

保存するたびに、[監査ログ](./8-audit-log.md)に**メール設定更新**が記録されます。接続テストも、成功したかどうかにかかわらず、実行するたびに**SMTP接続テスト**として記録されます。テナントのメールについてのオペレーター向けの説明は、[メール](../../3-operations/6-email.md#テナント独自のsmtpアカウント)にあります。

## お問い合わせへの回答に対する読者の返信

お問い合わせへの回答は、メールで読者に届きます。テナントが自分でメールを受信できるようにするまでは、回答の返信先は回答したスタッフのアドレスです。読者が返信すると、そのスタッフのメールボックスに届き、管理画面には届きません。**外部連携** › **メール情報**の**受信メール**のセクションを設定すると、読者の返信を管理画面に取り込み、元のお問い合わせの下に表示できます。返信の受信には、SendGrid、Resend、Mailgun、Amazon SESのほか、受信したメール全体をHTTPSのURLに送信できるメールサービスやメールサーバーを使えます。たとえば、Cloudflare Email Routingや、出版社が自前で運用するPostfixサーバーです。

### 準備するもの

- SendGrid、Resend、Mailgunのアカウントか、メールを受信できるリージョンでAmazon SESを使えるAWSアカウント。または、受信したメールを1通ずつ自作のコードに渡せるメールサービスかメールサーバー(Cloudflare Email RoutingかPostfixサーバー)。
- `reply.comics.example.com`のような、DNSを変更できる返信用のドメイン。このドメインのMXレコードはプロバイダーに向けるので、このドメイン宛てのメールはほかのメールボックスには届かなくなります。返信専用のサブドメインにしておけば、出版社のメインのドメインで受信しているメールには影響しません。
- インターネットからアクセスできるサイト。プロバイダーは、返信をサイト自身のドメインに送信します。サイトの前にIPアドレスの許可リスト、ログインの要求、ボット対策のチャレンジがある場合は、これらのリクエストを通すようにする必要があります。オペレーター向けには[リバースプロキシの設定](../../2-deployments/4-edge/index.md#webhook)で説明しています。

### 設定の手順

1. **外部連携** › **メール情報**を開きます。**受信メール**のセクションで、**受信メールのプロバイダ**からプロバイダーを選び、**返信をコンソールで受け取る**の**有効化**にチェックを入れ、返信用のドメインを**受信ドメイン**に入力します。
2. プロバイダー側を設定します。セクションには、サイトのドメインの**Webhook URL**と、URLをコピーするボタンが表示されます。
   - **SendGrid**では、長いランダムな文字列を自分で決め、**Webhookトークン**に入力します。DNSで、ドメインのMXレコードを優先度10で`mx.sendgrid.net`に向けます。SendGridの**Settings** › **Inbound Parse**でドメインを追加し、宛先のURLに**Webhook URL**を指定します。このとき、`<token>`の部分をトークンに置き換えます。SendGridはリクエストに署名しないため、サイトはURLに含まれるトークンで、SendGridからのリクエストをほかのリクエストと見分けます。
   - **Resend**では、**API Keys**で**Full access**のAPIキーを作成し、**APIキー**に入力します。サイトはこのキーを使ってResendから返信を読み取ります。**Domains**でドメインを追加して受信を有効にし、Resendに表示されるMXレコードをDNSに追加します。**Webhooks**で`email.received`イベントの送信先に**Webhook URL**を追加し、Resendに表示されるそのWebhookの署名シークレット(`whsec_…`)を**Webhook署名シークレット**に入力します。
   - **Amazon SES**では、長いランダムな文字列を自分で決めて**Webhookトークン**に入力し、メールの通知を発行するSNSトピックのARNを**SNSトピックARN**に入力します。AWSでドメイン、トピック、受信ルールを設定してから保存し、トピックを**Webhook URL**にサブスクライブします。手順は後の[Amazon SESで受信する](#amazon-sesで受信する)で説明しています。
   - **Raw MIME over HTTPS**では、長いランダムな文字列を自分で決め、**Webhookトークン**に入力します。ドメインのMXレコードは、メールを受信するサービスかサーバーに向けます。そのサービスやサーバーで、ドメインに届いたすべてのメールを、手を加えずに丸ごと**Webhook URL**に送信するよう設定します。送信するときは、コンテンツタイプを`message/rfc822`にし、URLの`<token>`をトークンに置き換え、メールの配送先アドレスを`X-Envelope-To`ヘッダーに入れます。読者側で転送やエイリアスを使っていると、返信の**To**にお問い合わせ固有のアドレスが残っていないことがよくあります。そのような返信も、このヘッダーでお問い合わせと照合できます。後で説明する[Cloudflare Email Routing](#cloudflare-email-routingからメールを送る)と[Postfix](#postfixからメールを送る)の設定は、これらをすべて満たしています。
   - **Mailgun**では、**Settings** › **API Security**にある**HTTP webhook signing key**をコピーし、管理画面の**HTTP Webhook署名キー**に入力します。Mailgunは、送信するすべての返信にこのキーで署名します。署名が一致しない送信は拒否されます。サブアカウントのドメインでは、サブアカウントのキーとプライマリーアカウントのキーのどちらも使えます。**Domains**でドメインを追加し、Mailgunに表示される受信用のMXレコードをDNSに追加します。次に、**Receiving**でルートを作成します。式の種類は**Match Recipient**にし、受信者には`.*@reply.comics.example.com`のように、ドメインのすべてのアドレスに一致するものを指定します。**Forward**にチェックを入れ、**Webhook URL**を表示されているとおりに、末尾の`/json`まで含めて指定します。Mailgunがメール全体に署名して送信するのは、末尾が`/json`のURLに対してだけです。それ以外のURLへの送信は拒否されます。MailgunのEUリージョンのアカウントでも、手順は同じです。
3. **保存**を選びます。セクションの状態が**利用可能**になり、**返信先アドレス**として、`contact+*@`にドメインを続けたアドレスが表示されます。これ以降の回答では、読者にこの形式のアドレスへの返信を求めます。`*`の部分はお問い合わせのIDで、返信はそのお問い合わせの下に表示されます。

![有効化にチェックを入れた受信メールのセクション。受信メールのプロバイダ、受信ドメイン、プロバイダーの認証情報、コピーボタン付きのWebhook URL、「保存」がある。](./email-inbound.png)

セクションが**利用可能**になるまでは、回答の返信先は回答したスタッフのアドレスのままです。セクションにも、そのことが表示されます。ほかの状態の意味は次のとおりです。**未設定**は、何も保存されていない状態です。**無効**は、設定は保存されているものの、**有効化**のチェックが外れている状態です。**設定不足**は、有効にはなっているものの、ドメインか、プロバイダーに必要な認証情報が足りない状態です。

トークンとキーは、一度保存すると二度と表示されません。各欄には伏せ字が表示され、**変更する**を選ぶと別の値に替えられます。別のプロバイダーを選んで保存すると、前のプロバイダー用に保存していた認証情報は削除されます。

返信の受信をやめるには、**有効化**のチェックを外して**保存**を選びます。次の回答から、返信先は再びスタッフのアドレスになります。設定は残るので、再び有効にするときにそのまま使えます。保存するたびに、[監査ログ](./8-audit-log.md)に**受信メール設定更新**が記録されます。

### Amazon SESで受信する

Amazon SESがドメイン宛てのメールを受信し、1通ずつ受信ルールに渡します。受信ルールはメールの通知をAmazon SNSのトピックに発行し、トピックはHTTPSのサブスクリプションを通じて、その通知を**Webhook URL**に届けます。SNSはすべての配信に署名しますが、どのAWSアカウントでも自分のトピックをこのURLにサブスクライブできてしまいます。そのため、サイトはURLのトークンと、配信元のトピックも確認します。

SESでメールを受信できるのは、一部のAWSリージョンだけです。対象のリージョンは[Email receiving endpoints](https://docs.aws.amazon.com/general/latest/gr/ses.html#ses_inbound_endpoints)に載っています。以下のドメイン、トピック、受信ルールは、このリージョンのどれかで作成してください。バケットは別のリージョンでもかまいません。

1. SESの**Identities**で、受信ドメインを検証します。DNSで、そのドメインのMXレコードを優先度10で`inbound-smtp.<region>.amazonaws.com`に向けます。たとえば`inbound-smtp.us-east-1.amazonaws.com`です。
2. SNSで、`publira-inbound`のような名前のスタンダードトピックを作成します。そのARNを、管理画面の**SNSトピックARN**に入力します。
3. SESの**Email receiving**で、有効なルールセットにルールを作成します。受信者の条件には受信ドメインを指定し、アクションには次のどちらかを設定します。
   - **Deliver to Amazon S3 bucket**を選び、**SNS topic**で先ほどのSNSトピックを選びます。SESは受信したメールをバケットに書き込み、その場所をトピックに通知します。サイトはバケットからメールを読み取ります。SESが受信できる40 MBまでの返信なら、大きさに関係なく受け取れるので、こちらのアクションを使ってください。バケットポリシーで、SESがバケットに書き込めるようにする必要があります([Giving permissions to Amazon SES for email receiving](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-permissions.html)を参照)。**Message encryption**はオフのままにします。オンにすると、SESがメールをクライアント側で暗号化し、サイトでは復号できなくなります。次に、IAMでアクセスキーを持つユーザーを作成し、バケット内のオブジェクトに対する`s3:GetObject`を許可するポリシーを付けます。そのアクセスキーを**AWSアクセスキーID**と**AWSシークレットアクセスキー**に入力します。サイトがこのバケット以外からは読み取らないようにするには、**S3バケット**を入力します。バケットがトピックと別のリージョンにある場合は、**S3バケットのリージョン**も入力します。
   - **Publish to Amazon SNS topic**を選び、トピックと、エンコーディングの**Base64**を指定します。Base64にすると、どの文字コードのメールも送られたときのまま届きます。メールは通知の中に含まれて届くので、バケットもアクセスキーも必要ありません。ただし、SESは150 KBを超えるメールをすべてバウンスします。画像や添付ファイルのある返信は、すぐにこの大きさを超えます。
4. 管理画面で**保存**を選びます。SNSからサイトにサブスクリプションの確認が届いた時点で、サブスクリプションが承認されます。サイトが承認するのは、保存してあるトークンとトピックに一致する確認だけです。
5. SNSで、トピックへのサブスクリプションを作成します。プロトコルは**HTTPS**にし、エンドポイントには`<token>`をトークンに置き換えた**Webhook URL**を指定します。**Enable raw message delivery**はオフのままにします。SNSの署名が付いていない配信は拒否されるためです。サブスクリプションは1分以内に**Confirmed**になります。**Pending confirmation**のままの場合は、管理画面でトークンとトピックを確認して保存し、サブスクリプションで**Request confirmation**を選びます。

手順3のユーザーに付けるIAMポリシーの例です。`publira-inbound-mail`は、使うバケットの名前に置き換えてください。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::publira-inbound-mail/*"
    }
  ]
}
```

バケットに書き込まれたものを既定でKMSキーで暗号化している場合は、そのキーに対する`kms:Decrypt`も追加してください。

サイトが配信を受け取れなかった場合、SNSは20秒間隔で3回再試行し、それでも届かなければその配信を破棄します。受け取れないのは、サイトが停止していて`5xx`を返すときや、バケットからメールを読み取れないときです。サブスクリプションに[配信ポリシー](https://docs.aws.amazon.com/sns/latest/dg/sns-message-delivery-retries.html)を設定すると、最長1時間まで再試行を続けられます。デッドレターキューを使えば、破棄された配信を残しておけます。S3アクションで書き込まれたメールは、どちらの場合もバケットに残ります。

### Cloudflare Email Routingからメールを送る

Cloudflare Email Routingは、受信したメールを1通ずつEmail Workerに渡し、Email Workerがそのメールを**Webhook URL**に送信します。受信ドメインのDNSは、Cloudflareで管理している必要があります。

1. Email Routingで、受信ドメインのルーティングを有効にします。`reply.comics.example.com`のようなサブドメインは、**Settings** › **Subdomains**で追加します。MXレコードはCloudflareが自動で追加します。同じ設定画面で**Subaddressing**も有効にしてください。これで、`contact+<message ID>@`宛てのメールが`contact@`のルールで処理されるようになります。
2. Email Routingの宛先アドレスに、スタッフのメールボックスを追加して確認します。サイトが受け取れなかった返信は、このメールボックスに届きます。
3. 下のコードでWorkerを作成します。変数`WEBHOOK_URL`には`inbound:<token>@`の部分を除いた**Webhook URL**を、シークレット`WEBHOOK_TOKEN`にはトークンを、変数`FALLBACK_ADDRESS`にはスタッフのメールボックスを設定します。
4. Email Routingのルーティングルールで、受信ドメインにカスタムアドレス`contact`を作成します。アクションは**Send to a Worker**にし、作成したWorkerを選びます。

```js
export default {
  async email(message, env) {
    let status;
    try {
      const response = await fetch(env.WEBHOOK_URL, {
        body: await new Response(message.raw).arrayBuffer(),
        headers: {
          Authorization: `Basic ${btoa(`inbound:${env.WEBHOOK_TOKEN}`)}`,
          "Content-Type": "message/rfc822",
          "X-Envelope-To": message.to,
        },
        method: "POST",
      });
      if (response.ok) {
        return;
      }
      status = response.status;
    } catch {
      // The site did not answer.
    }
    if (status === 400) {
      message.setReject("The site could not read this mail");
      return;
    }
    try {
      await message.forward(env.FALLBACK_ADDRESS);
    } catch {
      message.setReject(
        `The reply could not be delivered (${status ?? "no answer"})`
      );
    }
  },
};
```

`message.to`は、メールの配送先アドレスです。`+<message ID>`の部分も含まれます。

CloudflareのEmail Workerには、後で再送するよう送信者に求める手段がありません。メールを拒否するとそれで確定し、読者にはバウンスメールが届きます。そのため、このWorkerがメールを拒否するのは、読み取れるメールではないとしてサイトが受け付けなかった場合だけです。サイトが応答しない場合や、メールを受け取れない場合は、Workerがメールをスタッフのメールボックスに転送します。受け取れない場合とは、サイトが停止していて`5xx`を返すときや、管理画面に保存したトークンとWorkerのトークンが食い違っていて`401`を返すときです。転送された返信は、管理画面ではなくそのメールボックスで読みます。メールを拒否するのは、転送にも失敗した場合だけです。サイトが受け付けた後で破棄したメールは、受け付けたものとして扱われ、ほかのどこにも届きません。どのお問い合わせ宛てかを示していないメールや、**有効化**のチェックが外れているあいだに届いたメールがこれに当たります。

### Postfixからメールを送る

受信ドメインのメールを受信するPostfixサーバーでは、`pipe`トランスポートから`curl`で1通ずつメールを送信できます。ドメインのMXレコードをこのサーバーに向け、次のスクリプトを`/usr/local/bin/publira-inbound`として保存します。スクリプトには、**Webhook URL**をトークンと、トークンを除いたURLに分けて書きます。

```sh
#!/bin/sh
# Posts the mail on standard input for the recipient named as $1, and tells
# Postfix whether a failure is worth retrying.
status=$(curl --silent --output /dev/null --write-out '%{http_code}' \
  --max-time 60 --user 'inbound:<token>' \
  --header 'Content-Type: message/rfc822' \
  --header "X-Envelope-To: $1" \
  --data-binary @- \
  https://comics.example.com/api/v1/webhook/email/mime)
case "$status" in
  2??) exit 0 ;;
  400) exit 65 ;; # EX_DATAERR: not a mail the site can read; bounce it
  *) exit 75 ;;   # EX_TEMPFAIL: keep it queued and try again later
esac
```

Postfixは、コマンドが知らない終了ステータスで終わったメールをバウンスします。`curl`の終了ステータスもPostfixの知らないものです。そのため、このスクリプトはPostfixが理解する2つのステータスで応答します。バウンスするのは、メールではないとしてサイトが受け付けなかった送信だけです。それ以外の場合はメールがキューに残り、Postfixはキューの保持期間が切れるまで再試行します。それ以外の場合とは、応答がないとき、サイトが停止していて`5xx`を返すとき、管理画面に保存したトークンとスクリプトのトークンが食い違っていて`401`を返すときです。スクリプトにはトークンが書かれているので、トランスポートのユーザーだけが読めるようにしてください。`chown nobody /usr/local/bin/publira-inbound`と`chmod 700 /usr/local/bin/publira-inbound`を実行します。

`/etc/postfix/master.cf`に、トランスポートを追加します。

```text
publira   unix  -       n       n       -       -       pipe
  user=nobody argv=/usr/local/bin/publira-inbound ${recipient}
```

次に、ドメインのメールをこのトランスポートに送るよう、`/etc/postfix/main.cf`に次の設定を書きます。`${recipient}`が1つのアドレスを指すように、1回の送信の宛先は1つにします。

```text
relay_domains = reply.comics.example.com
transport_maps = hash:/etc/postfix/transport
publira_destination_recipient_limit = 1
```

`/etc/postfix/transport`には、次のように書きます。

```text
reply.comics.example.com  publira:
```

最後に、`postmap /etc/postfix/transport`と`postfix reload`を実行します。
