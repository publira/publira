# Scenarios

This directory holds scenario seeds for UI checks and E2E tests. They are separate from baseline and development seeds, and each runs **only when needed**.

## Principles

- File name: `<nnn>_<slug>.sql` or `<slug>.sql` (for example, `010_multi_tenant.sql`)
- A scenario seed contains only idempotent DML. Use `ON CONFLICT` and an ID range that does not break the shared development seeds
- Do not put DDL here. Schema changes go in a new migration under `db/migrations/` — see [`db/AGENTS.md`](../../AGENTS.md)

## Applying a scenario

### Manually

```bash
# Example using the E2E Compose Postgres instance (the port is the e2e/compose.yaml default)
export PUBLIRA_DB_URL="${PUBLIRA_DB_URL:-postgres://postgres:password@127.0.0.1:5433/publira?sslmode=disable}"
psql "${PUBLIRA_DB_URL:?Set PUBLIRA_DB_URL to the target database URL}" \
  -v ON_ERROR_STOP=1 \
  -f db/seeds/scenarios/010_multi_tenant.sql
```

### From E2E (Playwright)

1. After starting the stack and running `task e2e:db`, call it in a test:

```ts
import { applyScenarioSql } from "../src/db";

test.beforeAll(() => {
  applyScenarioSql("010_multi_tenant"); // → db/seeds/scenarios/010_multi_tenant.sql
});
```

2. The E2E scripts set `PUBLIRA_DB_URL`. When running `pnpm exec playwright test` alone, export the same URL.

For detailed E2E operation, see [e2e/README.md](../../../e2e/README.md).

## List

| File | Description |
| --- | --- |
| `010_multi_tenant.sql` | Adds a second tenant, `other.localhost` / `Boundary Tenant`, alongside the development seed's `localhost` / `Seed Tenant`. It has one published series (two published episodes and one unpublished scheduled episode), one unpublished series, and one page, and is used to verify tenant boundaries and publication decisions (`e2e/tests/catalog.tenant-boundary.spec.ts`, `e2e/tests/admin.published-pages.spec.ts`). Its record `public_id` values — and the page's uuid, which has no `public_id` — are constants in `e2e/src/scenarios/multi-tenant.ts` |
| `020_member_announcements.sql` | Seed for member-announcement pagination (`e2e/tests/announcements.pagination.spec.ts`) |
| `030_platform_operators.sql` | Adds limited `platform_operator` accounts, all `platformpass`, in addition to the development seed's super admin. `platform-operator@example.com` (public_id `ScenPFUSAAA1`) verifies permissions by role (`e2e/tests/platform.tenant-ops.spec.ts`). `platform-role-change@example.com` (`ScenPFUSAAA3`) and `platform-deactivated@example.com` (`ScenPFUSAAA4`) are promoted and deactivated by `e2e/tests/platform.operator-management.spec.ts`, which is why they are separate accounts from the first: it signs in as them after changing them, and the role-denial cases need theirs left a plain active operator. Re-applying the file restores all three, including replacing the roles the promotion rewrote. Constants are in `e2e/src/scenarios/platform-tenants.ts` |
| `040_auth_e2e.sql` | Accounts used only by authentication E2E tests. Adds `auth-admin@example.com`, `auth-member@example.com`, and `auth-platform@example.com` so that bumping `credentials_version` does not break development-seed sessions (`e2e/tests/admin.auth.spec.ts` / `host.auth.spec.ts` / `platform.auth.spec.ts`). Constants are in `e2e/src/scenarios/auth.ts` |
| `050_viewer_pages.sql` | Gives the development seed's free episode `Seed Episode 001-02` (`SeedEPSDAAA2`) eight body images — not the series' first episode, whose empty body other suites assert on — so the canvas viewer has pages to fetch, decode, and draw (`e2e/tests/host.viewer-performance.spec.ts`). Unlike the scenarios above it is not applied from a test: the rows are useless without the matching objects in storage, so `e2e/scripts/seed-viewer-pages.sh` applies it and uploads `e2e/fixtures/viewer-pages/*.jpg` to the object keys it names, and `task e2e:db` runs that script for the whole stack. Constants are in `e2e/src/scenarios/viewer-pages.ts` |
| `060_notification_inbox.sql` | Adds `notify.localhost` / `admin.notify.localhost` / `Notify Tenant` with one admin (`notify-admin@example.com`) and one member (`notify-member@example.com`). Publishing an episode notifies every member and every admin of that episode's tenant, so the specs that assert an empty notification bell (`e2e/tests/host.notifications.spec.ts` / `admin.notifications.spec.ts`) use a tenant that owns no series instead of the development seed accounts `admin.publish-flow` delivers to. Both specs apply it themselves, the way the scenarios before `050_viewer_pages.sql` do. Constants are in `e2e/src/scenarios/notification-inbox.ts` |
| `070_member_settings.sql` | Adds `settings-member@example.com` / `memberpass` (public_id `MsetMMBRAAA1`) to the development seed tenant. The member area E2E (`e2e/tests/host.member-settings.spec.ts`) renames the reader, switches their email notifications off, and follows a series, none of which the development seed member can absorb while `host.auth` signs in with its address and `announcements.pagination` reads its list. The spec applies the file before and after itself, so every statement in it either writes the starting value or deletes the rows the spec creates. Constants are in `e2e/src/scenarios/member-settings.ts` |
| `080_locale_switching.sql` | Adds `locale.localhost` / `admin.locale.localhost` / `Locale Tenant` (public_id `LangTNNTAAA1`), whose stored default locale is `ja` where every other seeded tenant stores `en`. Used by `e2e/tests/host.locale-switching.spec.ts` and `admin.locale-switching.spec.ts`. It owns no series and no users. Constants are in `e2e/src/scenarios/locale-switching.ts` |
| `090_email_change.sql` | Adds `email-change-member@example.com` / `memberpass` (public_id `EchgMMBRAAA1`) to the development seed tenant. The email address change E2E (`e2e/tests/host.email-change.spec.ts`) moves the account to `email-change-member-new@example.com` and signs in with it, which no account another suite authenticates as can absorb. The spec applies the file before and after itself, so it both writes the starting address and deletes the change requests the spec creates. Constants are in `e2e/src/scenarios/email-change.ts` |
| `100_account_lifecycle.sql` | Adds `account-lifecycle-member@example.com` / `memberpass` (public_id `AlifMMBRAAA1`) to the development seed tenant, and removes the accounts `account-lifecycle-new@example.com` and `account-lifecycle-expired@example.com` that the suite signs up. The reader account lifecycle E2E (`e2e/tests/host.account-lifecycle.spec.ts`) signs those two addresses up from `/signup` and resets the member's password, neither of which an account another suite signs in with can absorb: a sign-up needs an address that is not registered when the run starts, and a reset rewrites the password hash. The spec applies the file before and after itself, so it both writes the starting password and removes the accounts the sign-ups create. Constants are in `e2e/src/scenarios/account-lifecycle.ts` |
| `110_platform_setup.sql` | Puts the platform back the way the development seed leaves it: re-inserts `platform_config` and the super admin `platform@example.com` (public_id `SeedPFUSAAA1`), and removes `setup-operator@example.com`. The initial-setup E2E (`e2e/tests/platform.setup.spec.ts`) needs a platform with no operator at all, since `/setup` renders only while `platform_users` is empty, so it empties that table (`emptyPlatformOperators()` in `e2e/src/db.ts`) and applies this file afterwards whether it passed or failed. Constants are in `e2e/src/scenarios/platform-setup.ts` |
| `120_admin_reporting.sql` | Rows for the two read-only web-admin screens (`e2e/tests/admin.reporting.spec.ts`). Gives the development seed tenant 45 audit entries pinned to 2026-01-05 through 2026-01-13 (`rpt-audit-NNN`), so a date filter isolates them from the development seed's entries and from whatever the parallel specs write, and `content_daily_stats` rows for its first 25 episodes dated relative to the tenant's own calendar day the file is applied on, inside the read-through report's window, with rows just outside it that the report must leave out. Adds a tenant admin to the Boundary Tenant of `010_multi_tenant.sql`, `boundary-admin@example.com` / `adminpass` (public_id `BndrADMNAAA1`), with three audit entries of its own (`rpt-boundary-NNN`) and one read-through row, so the tenant boundary of both screens is asserted from both consoles; apply `010_multi_tenant.sql` first. Constants are in `e2e/src/scenarios/admin-reporting.ts` |
| `130_admin_operator_settings.sql` | Adds `aset.localhost` / `admin.aset.localhost` / `Operator Settings Tenant` (public_id `AsetTNNTAAA1`) with one tenant admin, `aset-admin@example.com` / `adminpass` (public_id `AsetADMNAAA1`). The admin operator-settings E2E (`e2e/tests/admin.operator-settings.spec.ts`) moves that account's email address and enables this tenant's SMTP override, neither of which the development seed admin or the seed tenant's SMTP row can absorb while other suites sign in as that address or send mail through that tenant. The spec applies the file before and after itself, so it both writes the starting address and SMTP row and deletes the change requests the spec creates. Constants are in `e2e/src/scenarios/operator-settings.ts` |
| `131_platform_operator_settings.sql` | Adds `aset-platform@example.com` / `platformpass` (public_id `AsetPFUSAAA1`) as a `platform_operator`, and restores the platform SMTP Reply-to to the development seed's `support@platform.local`. The platform operator-settings E2E (`e2e/tests/platform.operator-settings.spec.ts`) moves that account's email address and saves a Reply-to, which no account another suite authenticates as can absorb. The spec applies the file before and after itself, so it both writes the starting address and Reply-to and deletes the change requests the spec creates. Constants are in `e2e/src/scenarios/operator-settings.ts` |
| `140_episode_comments.sql` | Adds `comment.localhost` / `admin.comment.localhost` / `Comment Tenant` (public_id `CmntTNNTAAA1`) with `tenant_config.comment_mode` set to `immediate`, one published free episode (`CmntEPSDAAA1`), and two members, `comment-author@example.com` and `comment-reader@example.com` / `memberpass`. `comment_mode` is one setting for a whole tenant, so the episode comment E2E (`e2e/tests/host.episode-comments.spec.ts`) cannot turn commenting on for the development seed tenant while the reading and viewer-performance suites open its episode pages; two members are what lets the suite assert what one reader sees of another's comment. The spec applies the file before and after itself, and the file deletes every comment on that episode, so a re-run starts from an empty list. Constants are in `e2e/src/scenarios/episode-comments.ts` |
| `150_comment_moderation.sql` | Adds `moderate.localhost` / `admin.moderate.localhost` / `Moderation Tenant` (public_id `ModrTNNTAAA1`) with `tenant_config.comment_mode` set to `approval_required`, one published free episode (`ModrEPSDAAA1`), a tenant admin (`moderate-admin@example.com` / `adminpass`) and a member (`moderate-member@example.com` / `memberpass`). `comment_mode` is one setting for a whole tenant, so the tenant that holds comments for approval cannot be the `immediate` one of `140_episode_comments.sql`; the admin console E2E (`e2e/tests/admin.comment-moderation.spec.ts`) needs both an account to post as and one to moderate as, so this tenant owns both. The spec applies the file before and after itself, and the file deletes every comment on that episode, so a re-run starts from an empty queue. Constants are in `e2e/src/scenarios/comment-moderation.ts` |
